[AWS/Streaming] Consumer를 늘렸는데 Kinesis 지연이 줄지 않는 이유 - Shard, EFO, KCL

Kinesis의 write, read, processing capacity를 분리하고 EFO 선택, KCL checkpoint, resharding과 운영 SLO를 함께 설계합니다.

2026.09.22AWSKinesisEFOKCL

주문 event를 Kinesis Data Streams에 발행하고 fraud detection, 고객 알림과 analytics가 각각 소비한다고 가정해보겠습니다. 처음에는 fraud consumer 하나뿐이라 지연이 거의 없었습니다. analytics와 notification consumer를 추가하자 IteratorAge가 함께 증가했고, worker 수를 두 배로 늘려도 특정 shard의 backlog는 줄지 않았습니다.

이 상황에서 "consumer instance가 부족하다"고 결론 내리면 compute 비용만 늘 수 있습니다. 병목은 producer의 write capacity, 여러 consumer가 공유하는 read capacity, partition key가 만든 hot shard, KCL worker의 처리 성능과 downstream sink 중 어디에나 있을 수 있기 때문입니다.

이 글은 실제 production incident의 성과 보고서가 아니라 주문 event stream을 운영하기 위한 설계와 검증 계획입니다. 아래 처리량, latency와 오류율은 실측 결과가 아닌 초기 acceptance target입니다. load test와 장애 실험 결과를 채우기 전까지 production-grade를 달성했다고 주장하지 않습니다.

1. Stream이 아니라 end-to-end 처리 완료를 성공으로 정의한다

PutRecords 요청이 성공했다고 주문 projection이 갱신된 것은 아닙니다. Kinesis에 record가 저장된 시점과 consumer가 업무 효과를 commit한 시점을 분리해서 측정해야 합니다.

flowchart LR producer[Order producer] --> write[Write capacity] write --> shard[Kinesis shards] shard --> delivery[Shared read or EFO] delivery --> worker[KCL workers] worker --> sink[Business sink] sink --> done[Observable business completion]
계층용량을 결정하는 값대표 실패

Read deliveryshard별 shared throughput 또는 EFO consumer 수consumer 간 경합, subscription 오류

운영 SLO는 "stream이 ACTIVE"가 아니라 "정상 event의 99%가 5초 안에 모든 중요 projection에 반영"처럼 업무 완료 시점으로 정의합니다. AWS service metric은 원인 분석에 쓰고, 성공 여부는 application metric과 reconciliation 결과로 판단합니다.

2. Shard 수는 write와 read 중 더 큰 요구량으로 계산한다

Provisioned mode의 shard 하나는 최대 1 MB/s 또는 1,000 records/s의 write를 받고, shared-throughput consumer에는 shard당 합계 2 MB/s의 read를 제공합니다. 두 제한은 동시에 적용되므로 record가 작다고 byte 계산을 생략하거나, byte가 작다고 record 수를 무시하면 안 됩니다.

write_shards_by_bytes   = ceil(peak_write_MBps / 1)
write_shards_by_records = ceil(peak_records_per_second / 1000)
shared_read_shards      = ceil(sum(consumer_read_MBps) / 2)

base_shards = max(
  write_shards_by_bytes,
  write_shards_by_records,
  shared_read_shards
)

planned_shards = ceil(base_shards x headroom_ratio)

peak write가 6.4 MB/s, 4,000 records/s이고 세 consumer가 모든 record를 shared 방식으로 읽는다면 write 기준은 7개와 4개지만 aggregate read는 19.2 MB/s이므로 read 기준은 10개입니다. 여기에 30% headroom을 적용하면 초기 계획은 13개 shard가 됩니다.

이 계산은 균등 분포를 전제로 한 하한선입니다. 평균 사용률이 50%여도 하나의 partition key가 shard 한 개의 한도를 넘으면 해당 shard만 throttle됩니다. 그래서 shard count와 partition key 검증은 같은 capacity review에서 다룹니다.

3. Partition key는 데이터 분배와 순서 보장의 범위를 동시에 정한다

Kinesis는 partition key를 hash key로 변환해 shard에 record를 배치합니다. 같은 partition key의 record는 같은 shard에 들어가므로 해당 key 안의 순서를 다룰 수 있지만, 낮은 cardinality key는 hot shard를 만들기 쉽습니다.

후보장점위험판단
tenantIdtenant 단위의 전체 순서대형 tenant 하나가 shard 한도를 독점tenant 간 크기 편차가 크면 제외
orderId높은 cardinality, 주문 단위 순서tenant 전체 순서는 제공하지 않음주문 상태 전이가 독립적이면 선택
tenantId#bucket대형 tenant traffic 분산tenant 전체 순서를 downstream에서 복원해야 함명시적 sequence와 병합 로직이 있을 때만 선택
random UUID분배가 쉬움업무 순서와 재현 가능한 routing을 잃음순서가 전혀 필요 없는 telemetry에 한정

주문 stream에서는 orderId를 선택합니다. 한 주문 안의 상태 순서는 유지하면서 여러 주문을 shard에 분산할 수 있기 때문입니다. tenant 전체 순서가 필요하다는 요구가 생기면 key만 바꾸지 않고, 그 순서가 정말 업무 invariant인지부터 재검토합니다.

4. On-demand도 가능하지만 이 workload에서는 Provisioned를 선택한다

On-demand mode는 shard capacity planning과 일반적인 traffic 증가 대응을 AWS에 맡길 수 있습니다. 그러나 단일 partition key가 shard의 1 MB/s 또는 1,000 records/s write 한도를 넘는 문제는 자동 scaling으로 해결되지 않습니다. 과거 peak의 두 배를 갑자기 넘는 traffic에서도 일시적인 read·write exception이 발생할 수 있으므로 retry는 여전히 필요합니다.

선택지장점운영 책임적합한 조건
On-demand초기 sizing과 shard 증감 작업 감소partition skew, 급격한 peak와 비용 추적traffic 예측이 어렵고 운영 인력이 작음
Provisionedcapacity와 shard-level 병렬성을 명시적으로 통제sizing, resharding과 headroom 관리지속 부하가 예측 가능하고 검증 가능한 변경 절차가 있음

이 설계는 일별 peak가 반복되고, consumer별 latency gate와 비용 예산을 shard 수에 직접 연결해야 하므로 Provisioned를 선택합니다. 이것이 항상 더 저렴하다는 뜻은 아닙니다. 실제 30일 traffic과 reshard 운영 비용을 비교해 On-demand가 유리하면 mode를 변경하되, 동일한 skew와 retry test를 다시 통과해야 합니다.

5. Shared throughput과 EFO는 consumer 중요도에 따라 섞어 쓴다

shared-throughput consumer는 GetRecords로 polling하며 shard당 2 MB/s를 모든 shared consumer가 나눠 씁니다. Enhanced Fan-Out은 등록된 consumer마다 shard당 최대 2 MB/s의 전용 read throughput을 제공하고 SubscribeToShard로 record를 push합니다. 대신 consumer-shard hour와 retrieval 비용이 추가됩니다.

flowchart TB shard[Kinesis shard] shard --> shared[Shared read capacity] shared --> analytics[Analytics consumer] shard --> fraud[EFO pipe for fraud] shard --> notify[EFO pipe for notification] fraud --> fraudsink[Fraud decision store] notify --> notifysink[Notification workflow] analytics --> lake[Analytics lake]

세 consumer를 모두 EFO로 바꾸지 않습니다. 중요 consumer 두 개만 read 경합에서 분리하고 analytics 하나가 shared capacity를 사용하도록 구성합니다. 이 경우 앞선 예시의 shared read 요구량은 6.4 MB/s이므로 4개 shard이고, write 7개가 더 큰 기준입니다. 30% headroom을 적용하면 10개 shard에서 시작할 수 있습니다.

6. EFO는 hot shard와 느린 sink를 고치는 기능이 아니다

EFO 전환 뒤에도 lag가 남을 수 있습니다. 전용 read pipe가 해결하는 것은 consumer 간 read throughput 경합입니다. 하나의 partition key가 write capacity를 넘거나, record processor가 database connection을 기다리거나, poison event가 checkpoint를 막는 문제는 그대로 남습니다.

7. Stream과 EFO consumer identity를 IaC로 고정한다

runtime이 매번 다른 consumer name을 등록하게 두면 배포 version마다 비용과 quota가 누적되고 IAM resource도 추적하기 어려워집니다. 중요 consumer는 IaC에서 이름과 lifecycle을 관리하고, runtime에는 승인된 consumer identity만 주입합니다.

Resources:
  OrderEventsStream:
    Type: AWS::Kinesis::Stream
    Properties:
      Name: order-events
      ShardCount: 10
      RetentionPeriodHours: 72
      StreamModeDetails:
        StreamMode: PROVISIONED
      StreamEncryption:
        EncryptionType: KMS
        KeyId: alias/aws/kinesis
      Tags:
        - Key: Owner
          Value: order-platform
        - Key: DataClass
          Value: internal

  FraudConsumer:
    Type: AWS::Kinesis::StreamConsumer
    Properties:
      ConsumerName: order-fraud-v1
      StreamARN: !GetAtt OrderEventsStream.Arn

  NotificationConsumer:
    Type: AWS::Kinesis::StreamConsumer
    Properties:
      ConsumerName: order-notification-v1
      StreamARN: !GetAtt OrderEventsStream.Arn

72시간 retention은 24시간을 넘는 consumer 장애와 주말 대응을 흡수하기 위한 초기 recovery budget입니다. 장기 보관 목적은 S3 archive가 담당하고, Kinesis retention은 replay 가능한 운영 시간만 포함합니다. 배포는 EFO consumer가 ACTIVE인지 확인한 뒤 KCL worker를 시작합니다.

KCL이 consumer를 runtime에 직접 등록하도록 둘 수도 있지만 그 경우에만 RegisterStreamConsumer 권한을 부여합니다. IaC가 등록을 소유한다면 consumer ARN을 runtime 설정에 명시하고 등록 권한을 제거해 소유권을 한쪽으로 정합니다.

8. PutRecords의 HTTP 200을 batch 전체 성공으로 해석하지 않는다

PutRecords는 한 요청 안에서 성공 record와 실패 record를 함께 반환할 수 있습니다. 하나가 성공해도 API 응답 자체는 HTTP 200일 수 있으므로 FailedRecordCount와 각 result의 ErrorCode를 검사해야 합니다.

def put_with_bounded_retry(client, stream_arn, entries, max_attempts=5):
    pending = entries

    for attempt in range(max_attempts):
        response = client.put_records(
            StreamARN=stream_arn,
            Records=pending,
        )

        failed = [
            original
            for original, result in zip(pending, response["Records"])
            if "ErrorCode" in result
        ]
        if not failed:
            return

        pending = failed
        sleep_with_full_jitter(attempt)

    raise PublishIncomplete(pending)

성공 record까지 batch 전체를 다시 보내면 duplicate를 불필요하게 늘립니다. 실패 항목만 bounded exponential backoff와 jitter로 재시도하고, 예산을 소진한 event는 durable outbox에 남겨 별도 relay가 복구합니다. PutRecords는 batch 안의 엄격한 순서를 보장하지 않으므로 반드시 같은 key의 write 순서가 필요하다면 순차적인 PutRecord 경로를 검토합니다.

9. Event contract에는 replay와 중복 처리를 위한 식별자를 넣는다

{
  "eventId": "01K5R8VDF4T2N6Q9W7C3M1P0AZ",
  "eventType": "OrderStatusChanged.v2",
  "aggregateId": "ord-20260922-004821",
  "aggregateVersion": 7,
  "partitionKey": "ord-20260922-004821",
  "occurredAt": "2026-09-22T00:15:21.204Z",
  "producer": "order-api@4f8c1d2",
  "traceId": "1-68d0...",
  "payload": {
    "previousStatus": "PAID",
    "currentStatus": "FULFILLING"
  }
}
  • eventId는 consumer idempotency key와 quarantine key로 사용합니다.
  • aggregateVersion은 오래된 상태가 최신 projection을 덮지 못하게 합니다.
  • occurredAt은 Kinesis iterator lag와 별도로 업무 end-to-end lag를 계산합니다.
  • producer와 schema version은 incompatible producer를 추적하는 근거입니다.
  • partition key와 payload에는 불필요한 개인정보를 넣지 않습니다.

schema 변경은 additive change부터 적용하고, consumer가 이전과 새 version을 함께 읽는 기간을 둡니다. required field 삭제나 의미 변경은 새 event type으로 분리하고 compatibility fixture를 CI에 고정합니다.

10. KCL application name은 배포 이름이 아니라 durable consumer identity다

KCL은 application name을 기준으로 DynamoDB lease와 checkpoint state를 관리합니다. 같은 business consumer의 pod가 여러 개여도 application name은 같아야 shard를 나눠 처리합니다. 반대로 fraud와 notification이 같은 application name을 쓰면 서로의 lease를 빼앗아 각 event를 한쪽만 처리할 수 있습니다.

stream_name: order-events

consumers:
  fraud:
    kcl_application_name: order-fraud-v1
    delivery: enhanced-fan-out
    registered_consumer_name: order-fraud-v1
    initial_position: TRIM_HORIZON
  notification:
    kcl_application_name: order-notification-v1
    delivery: enhanced-fan-out
    registered_consumer_name: order-notification-v1
    initial_position: TRIM_HORIZON
  analytics:
    kcl_application_name: order-analytics-v1
    delivery: polling
    initial_position: TRIM_HORIZON

initial_position은 lease table에 checkpoint가 없는 최초 bootstrap에서만 기대한 시작점을 결정합니다. 기존 application name의 lease가 남아 있다면 설정을 바꿔도 과거 checkpoint에서 재개할 수 있습니다. replay가 필요할 때 production application name을 재사용하지 않고 별도 replay identity와 sink namespace를 사용합니다.

11. KCL 3.x metadata table도 application resource로 운영한다

KCL 3.x는 기본적으로 application마다 lease table, worker metrics table과 coordinator state table을 DynamoDB에 만듭니다. lease table에는 shard owner, checkpoint와 parent-child lineage가 저장됩니다. 이 table은 임시 cache가 아니라 consumer의 처리 위치를 가진 운영 state입니다.

Resource역할운영 정책
Lease tableshard lease와 checkpoint 저장on-demand billing, PITR·backup 요구 검토, 삭제 승인
Worker metrics tableKCL 3.x worker utilization 기반 balancinglibrary version과 migration 상태 추적
Coordinator state tableleader와 migration coordination일반 업무 table과 분리된 ownership
KCL custom metricslease, processing과 lag 관측namespace, detail level과 비용 예산 설정

KCL은 application을 폐기해도 metadata table을 자동으로 모두 삭제하지 않습니다. decommission checklist에 consumer deregistration, table snapshot 필요 여부, retention 기간, 삭제 승인과 IAM 제거를 포함합니다. KCL 3.5의 single-table format을 도입한다면 별도 migration과 rollback gate를 거치며 단순한 비용 최적화 변경으로 취급하지 않습니다.

12. Worker를 shard보다 많이 늘려도 한 shard는 더 빨라지지 않는다

KCL에서 하나의 shard lease는 한 시점에 한 worker가 소유하고, 해당 shard의 record processor가 순차적인 처리 위치를 관리합니다. open shard가 10개라면 processing parallelism의 상한도 기본적으로 10개입니다. standby 목적이 아니라면 worker를 20개로 늘려도 나머지는 처리할 shard가 없습니다.

flowchart TB leases[(KCL lease table)] leases --> w1[Worker A] leases --> w2[Worker B] leases --> w3[Worker C] w1 --> s1[Shard 1 processor] w1 --> s2[Shard 2 processor] w2 --> s3[Shard 3 processor] w2 --> s4[Shard 4 processor] w3 --> s5[Shard 5 processor] w3 --> s6[Shard 6 processor]

lag가 늘면 worker 수부터 올리지 않습니다. MillisBehindLatest, RecordProcessor.processRecords.Time, CPU, memory, CurrentLeases, LostLeases와 downstream latency를 함께 봅니다. 모든 worker가 CPU 포화라면 instance와 worker를 늘리고, 특정 shard만 느리면 hot key 또는 해당 shard의 slow event를 찾습니다.

13. Checkpoint는 읽은 위치가 아니라 durable side effect가 끝난 위치다

KCL checkpoint는 마지막으로 안전하게 처리한 sequence number를 DynamoDB lease table에 기록합니다. checkpoint를 먼저 쓰고 sink commit에 실패하면 record를 건너뛰어 data loss가 생깁니다. sink를 먼저 commit하고 checkpoint 전에 worker가 죽으면 같은 record가 replay됩니다.

sequenceDiagram participant K as Kinesis shard participant W as KCL worker participant S as Idempotent sink participant L as Lease table K->>W: Deliver record batch W->>S: Validate and apply events S-->>W: Durable commit W->>L: Checkpoint last committed record Note over W,L: Crash before checkpoint causes replay L-->>W: Resume after checkpoint on restart

따라서 KCL은 at-least-once processing으로 보고 sink를 idempotent하게 만듭니다. batch checkpoint 간격을 길게 잡으면 DynamoDB write와 overhead는 줄지만 crash 시 replay 범위가 커집니다. 간격은 비용보다 허용 가능한 duplicate replay window와 recovery time을 기준으로 결정합니다.

14. Record processor는 permanent failure와 retryable failure를 분리한다

@Override
public void processRecords(ProcessRecordsInput input) {
    for (KinesisClientRecord record : input.records()) {
        try {
            OrderEvent event = decoder.decode(record.data());
            contractValidator.validate(event);

            projectionStore.applyIdempotently(
                event.eventId(),
                event.aggregateId(),
                event.aggregateVersion(),
                event.payload()
            );
        } catch (UnsupportedEventException permanent) {
            quarantineStore.putIfAbsent(
                record.sequenceNumber(),
                record.partitionKey(),
                record.data(),
                permanent.getClass().getSimpleName()
            );
        } catch (RetryableDependencyException retryable) {
            throw retryable;
        }
    }

    input.checkpointer().checkpoint();
}

schema가 잘못된 permanent failure는 원문을 암호화된 quarantine에 durable하게 저장한 뒤 처리 완료로 간주할 수 있습니다. quarantine write 자체가 실패하면 checkpoint하지 않습니다. dependency timeout 같은 retryable failure는 batch를 실패시켜 이전 checkpoint부터 재처리합니다. 이미 성공한 record도 다시 올 수 있으므로 projection의 conditional write가 중복을 흡수해야 합니다.

예외를 log만 남기고 계속 진행하면 event 유실이 되고, 모든 예외를 무한 재시도하면 poison event 하나가 shard 전체를 막습니다. 실패 분류, 격리 저장소와 replay 승인 절차가 record processor 계약의 일부입니다.

15. Idempotent sink는 event ID와 aggregate version을 함께 확인한다

eventId만 저장하면 동일 event의 재실행은 막을 수 있지만, 서로 다른 event가 오래된 상태를 덮는 문제는 막지 못합니다. projection row에 마지막 aggregate version을 함께 저장하고 더 큰 version만 적용합니다.

UPDATE order_projection
SET status = :status,
    last_event_id = :event_id,
    aggregate_version = :version,
    updated_at = CURRENT_TIMESTAMP
WHERE order_id = :order_id
  AND aggregate_version < :version;

영향 row가 0이라면 이미 같은 또는 더 최신 version이 적용됐는지 조회합니다. payload가 같은 duplicate면 성공으로 반환하고, 같은 version에 다른 payload가 들어왔다면 producer contract violation으로 격리합니다. 외부 API 호출은 해당 서비스가 제공하는 idempotency key를 함께 사용하며, 결과가 불명확한 timeout은 조회와 reconciliation 대상으로 남깁니다.

16. Resharding과 KCL worker scaling은 서로 다른 작업이다

KCL은 shard split과 merge를 발견해 lease를 만들고 worker에 재배치하지만, stream의 shard 수를 스스로 바꾸지는 않습니다. KCL worker scaling은 이미 존재하는 shard를 처리할 compute를 늘리고, resharding은 stream throughput과 병렬 처리 lane을 늘립니다.

flowchart LR alarm[Capacity or lag alarm] --> classify{Bottleneck classification} classify --> capacity[Write or read capacity] classify --> compute[Worker CPU or memory] classify --> dependency[Slow dependency] classify --> hotkey[Single hot key] capacity --> reshard[Update shard count] compute --> workers[Scale KCL workers] dependency --> protectsink[Protect or scale sink] hotkey --> keydesign[Redesign partition contract] reshard --> lineage[Parent and child shard lineage] lineage --> checkpoint[Finish parent and checkpoint] checkpoint --> children[Process child shards]

KCL은 특정 partition key의 순서를 보존하기 위해 parent shard의 기존 record를 모두 처리한 뒤 child shard를 처리합니다. reshard 직후 worker 수를 늘렸는데도 child가 바로 처리되지 않는다면 장애로 단정하지 않고 BlockOnParentTask, parent lag와 checkpoint 상태를 확인합니다.

17. Resharding은 alarm의 자동 반응이 아니라 승인된 변경으로 시작한다

aws kinesis update-shard-count \
  --stream-name order-events \
  --target-shard-count 16 \
  --scaling-type UNIFORM_SCALING

aws kinesis describe-stream-summary \
  --stream-name order-events \
  --query 'StreamDescriptionSummary.{
    Status:StreamStatus,
    OpenShards:OpenShardCount,
    Mode:StreamModeDetails.StreamMode
  }'

UNIFORM_SCALING은 전체 hash range를 균등하게 다시 나누는 운영에 적합하지만 하나의 고정 partition key는 여전히 한 shard에만 매핑됩니다. 단일 key가 1 MB/s를 넘는다면 shard 수 증가를 반복하지 않고 event contract를 분할해야 합니다.

변경 전에는 account와 stream의 reshard quota, retention 안의 replay 여유, KCL worker headroom과 DynamoDB metadata table 상태를 확인합니다. 변경 후에는 open shard 수뿐 아니라 parent drain, lease reassignment, 모든 consumer의 lag와 sink 오류율이 안정화될 때까지 다음 변경을 금지합니다.

producer는 특정 stream의 write만, consumer는 특정 stream과 자신의 EFO consumer·KCL table만, operator는 resharding과 consumer lifecycle만 담당합니다. application runtime에 UpdateShardCount나 광범위한 kinesis:*를 주지 않습니다.

22. SLO와 regression gate를 stream 설정 변경에 연결한다

23. 비용 예산은 shard뿐 아니라 consumer와 운영 state까지 포함한다

Monthly stream cost
  = provisioned shard hours
  + PUT payload units
  + extended retention
  + EFO consumer-shard hours
  + EFO data retrieval
  + KCL DynamoDB metadata reads, writes and storage
  + CloudWatch shard-level metrics and logs
  + worker compute
  + replay and quarantine storage

EFO 비용은 등록 consumer 수와 shard 수의 곱에 민감합니다. shard를 10개에서 16개로 늘리면 stream capacity뿐 아니라 EFO consumer-shard hour와 KCL 처리 parallelism에 필요한 worker 비용도 함께 변합니다. 사용하지 않는 EFO consumer를 등록 상태로 방치하지 않고 decommission gate에서 제거합니다.

비용 최적화는 중요 consumer를 shared로 되돌리는 단일 결정이 아닙니다. 소비 목적이 겹치는 application을 하나로 합칠 수 있는지, analytics를 S3 delivery로 분리할 수 있는지, retention을 줄여도 recovery SLO가 유지되는지부터 확인합니다.

25. 아직 production-grade라고 주장하지 않는 범위

  • 이 글의 6.4 MB/s, shard 10개, 30% headroom과 latency target은 실제 traffic 측정값이 아닙니다.
  • CloudFormation과 record processor 예시는 전체 배포 가능한 repository가 아니라 핵심 계약을 설명하는 부분 구현입니다.
  • 실제 tenant 분포에서 partition key entropy와 단일 key peak를 측정하지 않았습니다.
  • KCL version upgrade와 2.x에서 3.x로의 metadata migration을 rehearsal하지 않았습니다.
  • 10개에서 16개 shard로 reshard하는 동안 모든 consumer의 parent-child 처리를 부하 환경에서 검증하지 않았습니다.
  • downstream database 장애가 retention 72시간을 넘는 재해 복구 절차를 구현하지 않았습니다.
  • Multi-Region stream replication, active-active producer와 global ordering은 다루지 않았습니다.
  • EFO와 worker compute를 포함한 실제 월 비용을 Cost and Usage Report로 검증하지 않았습니다.

이 상태에서 말할 수 있는 것은 "Kinesis consumer scaling의 운영 계약을 설계했다"까지입니다. 실제 peak load, hot key, worker crash, dependency outage, reshard와 replay 결과가 release evidence로 채워져야 production-grade라는 주장이 완성됩니다.

26. 마무리

Kinesis의 lag는 consumer instance 수 하나로 설명되지 않습니다. shard가 write와 read capacity를 만들고, partition key가 부하와 순서 범위를 정하며, EFO가 중요 consumer를 read 경합에서 분리하고, KCL lease와 checkpoint가 처리 위치와 장애 복구를 관리합니다.

Stream 운영의 핵심은 shard를 많이 만드는 것이 아니라 write, delivery, processing과 business completion의 예산을 분리하고, 어느 경계가 실패했는지 증명할 수 있게 만드는 것입니다.
