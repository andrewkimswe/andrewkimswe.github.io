[Data/AI] 데이터는 많은데 왜 의사결정은 느릴까? - Palantir Foundry와 AIP의 Ontology

Ontology가 데이터의 의미를 설명하는 데서 멈추지 않고 판단 로직, 실행 가능한 Action과 보안 경계를 하나의 운영 세계로 연결하는 방식을 살펴봅니다.

2026.09.26DataAI SystemsOntologyGovernance

기업에는 이미 많은 데이터가 있습니다. ERP에는 주문과 재고가 있고, CRM에는 고객 정보가 있으며, 데이터 웨어하우스에는 분석용 데이터가 쌓입니다. 제조 현장에서는 센서 데이터가 실시간으로 생성되고 조직 내부에는 문서, 이미지와 로그 같은 비정형 데이터도 존재합니다.

하지만 데이터를 모으는 것만으로 실제 업무가 바뀌지는 않습니다. 대시보드에서 재고 부족을 발견한 담당자는 다른 시스템으로 이동해 재고 이동을 요청하고, 필요하면 생산 일정을 조정합니다. 그 결정이 어떤 결과를 만들었는지 확인하려면 다시 별도의 수집과 분석 과정이 필요합니다.

Palantir Foundry와 AIP를 살펴보면서 가장 흥미로웠던 부분은 이를 데이터 관리만의 문제가 아니라 의사결정과 실행이 분리된 문제로 바라본다는 점이었습니다. 중심에는 기업의 Data, Logic, Action과 Security를 연결하는 Ontology가 있습니다.

이 글은 Palantir 공식 문서를 바탕으로 제품의 아키텍처를 해석한 개념 정리입니다. 실제 조직에 Foundry 또는 AIP를 도입해 성능, 비용이나 운영 성과를 검증한 사례가 아니며, 제품이 설명하는 목표와 제가 이해한 설계 의미를 구분해 기록합니다.

1. 데이터 파이프라인의 끝이 실제 업무의 끝은 아니다

전통적인 기업 데이터 흐름은 여러 source를 통합하고 정제한 뒤 분석 결과를 사람에게 제공합니다. 이 구조 자체가 잘못된 것은 아닙니다. 문제는 사람이 어떤 결정을 내렸는지, 그 결정을 운영 시스템에서 어떻게 실행했는지, 행동의 결과가 어땠는지가 분석 파이프라인 밖에 남기 쉽다는 점입니다.

flowchart LR sources[Enterprise data sources] --> integrate[Integration and transformation] integrate --> analytics[Analytics and dashboard] analytics --> decision[Human or AI decision] decision --> action[Operational action] action --> result[Business result] result -->|Feedback| sources

재고 부족 알림이 정확해도 실제 재고 이동이 생성되지 않았다면 업무는 끝나지 않았습니다. 반대로 Action이 수행됐어도 결과와 승인 이력이 데이터로 돌아오지 않으면 다음 판단의 근거가 남지 않습니다. 따라서 목표는 dashboard delivery가 아니라 Data, Decision, Action, Feedback이 닫힌 루프를 이루는 것입니다.

2. Ontology는 기업의 명사와 동사를 함께 모델링한다

Palantir의 입문 문서는 Ontology를 object, link와 action의 정의로 구성된 조직의 digital representation이라고 설명합니다. Object는 실제 업무의 명사, link는 관계, action은 그 세계를 바꾸는 동사에 가깝습니다.

구성 요소제조·물류 예시담는 의미
ObjectPlant, Warehouse, Supplier, Shipment, Order업무에서 식별하고 다루는 실체
Property재고량, ETA, lead time, 상태Object의 현재 상태
LinkWarehouse가 Plant에 부품을 공급함Object 사이의 업무 관계
Action재고 이동, 주문 생성, 일정 변경업무 세계를 변경하는 허용된 행동

하나의 Warehouse를 표현하는 데이터가 SAP 테이블, 물류 시스템, 센서와 별도 데이터베이스에 흩어져 있을 수 있습니다. Ontology는 사용자가 저장 위치와 조인 규칙을 먼저 이해하지 않아도 Warehouse A라는 업무 객체와 관련 상태를 중심으로 탐색할 수 있게 합니다.

flowchart LR sap[SAP] --> ontology[Ontology] iot[IoT and time series] --> ontology crm[CRM] --> ontology docs[Documents] --> ontology ontology --> warehouse[Warehouse A] warehouse --> inventory[Inventory] warehouse --> shipments[Shipments] warehouse --> suppliers[Suppliers] warehouse --> actions[Available actions]

그래서 Ontology는 raw data와 business language 사이의 semantic abstraction 역할을 하지만, 그것만으로 설명이 끝나지는 않습니다. Palantir는 읽기 모델뿐 아니라 판단 로직과 쓰기 동작까지 같은 체계에 포함합니다.

3. 핵심은 Data, Logic, Action, Security의 결합이다

공식 Architecture Center는 Ontology를 Data, Logic, Action, Security의 네 축으로 설명합니다. 이 구분을 사용하면 semantic layer와 운영 시스템의 차이를 더 선명하게 볼 수 있습니다.

flowchart TB security[Security and governance] data[Data
What exists] logic[Logic
How to decide] action[Action
What can change] ontology[Ontology] data --> ontology logic --> ontology action --> ontology security -. constrains every interaction .-> data security -.-> logic security -.-> action
축질문가능한 구현
Data현재 무엇이 존재하는가?Object, property, link, 시계열과 문서
Logic상태를 어떻게 판단할 것인가?Business rule, SQL, ML model, optimizer, function
Action무엇을 변경할 수 있는가?Object edit, 승인 workflow, webhook과 외부 system write-back
Security누가 어떤 목적으로 읽고 실행할 수 있는가?Resource·object permission, action permission, audit

Logic은 하나의 AI 모델을 뜻하지 않습니다. 단순한 business rule, 기존 forecasting model, optimizer, LLM 기반 function과 여러 compute engine을 묶은 orchestration이 모두 후보가 될 수 있습니다. Action도 화면의 버튼에 그치지 않고 object를 변경하거나 외부 시스템에 side effect를 전달할 수 있습니다.

4. 재고 부족 시나리오로 Closed Loop를 연결해본다

부품 재고를 관리하는 제조기업을 가정해보겠습니다. 현재 재고는 500개이고 다음 주 예상 수요는 800개이며, 가장 가까운 공급자의 lead time은 8일입니다. 각각의 값만 나열하면 현황 설명이지만, 관계와 Logic을 연결하면 의사결정의 입력이 됩니다.

flowchart LR state[Warehouse A
Inventory 500] --> forecast[Demand forecast
Demand 800] supplier[Supplier
Lead time 8 days] --> evaluate[Shortage evaluation] forecast --> evaluate evaluate --> proposal[Transfer proposal] proposal --> approval{Approval policy} approval -->|Approved| transfer[Create stock transfer] approval -->|Rejected| review[Human review] transfer --> erp[ERP transfer order] erp --> actual[Delivery result] actual --> state

판단과 실행의 주체는 한 가지로 고정되지 않습니다. 사람이 직접 판단할 수 있고, AI가 대안을 제시한 뒤 사람이 승인할 수도 있으며, 충분히 반복되고 검증된 조건에서는 제한된 Action을 자동 실행할 수도 있습니다. 중요한 것은 AI를 넣었다는 사실보다 각 단계의 책임과 권한이 명시되어 있는가입니다.

5. 사람과 AI가 같은 업무 세계를 본다는 의미

LLM은 조직 내부의 warehouse_id=1842가 어떤 공장을 지원하는지, 특정 부품의 lead time이 얼마인지, 어떤 상황에서 재고 이동이 허용되는지 기본적으로 알지 못합니다. 검색으로 관련 문서를 제공할 수는 있지만, 문서의 설명과 실행 가능한 현재 상태는 같지 않습니다.

Ontology는 사람과 AI가 동일한 object, 관계, Logic과 허용된 Action을 참조할 수 있는 공통 기반을 지향합니다. AI agent가 임의의 SQL이나 API를 만들어내는 대신 승인된 업무 객체와 도구의 경계를 따라 행동하도록 만드는 것입니다.

주체강점통제가 필요한 지점
Human맥락 판단, 예외 처리, 책임 있는 승인과도한 권한, 수작업 누락, 판단 근거 기록
AI agent정보 종합, 대안 생성, 반복 workflow 수행도구 allowlist, 입력·출력 검증, approval과 audit
Traditional compute결정적 규칙, 대규모 계산, 최적화버전, 입력 품질, 실패와 timeout 처리

여기서 Ontology는 agent의 지식을 무한히 확장하는 장치라기보다 무엇을 알고 무엇을 할 수 있는지 제한하는 계약에 가깝습니다. Context와 capability를 함께 제공하되 Security가 둘 모두를 제약해야 합니다.

6. 기존 Data Warehouse와의 차이는 기능 목록보다 중심축에 있다

Foundry를 처음 접하면 "결국 데이터를 모아 semantic layer를 만드는 것 아닌가?"라는 질문이 생깁니다. 실제로 warehouse, lakehouse와 semantic layer도 governance, ML과 write-back을 구현할 수 있으므로 제품 간 절대적인 기능 구분은 어렵습니다.

관점분석 중심 구성Foundry/AIP가 강조하는 구성
중심 단위Table, schema, metricBusiness object, link, action
주요 산출물Dataset, report, insightDecision, workflow, operational change
Logic분석·ML 도구에서 별도 관리 가능Object와 Action의 맥락에 연결
외부 시스템주로 data sourceData source이면서 system of action
Feedback별도 pipeline으로 구성의사결정과 결과의 read-write loop를 중심에 둠
AI데이터의 consumer통제된 object와 action을 사용하는 actor

차이는 "다른 플랫폼에서는 불가능하다"가 아니라 어디를 기본 설계 단위로 삼느냐에 있습니다. Foundry/AIP의 설명은 데이터를 최종 산출물로 두기보다 운영 의사결정과 행동을 구성하는 재료로 둡니다.

7. 기존 데이터 플랫폼을 버리는 전략만 있는 것은 아니다

기업에는 이미 Snowflake, Databricks, BigQuery, data lake와 여러 운영 데이터베이스가 있습니다. Palantir의 Multimodal Data Plane은 이를 모두 Foundry storage로 복사해야 한다는 전제 대신, 기존 data와 compute를 연결하는 방향을 제시합니다.

flowchart LR snowflake[Snowflake] --> virtual[Virtual tables and catalogs] databricks[Databricks] --> virtual lake[Object storage and Iceberg] --> virtual virtual --> foundry[Foundry data and Ontology] foundry --> apps[Applications and AI workflows] foundry -->|Pushdown when supported| compute[Source-native compute] compute --> snowflake compute --> databricks

Virtual Table은 지원되는 외부 플랫폼의 table을 Foundry dataset으로 먼저 저장하지 않고 조회할 수 있게 합니다. Pushdown compute는 조건이 맞을 때 계산을 데이터가 있는 runtime으로 보냅니다. 이는 중복 저장과 이동을 줄일 수 있지만 언제나 더 나은 선택은 아닙니다.

선택장점운영 비용과 제약
Virtual Table복제 감소, source의 최신 상태 조회대화형 latency, source 장애 전파, query·egress 비용
Foundry materialization예측 가능한 조회, snapshot과 pipeline 통제저장 중복, freshness 지연, 동기화 책임
Pushdown compute기존 compute 투자와 locality 활용source별 지원 범위, resource contention, 비용 귀속

따라서 "zero-copy"를 목표 자체로 두면 안 됩니다. workload의 latency, freshness, 장애 격리, 규제와 비용 귀속을 기준으로 연결과 materialization을 선택해야 합니다.

8. Action이 강력할수록 Governance는 실행 경로 안에 있어야 한다

챗봇이 잘못된 답을 만드는 것과 agent가 ERP에 잘못된 주문을 생성하는 것은 피해 범위가 다릅니다. Action을 연결하는 순간 governance는 데이터 조회 권한을 넘어 현실 세계에 행사할 수 있는 권한을 통제하는 문제가 됩니다.

flowchart LR request[Human or agent request] --> identity[Identity and purpose] identity --> object[Object-level access] object --> policy[Action policy and validation] policy --> approval{Approval required?} approval -->|Yes| human[Named approver] approval -->|No| execute[Execute action] human --> execute execute --> system[Operational system] system --> audit[Result, lineage and audit] audit --> monitor[Monitoring and review]

최소한 다음 경계가 분리되어야 합니다.

  • Object를 읽을 권한과 Action을 실행할 권한
  • 대안을 생성할 권한과 실제 side effect를 승인할 권한
  • 단일 객체 변경과 대량 변경 또는 고위험 거래
  • 일시적 dependency failure, policy rejection과 business validation failure
  • Action 요청자, 승인자, 실행 identity와 결과를 연결하는 audit trail

AI가 같은 Ontology를 사용한다는 이유만으로 사람과 동일한 권한을 가져서는 안 됩니다. agent별 capability allowlist, parameter constraint, spend 또는 volume limit, timeout, bounded retry와 human approval 조건이 Action 계약에 포함되어야 합니다.

9. Ontology는 모델보다 조직의 소유권 문제에 가깝다

기술적으로 object type을 정의하는 것보다 어려운 일은 어떤 정의가 조직의 기준인지 합의하는 것입니다. Customer, Available Inventory, Delayed Shipment 같은 용어는 팀마다 다르게 해석될 수 있고, Action은 실제 업무 책임과 연결됩니다.

영역필요한 owner결정할 내용
Business objectDomain owner정의, primary key, lifecycle과 품질 기준
Source mappingData platformlineage, freshness, reconciliation과 schema change
LogicDomain·ML owner버전, 입력 계약, 평가와 rollback
ActionOperational service ownervalidation, idempotency, approval과 failure handling
SecuritySecurity·compliance목적 기반 접근, classification, audit와 retention
OutcomeBusiness owner성공 metric, 부작용과 중단 기준

Ontology를 중앙팀이 대신 완성하는 단기 프로젝트로 보면 semantic bottleneck이 생길 수 있습니다. 반대로 각 팀이 독립적으로 object와 action을 늘리면 동일 개념이 중복되고 권한 경계가 흐려집니다. 공통 표준과 domain ownership을 함께 설계해야 합니다.

10. 도입 전에 답해야 할 질문

제품 데모의 완성된 workflow보다 먼저 확인하고 싶은 것은 운영 계약입니다.

  1. 첫 use case의 의사결정은 무엇이며 현재 어느 시스템 사이에서 끊겨 있는가?
  2. 성공을 dashboard 사용량이 아니라 어떤 업무 outcome으로 측정할 것인가?
  3. Object의 source of truth와 freshness budget은 무엇인가?
  4. 동일한 business term의 정의 충돌을 누가 해결하는가?
  5. Action은 어디까지 write-back하며 idempotency와 compensation을 누가 구현하는가?
  6. AI가 제안만 하는 단계와 자동 실행하는 단계를 어떤 evidence로 구분하는가?
  7. Virtual Table의 source 장애와 latency가 critical workflow로 전파되면 어떻게 degrade할 것인가?
  8. Logic, prompt, model과 Ontology 변경을 어떤 regression gate로 검증하는가?
  9. 권한 오설정이나 잘못된 대량 Action을 탐지하고 중단하는 kill switch가 있는가?
  10. 플랫폼 비용뿐 아니라 ontology modeling과 운영 ownership 비용을 누가 부담하는가?

이 질문에 답하지 못한 채 object 수와 agent 수만 늘리면 데이터 통합의 복잡성이 ontology 운영의 복잡성으로 이동할 수 있습니다. 반대로 좁은 use case에서 decision latency, 수작업 단계, 오류율과 승인 시간을 먼저 측정하면 플랫폼의 가치와 위험을 같은 기준으로 볼 수 있습니다.

11. 이 글에서 검증하지 않은 것

  • Foundry 또는 AIP tenant에서 Ontology, Action과 AIP Agent를 직접 구현하지 않았습니다.
  • Virtual Table과 materialized dataset의 latency, 비용과 장애 전파를 측정하지 않았습니다.
  • ERP write-back의 idempotency, transaction boundary와 compensation을 재현하지 않았습니다.
  • 대규모 object·link 환경의 query 성능과 permission evaluation 비용을 검증하지 않았습니다.
  • 다른 data·AI platform과 동일 workload를 구현해 정량 비교하지 않았습니다.
  • 실제 조직에서 ontology ownership, 변경 승인과 adoption이 유지되는지 관찰하지 않았습니다.

따라서 이 글에서 말할 수 있는 것은 Palantir가 제시하는 Ontology 중심 아키텍처의 구조와 설계 질문까지입니다. 실제 도입 효과와 production 적합성은 구체적인 use case, 조직의 기존 시스템, 운영 evidence와 비용을 통해 별도로 판단해야 합니다.

12. 마무리

Foundry와 AIP의 Ontology는 단순히 데이터가 무엇을 의미하는지 정의하는 데서 멈추지 않습니다. 현실 세계의 Object와 관계, 이를 판단하는 Logic, 상태를 바꾸는 Action, 그리고 모든 상호작용을 제약하는 Security를 하나의 운영 계층에서 연결하려 합니다.

기업 AI의 어려움은 모델이 답을 생성하는 데만 있지 않습니다. 조직의 현실을 어떤 객체와 관계로 표현하고, 어떤 판단을 신뢰하며, 누구에게 어떤 행동을 허용할 것인지 운영 가능한 계약으로 만드는 데 있습니다.

이 관점에서 Ontology는 AI에게 더 많은 자유를 주는 장치라기보다 사람과 AI가 같은 업무 세계를 보면서도 각자의 권한과 책임 안에서 행동하게 만드는 기반으로 이해할 수 있습니다.
