AWS · Database · Reliability

[AWS/Database] RDS 엔진 업그레이드를 무중단이라고 부르기 전에 - Blue/Green, Switchover Gate, Rollback

RDS Blue/Green의 생성 방법보다 변경 적합성, 복제 상태, switchover gate, 애플리케이션 재연결과 rollback 책임을 먼저 설계합니다.

2026.09.09AWSDatabaseRDSReliability

RDS for MySQL의 major version 지원 종료가 다가오고 있습니다. 보안 패치를 계속 받으려면 엔진을 업그레이드해야 하지만, 결제 API가 사용하는 운영 데이터베이스를 in-place로 올리면 호환성 문제가 발생했을 때 원인을 분석할 staging 환경도, 빠르게 돌아갈 production 환경도 남지 않습니다.

Amazon RDS Blue/Green Deployments는 운영 환경인 blue를 복제한 green 환경에서 엔진, parameter와 storage 변경을 검증한 뒤 짧은 switchover로 production을 교체합니다. 그러나 이 기능이 자동으로 무중단과 안전한 rollback을 보장하는 것은 아닙니다. switchover 중에는 write가 중지되고 연결이 종료되며, 전환 뒤 새 production에 쌓인 write는 이전 blue로 자동 복제되지 않습니다.

이 글은 실제 production 업그레이드 결과가 아니라 RDS for MySQL 8.0에서 8.4로 이동하는 운영 설계 예시입니다. 아래 수치는 실측 성과가 아닌 초기 acceptance target입니다. production과 유사한 데이터·부하로 rehearsal을 수행하고 결과 열을 채우기 전까지 "무중단 업그레이드를 달성했다"고 주장하지 않습니다.

1. 문제를 엔진 변경이 아니라 쓰기 경로의 통제된 교체로 정의한다

DB upgrade의 위험은 새 엔진이 부팅되는지에만 있지 않습니다. SQL mode, optimizer, collation, authentication plugin, parameter와 driver 조합이 애플리케이션의 실제 query에서 함께 바뀝니다. 변경 후 처음 드러나는 느린 query나 재연결 폭증도 사용자 장애가 됩니다.

flowchart LR change[Engine and parameter change] --> compatibility[SQL and driver compatibility] change --> replication[Replication health] change --> reconnect[Connection recovery] change --> recovery[Rollback and recovery window] compatibility --> decision{Release decision} replication --> decision reconnect --> decision recovery --> decision

따라서 완료 조건을 "green이 available 상태가 됨"으로 두지 않습니다. 대표 query의 결과와 실행 계획, peak write를 따라가는 복제 성능, switchover 동안의 오류 예산, 전환 뒤 PITR와 rollback 경로를 모두 변경 계약에 포함합니다.

2. Blue/Green은 무중단이 아니라 downtime을 제한하는 도구다

RDS는 switchover 전에 guardrail을 확인하고, blue와 green의 새 write를 중지한 뒤 양쪽 DB 연결을 종료합니다. 복제가 따라잡으면 resource 이름과 endpoint를 교체하고 green을 새 production으로 엽니다. 애플리케이션 관점에서는 기존 connection이 끊어지고 새 connection을 만들어야 하는 짧은 장애 구간입니다.

sequenceDiagram participant A as Application participant B as Blue production participant G as Green staging participant R as Amazon RDS A->>B: Normal reads and writes B-->>G: Continuous replication R->>R: Run switchover guardrails R->>B: Stop new writes R->>G: Stop new writes R--xA: Drop database connections B-->>G: Apply remaining changes R->>R: Rename resources and endpoints A->>G: Reconnect to original endpoint G-->>A: Resume reads and writes

그러므로 사용자 SLO는 RDS 작업 완료 시간이 아니라 API의 error와 recovery로 정의합니다. 예를 들어 "switchover 명령 후 60초 안에 write API가 정상화되고, 중복 결제가 없으며, p99 latency가 5분 안에 baseline으로 회복"하는지를 측정합니다.

이 사례는 같은 Region·계정의 RDS for MySQL이고 cross-Region read replica와 cascading replica가 없으며, application이 짧은 재연결을 허용합니다. 이 조건에서는 RDS Blue/Green을 선택합니다. 반대로 unsupported topology이거나 PostgreSQL logical replication 제약을 수용할 수 없다면 기능을 억지로 맞추지 않고 DMS 또는 별도 migration 절차를 검토합니다.

4. 생성 전에 지원 여부보다 변경 적합성을 먼저 검사한다

현재 RDS Blue/Green은 RDS for MySQL, MariaDB와 PostgreSQL의 지원 버전에서 사용할 수 있지만, 모든 RDS topology와 통합을 지원하지는 않습니다. 특히 다음 항목은 실행 전에 inventory에서 차단합니다.

  • cross-Region 또는 cascading read replica가 연결되어 있는가
  • Multi-AZ DB cluster deployment인가, 지원되는 Multi-AZ DB instance인가
  • Secrets Manager가 master user password를 직접 관리하는 구성인가
  • Redshift zero-ETL integration 또는 external replication이 연결되어 있는가
  • custom option group과 major version upgrade 조합이 제약에 걸리는가
  • RDS Proxy를 사용한다면 blue DB가 Proxy에 미리 등록되어 있는가
  • IaC pipeline이 Blue/Green resource 자체를 CloudFormation으로 만들려고 하는가

Blue/Green Deployments 자체는 현재 CloudFormation 지원 대상이 아니므로, 여기서는 승인된 CLI workflow로 lifecycle을 제어하고 deployment ID와 상태를 변경 기록에 남깁니다. DB instance, parameter group, alarm 같은 주변 resource는 기존 IaC 소유권을 유지합니다.

5. MySQL과 PostgreSQL의 복제 제약을 같은 규칙으로 다루지 않는다

Engine과 방식주요 관찰값변경 제약
MySQL / MariaDB binlog replicationReplicaLag, transaction과 DDL복제 호환 schema만 변경하고 non-transactional engine 회피
PostgreSQL physical replicationWAL replay와 replica 상태green이 strict read-only이며 schema 변경 불가
PostgreSQL logical replicationOldestReplicationSlotLag, slot disk usageDDL·DCL, large object, unlogged table과 sequence 처리 제약

PostgreSQL logical replication에서 blue에 DDL을 실행하면 green에 자동 반영되지 않고 replication이 degraded 상태가 될 수 있습니다. 이 기간의 migration freeze는 권고 문구가 아니라 배포 정책이어야 합니다. 반대로 MySQL이라고 모든 schema 변경이 안전한 것도 아닙니다. rename이나 replication과 호환되지 않는 DDL은 별도 expand-contract release로 분리합니다.

6. 처음 실패하기 쉬운 접근은 DB 변경을 한 번에 묶는 것이다

처음에는 엔진, instance class, storage, parameter와 schema를 green에서 한꺼번에 바꾸면 maintenance를 한 번만 하면 된다고 생각할 수 있습니다. 하지만 문제가 생겼을 때 optimizer 변화인지, parameter인지, storage latency인지 분리하기 어렵습니다. 결과가 좋아져도 어느 변경이 효과를 냈는지 설명할 수 없습니다.

두 번째 실패는 snapshot 기반 test만 통과하고 production cutover를 승인하는 것입니다. snapshot은 query compatibility를 볼 수 있지만 production의 지속적인 write를 green이 따라갈 수 있는지와 switchover connection storm을 검증하지 못합니다.

세 번째 실패는 green endpoint에 test write를 허용하는 것입니다. green의 독립 write는 replication conflict와 의도하지 않은 production data를 만들 수 있습니다. 기능 검증이 write를 요구한다면 production replication 대상과 분리된 disposable snapshot 환경에서 먼저 수행하고, Blue/Green green에서는 read-only smoke test와 통제된 변경만 실행합니다.

major version과 parameter group은 같은 green에 적용할 수 있지만 검증 결과는 변경 축별로 남깁니다. 먼저 production query compatibility를 확인하고, 다음으로 실행 계획과 resource 사용량을 비교하며, 마지막으로 동일한 application version으로 switchover rehearsal을 수행합니다.

8. 생성 명령과 변경 증거를 같은 release record에 남긴다

SOURCE_ARN="arn:aws:rds:ap-northeast-2:123456789012:db:orders-prod"

aws rds create-blue-green-deployment \
  --blue-green-deployment-name orders-mysql84-20260909 \
  --source "$SOURCE_ARN" \
  --target-engine-version 8.4 \
  --target-db-parameter-group-name orders-mysql84-v1 \
  --tags \
      Key=Service,Value=orders \
      Key=ChangeId,Value=CHG-2026-0909 \
      Key=Owner,Value=database-platform

aws rds describe-blue-green-deployments \
  --filters Name=blue-green-deployment-name,Values=orders-mysql84-20260909 \
  --query 'BlueGreenDeployments[0].{
    Id:BlueGreenDeploymentIdentifier,
    Status:Status,
    Source:Source,
    Target:Target,
    Tasks:Tasks
  }'

release record에는 CLI parameter뿐 아니라 blue의 engine version, parameter·option group, instance class, storage, topology와 immutable resource ID를 저장합니다. switchover에서 DB identifier가 바뀌어도 resource ID는 바뀌지 않으므로, CloudWatch alarm이나 외부 inventory가 identifier만 추적하는지 resource ID를 추적하는지도 확인합니다.

9. Green 검증은 연결 성공이 아니라 결과와 실행 계획을 비교한다

production credential을 그대로 배포해 green을 테스트하지 않습니다. test runner 전용 security group과 최소 권한 DB user를 만들고, green endpoint는 release job의 protected environment에서만 주입합니다. test 결과에는 query suite version과 데이터 기준 시각을 함께 남깁니다.

-- MySQL 예시: 대표 query의 결과와 plan을 blue/green에서 각각 수집
SELECT COUNT(*) AS active_orders
FROM orders
WHERE status IN ('PAID', 'FULFILLING')
  AND created_at >= UTC_TIMESTAMP() - INTERVAL 24 HOUR;

EXPLAIN ANALYZE
SELECT order_id, customer_id, total_amount
FROM orders
WHERE customer_id = 4821
ORDER BY created_at DESC
LIMIT 20;

replica인 green에서 읽은 값은 측정 순간의 blue와 완전히 같지 않을 수 있습니다. 단순 row count 비교는 replica lag에 영향을 받으므로, 비교 시각의 replication position과 업무 invariant를 함께 사용합니다.

10. Replica lag는 숫자 하나가 아니라 write budget의 결과다

MySQL과 MariaDB에서는 green의 ReplicaLag를 확인합니다. 평균이 낮아도 batch, DDL 또는 긴 transaction 중에 tail lag가 커지면 switchover가 허용된 timeout 안에 끝나지 않을 수 있습니다. blue의 DatabaseConnections, ActiveTransactions, DB load와 storage throughput도 같은 시간축에서 봅니다.

flowchart TD writes[Blue write workload] --> binlog[Replication log] binlog --> apply[Green apply capacity] apply --> lag{Lag within gate?} lag -->|yes| ready[Continue validation] lag -->|no| classify{Cause} classify --> tx[Long transaction] classify --> ddl[DDL or bulk job] classify --> capacity[CPU memory or storage] tx --> reschedule[Drain or reschedule workload] ddl --> reschedule capacity --> tune[Scale or tune green]

lag를 줄이기 위해 durability parameter를 임시로 완화하는 방식은 자동 처방으로 두지 않습니다. 예를 들어 green의 innodb_flush_log_at_trx_commit을 임시 변경했다면, switchover 전에 production 값으로 복구하고 재부팅·crash 위험을 포함한 검증을 다시 통과해야 합니다.

11. Switchover gate는 사람이 읽는 checklist와 기계 판정을 함께 둔다

# rds-blue-green-gate.yml - 특정 CI 제품에 종속되지 않은 운영 계약 예시
change_id: CHG-2026-0909
target: orders-mysql84-20260909
require:
  deployment_status: AVAILABLE
  replication_status: HEALTHY
  replica_lag_seconds_p99_15m: "<= 1"
  long_running_write_over_seconds: 0
  active_ddl: 0
  green_test_writes: 0
  query_result_suite: pass
  query_plan_regressions: 0
  application_reconnect_rehearsal: pass
  backup_and_pitr_check: pass
  all_critical_alarms: OK
budget:
  switchover_timeout_seconds: 120
  write_unavailable_seconds: "<= 60"
  api_error_rate_5m: "<= 0.1%"
  recovery_to_baseline_minutes: "<= 5"
approval:
  application_owner: required
  database_owner: required
  incident_commander: assigned
  rollback_decision_deadline_minutes: 30

ReplicaLag <= 1은 이 workload를 위한 초기 target이지 AWS의 보장값이 아닙니다. rehearsal에서 1초의 lag가 실제 몇 초의 write 중지로 이어지는지 측정해 조정합니다. RDS 자체 guardrail을 통과했다는 사실도 application query와 재연결이 안전하다는 증거를 대신하지 않습니다.

12. 배포 직전에는 장기 transaction과 자동 작업을 비운다

maintenance 시작 전에 batch writer, schema migration, scheduled event와 긴 report query를 중지합니다. 새 주문을 완전히 막기 어렵다면 write rate를 낮추고 idempotency key가 있는 요청만 제한 재시도를 허용합니다.

-- MySQL: 장기 실행 작업을 찾기 위한 예시
SELECT
  trx_mysql_thread_id AS thread_id,
  trx_started,
  TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_seconds,
  trx_rows_modified,
  trx_query
FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 30
ORDER BY age_seconds DESC;

검색 결과가 있다는 이유만으로 session을 자동 종료하지 않습니다. payment capture나 inventory deduction처럼 중간 종료 비용이 큰 transaction은 application owner가 의미를 확인해야 합니다. kill 기준과 업무 영향은 runbook에 미리 정합니다.

13. Switchover timeout은 기다릴 수 있는 시간이 아니라 허용 가능한 장애 예산이다

RDS의 switchover timeout은 30초부터 3,600초까지 지정할 수 있고 기본값은 300초입니다. timeout을 크게 잡으면 성공 가능성이 높아지는 것처럼 보이지만, application이 기다릴 수 없는 시간까지 database 전환을 계속할 수 있습니다. 이 사례에서는 rehearsal p99와 API error budget을 근거로 120초에서 시작합니다.

BG_ID="bgd-0123456789example"

aws rds switchover-blue-green-deployment \
  --blue-green-deployment-identifier "$BG_ID" \
  --switchover-timeout 120

for attempt in {1..36}; do
  status="$(aws rds describe-blue-green-deployments \
    --blue-green-deployment-identifier "$BG_ID" \
    --query 'BlueGreenDeployments[0].Status' \
    --output text)"

  case "$status" in
    SWITCHOVER_COMPLETED) break ;;
    SWITCHOVER_FAILED|INVALID_CONFIGURATION) exit 1 ;;
  esac
  sleep 5
done

test "$status" = "SWITCHOVER_COMPLETED"

실행자는 명령 직전에 deployment ID, source와 target ARN을 다시 확인합니다. 이름만 비슷한 다른 환경을 전환하지 않도록 release job은 tag와 source ARN이 change record와 일치하지 않으면 중단합니다.

14. 애플리케이션은 endpoint 유지보다 connection 종료에 대비해야 한다

switchover가 완료되면 green이 기존 production의 이름과 endpoint를 넘겨받지만, 기존 DB connection은 이미 종료됩니다. connection pool이 DNS와 socket을 오래 붙잡거나 모든 instance가 동시에 재시도하면 전환 직후 connection storm이 발생할 수 있습니다.

  • DB driver와 pool의 connection validation 및 최대 lifetime을 rehearsal에서 확인합니다.
  • 연결 실패는 exponential backoff와 jitter를 적용해 작게 제한합니다.
  • 재시도 가능한 read와 idempotency key가 있는 write를 구분합니다.
  • transaction commit 결과를 모르는 경우 같은 write를 무조건 반복하지 않습니다.
  • RDS Proxy를 사용한다면 blue를 Proxy에 먼저 등록하고 Proxy endpoint 경로도 함께 rehearsal합니다.
Request retry budget
  = min(API remaining latency budget, database recovery budget)

Retry only when
  transient connection failure
  AND operation is read-only or idempotent
  AND total attempts remain bounded

15. EventBridge와 CloudWatch를 release timeline으로 묶는다

RDS는 Blue/Green 생성 완료, 실패, switchover 시작·완료·취소 이벤트를 발행합니다. EventBridge에서 해당 이벤트를 deployment channel과 incident timeline으로 전달하되, 이벤트 수신 자체를 성공 판정으로 사용하지 않습니다. application canary와 CloudWatch metric이 함께 통과해야 release를 종료합니다.

Business결제 승인 대비 주문 생성, 중복 write기술 성공이 업무 정합성을 보장했는가

metric dimension에는 order ID나 customer ID를 넣지 않습니다. service, operation, environment와 error class처럼 제한된 값을 사용하고 개별 거래 조사는 접근 통제된 trace와 audit log에서 수행합니다.

16. Rollback을 application, infrastructure, data 세 종류로 나눈다

Blue/Green switchover가 끝나면 replication은 끊어집니다. 이전 blue가 남아 있어도 새 production에 들어온 write가 자동으로 돌아가지 않으므로, "문제가 생기면 old blue로 되돌린다"는 한 줄은 rollback plan이 아닙니다.

flowchart TD incident[Post-switchover regression] --> classify{Failure scope} classify -->|Application only| app[Roll back application version
keep new database] classify -->|Parameter or capacity| infra[Forward-fix green configuration] classify -->|Data corruption or incompatibility| data{New writes accepted?} data -->|no| redirect[Controlled return to retained blue] data -->|yes| reconcile[Stop writes
capture delta
reconcile or reverse replicate] reconcile --> decision[Explicit recovery decision]
  • Application rollback: 이전 application version이 새 DB engine과 호환되면 DB는 유지하고 code만 되돌립니다.
  • Infrastructure forward fix: parameter나 instance capacity 문제는 새 production에서 수정하는 편이 데이터 이동보다 안전할 수 있습니다.
  • Data rollback: 전환 후 write가 발생했다면 write freeze, delta capture, reconciliation과 검증이 필요합니다.

old blue는 즉시 삭제하지 않습니다. 하지만 보관 기간이 길수록 이중 비용과 보안 패치 책임이 늘어납니다. 데이터 복구 요구와 새 production 관찰 기간을 기준으로 명시적인 삭제 시각과 승인자를 정합니다.

17. PITR window가 전환과 함께 이어진다고 가정하지 않는다

green은 기존 blue와 다른 resource ID를 유지합니다. switchover 뒤 새 production의 PITR history는 green 생성 시점부터 시작하며, 이전 blue의 전체 복구 기록이 새 production으로 합쳐지지 않습니다. 장기 RPO 요구가 있다면 이 차이가 deployment 승인 조건이 됩니다.

timeline title Recovery history around switchover Blue created : Blue PITR history grows Green created : Green PITR history starts separately Switchover : Green becomes production : Blue history stays with old resource ID Retention window : Keep old blue for required recovery points Approved deletion : Delete old blue after recovery obligation ends

전환 직전 manual snapshot 하나만으로 모든 복구 요구를 충족한다고 가정하지 않습니다. restore time, retained old blue 비용, backup retention과 "어느 시각으로 어느 resource를 복구할지"를 restore drill에서 확인합니다.

18. 비용 budget은 green 생성부터 old blue 삭제까지 계산한다

Blue/Green 기능의 별도 고정 요금보다 중요한 것은 green이 blue와 같은 topology를 복제해 compute, storage, I/O와 backup 비용을 만든다는 점입니다. AWS FAQ는 deployment가 유지되는 동안 DB instance workload 비용이 대략 두 배가 될 수 있다고 설명합니다.

Change cost
  = green compute and storage during validation
  + green I/O and backup
  + test traffic and observability
  + retained old-blue compute and storage after switchover
  + engineer and maintenance-window cost

Cost guardrail
  green lifetime <= 72 hours
  intensive observation = 30 minutes
  old-blue retention = approved recovery window
  delete only after backup and rollback sign-off

green을 일찍 만들고 승인 회의를 기다리는 시간이 길수록 비용과 replication exposure가 함께 늘어납니다. 변경 준비가 끝난 뒤 생성하고, 실패한 validation은 고장 난 green을 오래 유지하기보다 원인을 수정한 뒤 재생성하는 정책을 둡니다.

21. 아직 production-grade라고 주장하지 않는 범위

  • 이 글의 latency, lag, error와 비용 수치는 실제 production 측정 결과가 아닙니다.
  • RDS for MySQL 8.0에서 8.4로 이동하는 예시이며 실제 minor version과 Region 지원 여부를 고정하지 않았습니다.
  • 결제사 호출과 DB commit 사이에서 결과를 알 수 없는 transaction의 reconciliation을 구현하지 않았습니다.
  • cross-Region read replica, zero-ETL, 외부 CDC와 analytics consumer 재연결을 검증하지 않았습니다.
  • connection 수가 매우 많은 환경의 재연결 폭증과 RDS Proxy 조합을 대규모로 부하 테스트하지 않았습니다.
  • 전환 후 reverse replication 또는 DMS 기반 data rollback pipeline을 구축하지 않았습니다.
  • 실제 restore drill과 old blue 삭제 승인까지 수행하지 않았습니다.

이 상태에서 말할 수 있는 것은 "Blue/Green을 사용하는 release contract를 설계했다"까지입니다. production-grade라는 주장은 rehearsal 결과, 실패한 전환의 원인과 개선, 실제 복구 증거가 채워진 뒤에만 가능합니다.

22. 마무리

RDS Blue/Green Deployments의 가치는 DB 복사본을 하나 더 만드는 데 있지 않습니다. production과 변경 환경을 분리하고, 복제 상태와 application 검증을 거쳐, write 중지와 connection 종료가 포함된 cutover를 제한된 오류 예산 안에서 실행하는 데 있습니다.

안전한 database deployment는 switchover 버튼이 아니라 변경 적합성, 기계적인 승인 기준, 재연결 설계와 데이터 rollback의 한계를 함께 소유하는 운영 계약입니다.
