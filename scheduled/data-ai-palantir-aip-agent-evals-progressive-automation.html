[Data/AI] AI Agent에게 실제 업무 권한을 어디까지 줄 것인가? - Palantir AIP Evals와 Progressive Automation

좋은 답변을 만드는 것과 기업 시스템에서 안전하게 행동하는 것은 다른 문제입니다. Agent의 tool 사용과 Action 권한을 평가하고, 증거가 쌓인 범위에서만 자동화를 확대하는 운영 계약을 살펴봅니다.

2026.09.26AI AgentAIP EvalsAutomationGovernance

앞선 글에서는 Palantir Foundry와 AIP가 기업의 Data, Logic, Action과 Security를 Ontology로 연결하는 방식을 살펴봤습니다. 이번 글에서는 Ontology 자체를 다시 설명하기보다 그 위에서 AI Agent가 실제 업무에 참여할 때 생기는 운영 문제에 집중합니다.

질문은 "Agent가 답을 잘하는가?"에서 끝나지 않습니다. 어떤 Logic을 선택했는지, 올바른 parameter로 tool을 호출했는지, 허용되지 않은 Action을 거부했는지, 실행 결과가 실제 업무 목표를 만족했는지까지 확인해야 합니다. 권한이 커질수록 평가 대상도 response quality에서 system behavior로 확장됩니다.

이 글은 Palantir 공식 문서를 바탕으로 AIP Evals, Ontology SDK와 Branching을 운영 관점에서 해석한 설계 글입니다. 실제 Foundry tenant에서 Agent를 배포해 성능이나 비용을 측정한 결과가 아니며, Progressive Automation은 AIP Evals가 권한을 자동 승격하는 기능이 아니라 평가와 runtime evidence를 근거로 조직이 자율성 범위를 결정하는 운영 모델로 사용합니다.

1. Agent의 목적은 대화가 아니라 Workflow의 일부가 되는 것이다

재고 부족을 발견하는 dashboard와 재고 이동을 생성하는 ERP가 분리되어 있다면 담당자는 분석 결과를 다시 해석하고 다른 시스템에서 같은 context를 복원해야 합니다. Agent를 추가하는 목적은 이 과정을 자연어 화면 하나로 가리는 것이 아니라, 판단과 실행 사이의 반복 가능한 업무 계약을 만드는 데 있습니다.

flowchart TB signal[Operational signal] --> context[Business context] context --> decision[Decision workflow] decision --> proposal[Proposed action] proposal --> approval{Policy and approval} approval -->|Allowed| execute[Controlled execution] approval -->|Denied| review[Human review] execute --> outcome[Business outcome] outcome --> evidence[Evaluation evidence]

Workflow의 각 단계는 서로 다른 주체가 맡을 수 있습니다. 규칙 엔진이 위험도를 계산하고, LLM이 비정형 보고서에서 context를 추출하며, 사람이 고위험 결정을 승인하고, Action이 외부 시스템에 write-back할 수 있습니다. Agent는 모든 단계를 대체하기보다 이들을 조율하는 역할을 맡습니다.

2. LLM이 잘하는 일과 검증된 계산을 분리한다

공장 정비 보고서에 최근 세 교대 동안 모터 진동이 커졌다는 문장이 들어왔다고 가정하겠습니다. LLM은 보고서에서 장비, 증상과 시간 범위를 추출하는 데 유용합니다. 하지만 고장 확률을 생성된 숫자로 대신할 이유는 없습니다. 이미 검증된 failure prediction model이 있다면 그 모델을 호출하고, maintenance rule과 optimizer를 함께 사용해야 합니다.

flowchart TB report[Maintenance report] --> llm[LLM context extraction] llm --> model[Failure prediction model] telemetry[Sensor telemetry] --> model model --> rule[Maintenance policy] rule --> optimizer[Schedule optimizer] optimizer --> proposal[Maintenance proposal]
구성 요소맡길 일검증할 계약
LLM비정형 context 추출, 설명과 대안 구성근거 연결, schema, 누락과 환각
Business rule금지 조건, threshold와 승인 정책결정성, 우선순위와 예외
ML model예측 score와 분류입력 분포, calibration과 version
Optimizer자원·일정 제약 아래 해 탐색constraint, infeasible 처리와 timeout
ActionOntology 또는 외부 system 변경권한, idempotency, side effect와 audit

Agent 품질을 model benchmark 하나로 판단하면 안 되는 이유입니다. 올바른 답을 생성했어도 잘못된 tool을 선택하거나 stale data를 읽거나 side effect를 중복 실행하면 workflow는 실패합니다.

3. 자동화 수준은 하나의 스위치가 아니라 권한 사다리다

처음부터 Agent에 production write 권한을 주는 것은 위험합니다. 같은 use case라도 관찰, 제안, 승인 기반 실행, 제한된 자동 실행 순서로 권한을 나눌 수 있습니다.

단계Agent 역할Human 역할허용된 영향
0. Observe실행 없이 기록된 사례를 분석기존 방식으로 판단·실행Production side effect 없음
1. Assist정보 요약과 근거 제시판단과 Action 선택Read-only
2. RecommendAction과 parameter 제안검토 후 직접 실행제안만 저장
3. Approve검증된 Action 호출 준비명시적으로 승인 또는 거부승인된 요청만 실행
4. Constrained auto낮은 위험 범위를 자동 실행예외 처리와 사후 검토금액·대상·빈도 제한
5. Expanded auto더 넓은 조건에서 실행정책·SLO·incident 책임지속 monitoring과 kill switch 전제
flowchart TB observe[Observe] --> assist[Assist] assist --> recommend[Recommend] recommend --> approve[Human approval] approve --> constrained[Constrained automation] constrained --> expanded[Expanded automation] expanded -. regression .-> constrained constrained -. incident .-> approve

이 사다리는 일방통행이 아닙니다. 모델, prompt, Logic, data mapping이나 업무 정책이 바뀌면 낮은 단계로 되돌려 재검증해야 합니다. incident와 regression은 권한 축소의 trigger이고, 자동화 확대에는 명시적인 owner와 승인 기록이 필요합니다.

4. AIP Evals는 권한 승격 기능이 아니라 판단 근거를 만드는 도구다

AIP Evals는 AIP Logic, AIP Chatbot과 code-authored function을 대상으로 test case, target function과 evaluation function을 구성하고 실행 결과를 이전 version과 비교할 수 있는 환경입니다. 같은 입력을 여러 번 실행해 비결정적 결과의 variance를 확인하거나 model·parameter 조합을 비교할 수도 있습니다.

하지만 evaluation suite가 통과했다고 Agent의 production 권한이 자동으로 커지는 것은 아닙니다. Evals는 후보 구현의 behavior를 측정하는 evidence를 제공하고, 실제 권한 변경은 risk owner가 runtime monitoring과 업무 영향까지 보고 결정해야 합니다.

flowchart TB cases[Versioned test cases] --> candidate[Candidate Logic or Agent] candidate --> outputs[Outputs and tool traces] outputs --> evaluators[Deterministic and model evaluators] evaluators --> report[Quality, variance, cost report] report --> gate{Release gate} gate -->|Pass| shadow[Shadow or approval mode] gate -->|Fail| revise[Revise Logic, prompt or tools] shadow --> runtime[Runtime evidence] runtime --> autonomy{Autonomy review}

5. Response가 아니라 의사결정 경로를 평가한다

Agent가 실제 Action에 가까워질수록 정답 문자열만 비교하는 평가는 부족합니다. 평가 대상을 여러 계층으로 나눠야 실패 위치를 설명할 수 있습니다.

평가 계층질문예시 metric
Context필요한 object와 최신 상태를 찾았는가?required context recall, stale input rate
Reasoning output판단과 설명이 기대 조건을 만족하는가?correctness, completeness, source support
Tool selection허용된 Logic과 tool을 올바른 순서로 골랐는가?tool precision, forbidden tool calls
Parameter대상, 수량과 조건이 정확한가?exact match, range violation, schema failure
Policy금지·승인 조건을 우회하지 않았는가?unsafe action attempts, approval bypass
Execution중복 없이 의도한 side effect를 만들었는가?idempotency violations, execution failure
Outcome실제 업무 결과가 개선됐는가?decision time, override rate, error cost
Operations예산 안에서 안정적으로 동작하는가?p95 latency, token·tool cost, timeout rate

LLM-as-a-judge는 의미 기반 평가에 유용하지만 유일한 gate로 두지 않습니다. 금액 한도, tool allowlist, parameter schema, permission과 idempotency는 deterministic evaluator로 검사하고, 애매한 품질 기준에는 model evaluator와 human review를 조합합니다.

6. Dev set 개선만으로 자동화 단계를 높이지 않는다

Prompt와 test case를 같은 사람이 반복해서 조정하면 평가셋에 맞춘 개선이 생길 수 있습니다. Agent 변경도 retrieval이나 ML model과 마찬가지로 개발용 사례와 untouched validation을 분리해야 합니다.

# agent-release-gate.yml - 도구 독립적인 운영 계약 예시
inventory_transfer_agent:
  candidate_version: aip-logic-17
  evaluation:
    held_out_cases: 180
    required_context_recall: ">= 0.98"
    tool_selection_accuracy: ">= 0.99"
    parameter_exact_match: ">= 0.99"
    forbidden_action_attempts: 0
    approval_bypass_attempts: 0
    p95_latency_seconds: "<= 8"
    mean_cost_per_case_usd: "<= 0.12"
  rollout:
    initial_mode: recommendation_only
    shadow_days: 14
    minimum_reviewed_decisions: 500
    max_human_override_rate: "<= 0.03"
  block_on:
    - ontology_contract_changed
    - tool_schema_changed
    - held_out_regression
    - evaluator_version_missing
    - production_kill_switch_missing

숫자는 실제 측정 결과가 아니라 acceptance contract의 예시입니다. 중요한 것은 baseline과 candidate가 동일한 held-out case, evaluator version과 반복 횟수에서 비교되고, aggregate score가 좋아도 safety-critical case 하나가 실패하면 release를 막는 것입니다.

7. Offline Evals와 Runtime Monitoring은 서로 대체하지 않는다

평가셋은 알려진 위험을 반복 검증하지만 production의 모든 context를 담을 수 없습니다. 실제 사용자, 권한, dependency와 데이터 분포가 들어오면 새로운 failure mode가 나타납니다.

관찰분류대응
필수 object를 찾지 못함Context failureAction 금지, fallback과 data owner 알림
금지 tool 호출을 시도Policy failure호출 차단, security event와 사례 보존
동일 요청이 재실행됨Execution failureidempotency key 확인, 중복 side effect 조정
사람이 제안을 반복 수정Decision quality driftoverride 이유 수집, autonomy 단계 하향
외부 system timeoutDependency failurebounded retry, 상태 조회와 503·504 구분
비용 또는 latency 급증Operational regressionbudget 차단, model·tool 경로 분석

metric에는 Agent version, workflow, tool과 outcome class 정도만 넣고 customer ID, order ID나 원문 prompt 같은 high-cardinality·민감 정보를 label로 사용하지 않습니다. 개별 의사결정의 context와 trace는 접근 통제된 audit store에 보관하고 metric과 연결합니다.

8. OSDK는 Ontology를 제품의 typed backend로 사용하게 한다

Ontology SDK(OSDK)는 TypeScript, Python과 Java에서 선택한 Ontology의 type을 생성하고 object 조회, Action 적용, function과 AIP Logic 호출을 지원합니다. 따라서 사용자가 반드시 Foundry UI 안에서만 workflow를 수행할 필요는 없습니다.

flowchart LR web[Web or mobile product] --> osdk[Generated OSDK client] service[Backend service] --> osdk osdk --> auth[OAuth and scoped permissions] auth --> ontology[Ontology objects and links] auth --> functions[Functions and AIP Logic] auth --> actions[Governed actions]

이 접근은 "SDK of the business"라는 표현처럼 Warehouse, Shipment, Order와 TransferInventory를 application interface로 노출합니다. 동시에 SDK가 permission, retry, transaction과 업무 invariant를 대신 설계해주는 것은 아닙니다. Client credential 범위, Action idempotency, API version과 실패 계약은 application owner의 책임으로 남습니다.

9. Runtime 권한과 시스템 변경 권한을 분리한다

Agent가 production object를 읽고 Action을 실행하는 권한과, Ontology·Logic·application 정의 자체를 변경하는 권한은 다른 통제입니다. 전자는 runtime policy가, 후자는 branch와 review workflow가 담당해야 합니다.

flowchart TB runtime[Runtime control
What can execute now] change[Change control
What can enter production] runtime --> identity[Identity, object and action permission] runtime --> limits[Parameter, volume and approval limits] change --> branch[Isolated branch] branch --> evals[Evals and tests] evals --> review[Proposal review] review --> main[Merge to main]

Foundry의 Ontology는 Global Branching에서 변경, conflict resolution, proposal review와 merge를 지원합니다. 다만 모든 resource와 interface가 같은 수준으로 branch-aware한 것은 아닙니다. 공식 문서 기준 pro-code Agent의 Global Branching 연동은 Beta이고 OSDK type과 일부 API에는 제한이 있으므로, "Agent가 만든 모든 변경이 안전한 branch 안에서 완전히 격리된다"고 일반화하면 안 됩니다.

10. 권한 확대 결정에는 명시적인 owner가 필요하다

결정Primary owner필요한 evidence
Business outcome 정의Domain owner현재 decision time, 오류 비용과 목표
Logic·model 변경AI/ML ownerheld-out eval, variance, latency와 cost
Tool·Action 계약Service ownerschema, idempotency, timeout과 rollback
권한·승인 정책Security와 risk ownerabuse case, least privilege와 audit test

Incident와 권한 축소On-call ownerkill switch, fallback과 recovery runbook

추천 모드에서 정확도가 높았다는 이유만으로 자동 실행으로 넘어가지 않습니다. 승인 모드에서 실제 사용자의 거부·수정 이유를 수집하고, 제한된 tenant나 금액 범위에서 canary를 수행한 뒤, 오류 예산과 업무 outcome이 함께 통과할 때만 범위를 확대합니다.

11. 이 글에서 검증하지 않은 것

  • AIP Logic, AIP Evals와 OSDK를 실제 tenant에서 구성하거나 실행하지 않았습니다.
  • 앞선 evaluation threshold와 rollout 기간은 실측값이 아니라 설계 예시입니다.
  • 실제 ERP 또는 production system에 대한 write-back과 compensation을 구현하지 않았습니다.
  • model evaluator의 bias, 재현성과 evaluator 자체의 regression을 측정하지 않았습니다.
  • Global Branching에서 pro-code Agent, OSDK와 Platform API의 제한을 재현하지 않았습니다.
  • 조직이 자동화 단계와 ownership 모델을 실제로 채택하고 유지할 수 있는지 검증하지 않았습니다.

따라서 이 글은 Palantir 제품의 실제 도입 성과가 아니라 Agent의 업무 권한을 평가하고 확대하기 위한 운영 설계입니다. Production 적합성을 주장하려면 고정된 evaluation suite, shadow traffic, 실제 human override, incident drill과 업무 outcome이 release evidence로 남아야 합니다.

12. 마무리

Enterprise Agent의 핵심 문제는 LLM에게 무엇을 물어볼지가 아니라 어떤 context와 Logic을 제공하고, 어떤 Action을 어느 범위까지 허용하며, 더 많은 권한을 줘도 된다는 것을 어떻게 증명할지에 있습니다.

Progressive Automation은 AI를 믿는 속도가 아니라, 평가와 운영 증거가 허용하는 범위까지만 권한을 이동시키는 변화 관리입니다.

AIP Evals는 후보 Logic의 품질과 variance를 비교하는 중요한 도구지만, 실제 자율성은 offline evaluation만으로 결정되지 않습니다. Human override, policy violation, dependency failure, 비용과 business outcome을 함께 관찰하고 언제든 낮은 권한 단계로 돌아갈 수 있어야 합니다.
