AWS · Messaging · Reliability

[AWS/Messaging] 주문 처리 Lambda가 재시도될 때 결제가 두 번 되지 않게 하려면? - SQS Idempotency, Partial Batch, DLQ

SQS를 붙이는 구성에서 더 나아가 주문의 멱등성 경계, 부분 실패, visibility budget, DLQ 분석과 안전한 redrive를 운영 계약으로 만듭니다.

2026.09.19AWSSQSLambdaReliability

주문 API가 주문을 저장한 뒤 SQS에 OrderCreated 메시지를 보내고, Lambda가 결제 승인과 재고 차감을 수행한다고 가정해보겠습니다. 어느 날 결제는 두 번 승인됐는데 주문 상태는 한 번만 변경됐습니다. Lambda 로그에는 같은 주문이 몇 분 간격으로 두 번 처리된 기록이 남았습니다.

이것은 SQS의 오류라기보다 비동기 시스템의 기본 실패 모델을 애플리케이션이 흡수하지 못한 결과입니다. Standard queue는 at-least-once delivery를 제공하므로 메시지가 중복 전달될 수 있습니다. Lambda가 side effect를 완료하고 응답하기 전에 종료되거나 visibility timeout이 지나도 같은 메시지가 다시 처리될 수 있습니다.

이 글은 실제 production incident 회고가 아니라 주문 처리 pipeline의 설계와 검증 계획입니다. 아래 수치는 실측 결과가 아닌 초기 acceptance target입니다. 중복 주입과 장애 실험 결과를 기록하기 전까지 exactly-once business processing을 달성했다고 주장하지 않습니다.

1. 성공을 메시지 삭제가 아니라 업무 효과의 단 한 번 적용으로 정의한다

SQS message가 한 번만 보였는지보다 중요한 것은 같은 주문 명령이 여러 번 도착해도 결제, 재고와 주문 상태가 한 번만 바뀌는가입니다. 전송, 전달과 업무 처리는 서로 다른 보장입니다.

2. 중복은 네 개의 실패 창에서 발생한다

sequenceDiagram participant P as Producer participant Q as Amazon SQS participant L as Lambda consumer participant D as Payment or database P->>Q: Send OrderCreated Q-->>P: ACK can be lost P->>Q: Producer retries Q->>L: Deliver batch L->>D: Apply side effect D-->>L: Success L--xQ: Lambda ends before successful batch response Q->>L: Deliver message again after visibility timeout
  1. producer가 성공 응답을 받지 못해 같은 event를 다시 보냅니다.
  2. SQS의 분산 저장 과정에서 Standard queue message가 중복 전달될 수 있습니다.
  3. consumer 처리 시간이 visibility timeout을 넘으면 다른 invocation이 같은 message를 받습니다.
  4. side effect는 성공했지만 Lambda가 성공 응답을 반환하기 전에 종료됩니다.

visibility timeout을 길게 잡는 것만으로 네 번째 실패 창을 없앨 수 없습니다. 결제는 성공했고 process가 죽었다면 timeout 길이와 상관없이 재전달됩니다. 그래서 consumer idempotency가 기본 계약이어야 합니다.

3. Standard와 FIFO는 멱등성의 대체 관계가 아니다

선택지장점남는 책임선택 조건
Standard queue높은 처리량, 단순한 scale-out중복과 순서 역전 허용, consumer 멱등성 필수주문별 작업이 독립적이고 높은 처리량 우선
FIFO queuemessage group 안의 순서와 5분 deduplication windowconsumer 재실행과 외부 side effect 멱등성은 여전히 필요같은 주문의 상태 전이가 반드시 순차적
Step Functions여러 단계 상태와 보상 흐름을 명시각 Task의 idempotency와 외부 API 오류 처리장기 실행과 단계별 보상이 핵심
동기 처리흐름이 단순하고 즉시 결과 반환dependency latency와 장애가 API에 직접 전파짧고 강한 일관성이 필요한 소규모 경로

이 사례는 주문마다 독립적인 결제 준비 명령을 높은 처리량으로 처리하므로 Standard queue를 선택합니다. 주문 상태의 순서가 중요한 별도 pipeline은 FIFO를 사용하고 MessageGroupId=orderId로 직렬화할 수 있습니다. 그러나 FIFO의 producer deduplication window가 지났거나 consumer가 재실행되는 경우까지 business side effect가 자동으로 한 번만 실행되는 것은 아니므로 idempotency record는 유지합니다.

4. 주문 저장과 메시지 전송 사이에는 transactional outbox가 필요하다

주문 row를 commit한 뒤 SendMessage를 호출하면 두 시스템에 대한 dual write가 됩니다. DB commit 후 process가 죽으면 주문은 있지만 event가 없고, SQS 전송 후 DB rollback이 발생하면 존재하지 않는 주문을 처리할 수 있습니다.

flowchart LR api[Order API] --> tx[Single DB transaction] tx --> order[(orders)] tx --> outbox[(order_outbox)] outbox --> relay[Outbox relay] relay --> queue[SQS order-events] queue --> worker[Order worker Lambda] 
START TRANSACTION;

INSERT INTO orders (
  order_id, customer_id, amount, status, request_key
) VALUES (
  :order_id, :customer_id, :amount, 'PENDING', :request_key
);

INSERT INTO order_outbox (
  event_id, aggregate_id, event_type, payload, created_at
) VALUES (

);

COMMIT;

relay는 unpublished outbox를 SQS에 보내고 성공 상태를 기록합니다. relay 자체도 같은 event를 두 번 보낼 수 있으므로 event_id가 consumer의 안정적인 중복 식별자가 됩니다. outbox는 duplicate를 제거하지 않고 event 유실과 잘못된 선행 전송을 방지합니다.

5. MessageId 대신 업무 idempotency key를 계약에 넣는다

{

  "orderId": "ord-20260919-004821",

  "amount": 42000,

  "traceId": "1-68ce..."
}
  • eventId는 발행 event 인스턴스를 식별합니다.
  • idempotencyKey는 같은 업무 효과를 식별하며 operation과 version을 포함합니다.
  • aggregateVersion은 오래된 상태 전이를 거부하거나 순서를 확인할 때 사용합니다.
  • 같은 key인데 amount나 currency가 다르면 duplicate가 아니라 contract violation입니다.
  • 카드번호, 주소처럼 처리를 위해 필요하지 않은 개인정보는 message에 넣지 않습니다.

SQS redrive는 message에 새 messageId와 enqueue time을 부여할 수 있습니다. 따라서 transport ID를 업무 idempotency key로 사용하면 replay에서 보호가 사라집니다.

6. 멱등성 저장소는 INPROGRESS와 COMPLETED를 구분한다

DynamoDB에 idempotency record를 저장하면 동시 invocation 중 하나만 lock을 획득하게 할 수 있습니다. 단순히 처리 후 processed=true를 기록하면 두 invocation이 동시에 side effect를 시작하는 race를 막지 못합니다.

stateDiagram-v2 [*] --> INPROGRESS: conditional create INPROGRESS --> COMPLETED: side effect and result saved INPROGRESS --> EXPIRED: execution lease expires EXPIRED --> INPROGRESS: bounded retry acquires new lease COMPLETED --> COMPLETED: duplicate returns stored result

record에는 key, payload hash, 상태, owner token, in-progress expiry, result reference와 retention expiry를 둡니다. DynamoDB TTL은 즉시 삭제 보장이 아니므로 중복 판단은 expiry timestamp를 애플리케이션이 직접 확인합니다. lock expiry는 Lambda timeout보다 조금 길게 두되, 지나치게 길어 정상 retry가 오래 막히지 않도록 장애 실험으로 정합니다.

7. Powertools는 저장소 boilerplate를 줄이지만 업무 경계를 대신 정하지 않는다

import os

from aws_lambda_powertools.utilities.idempotency import (
    DynamoDBPersistenceLayer,
    IdempotencyConfig,
    idempotent_function,
)

persistence = DynamoDBPersistenceLayer(
    table_name=os.environ["IDEMPOTENCY_TABLE"],
)
config = IdempotencyConfig(
    event_key_jmespath="idempotencyKey",
    payload_validation_jmespath="[orderId, amount, currency]",
    raise_on_no_idempotency_key=True,
    expires_after_seconds=30 * 24 * 60 * 60,
)


@idempotent_function(
    data_keyword_argument="command",
    persistence_store=persistence,
    config=config,
)
def capture_payment(command: dict) -> dict:
    return payment_client.capture(
        order_id=command["orderId"],
        amount=command["amount"],
        currency=command["currency"],
        idempotency_key=command["idempotencyKey"],
    )

이 예시는 key의 동시 실행과 완료 결과 재사용을 처리하지만, 외부 결제 API가 idempotency key를 지원해야 가장 위험한 창을 닫을 수 있습니다. 결제가 성공한 직후 Lambda가 종료되면 DynamoDB에는 여전히 INPROGRESS만 남을 수 있기 때문입니다. 결제사가 동일 key에 같은 결과를 반환하지 않는다면 정확히 한 번의 결제를 일반적인 local lock만으로 증명할 수 없습니다. 이 경우 승인 조회 API, reconciliation ledger와 수동 보상 절차가 필요합니다.

보존 기간은 source queue, DLQ와 수동 redrive가 허용되는 가장 긴 기간보다 길게 잡습니다. 또한 결제와 재고 차감을 하나의 decorator 안에 묶었다고 두 side effect가 하나의 transaction이 되는 것은 아닙니다. 각 operation이 독립된 idempotency key를 갖거나, 단계와 보상 상태를 저장하는 workflow가 필요합니다.

8. Partial batch response로 성공한 주문의 재실행을 줄인다

Lambda의 SQS event source mapping은 여러 message를 한 batch로 전달합니다. 기본 동작에서는 한 message가 실패해 invocation이 오류를 반환하면 성공한 message까지 visibility timeout 후 다시 보입니다. ReportBatchItemFailures를 켜고 실패한 message ID만 반환해야 불필요한 재처리를 줄일 수 있습니다.

import json
import logging

logger = logging.getLogger()


def handler(event, context):
    failures = []

    for record in event["Records"]:
        try:
            command = json.loads(record["body"])
            validate_contract(command)
            capture_payment(command=command)
        except Exception as exc:
            logger.warning(
                "order message failed",
                extra={
                    "message_id": record["messageId"],
                    "error_class": type(exc).__name__,
                },
            )
            failures.append({"itemIdentifier": record["messageId"]})

    return {"batchItemFailures": failures}

handler 바깥으로 exception을 다시 던지면 partial response가 전달되지 않아 batch 전체가 실패합니다. 반대로 오류를 log만 남기고 failure 목록에서 빼면 SQS가 message를 삭제해 유실됩니다. FIFO queue라면 순서를 지키기 위해 첫 실패 뒤 같은 message group의 미처리 항목도 실패로 반환해야 합니다.

9. Queue와 Lambda 설정을 하나의 retry budget으로 계산한다

Lambda 공식 가이드는 source queue의 visibility timeout을 함수 timeout의 최소 6배로 두고, batching window가 있다면 그 시간도 더하도록 권장합니다. 함수 timeout이 30초이고 batch window가 1초라면 초기 visibility timeout은 최소 181초가 필요하므로 여기서는 180초가 아니라 여유를 둔 210초에서 시작합니다.

Initial visibility budget
  = Lambda timeout x 6
  + maximum batching window
  + operational margin

Example
  = 30 seconds x 6 + 1 second + 29 seconds
  = 210 seconds

maxReceiveCount는 단순히 클수록 안전하지 않습니다. 너무 작으면 짧은 dependency 장애도 DLQ로 보내고, 너무 크면 poison message가 비용과 부하를 계속 만듭니다. AWS의 Lambda-SQS 가이드는 최소 5를 권장하므로 5에서 시작하되, 결제 API의 정상 복구 시간과 DLQ 대응 SLO를 함께 측정해 결정합니다.

10. IaC에 DLQ, redrive policy와 부분 실패를 함께 고정한다

Resources:

DLQ retention은 source queue보다 길게 둡니다. Standard queue message의 만료 기준은 DLQ로 이동해도 원래 enqueue timestamp를 유지하기 때문에, 같은 retention을 쓰면 조사 시간이 예상보다 짧아질 수 있습니다. RedriveAllowPolicy는 이 source queue만 DLQ를 사용할 수 있도록 제한합니다.

SSE-KMS를 사용하면 consumer와 redrive operator에 필요한 decrypt·data key 권한을 IAM과 key policy까지 포함해 검토합니다. 운영자가 source queue의 message를 콘솔에서 반복 조회하는 동작도 receive count에 영향을 줄 수 있으므로, 조사 절차는 read-only처럼 보이는 콘솔 행동까지 포함해야 합니다.

SQS redrive policy는 오류 종류를 이해하지 못하고 receive count만 봅니다. 애플리케이션 metric은 permanent, retryable, duplicate와 contract violation을 구분해야 합니다. 그렇지 않으면 "error rate가 높다"는 경보만 남고 어떤 팀이 무엇을 고쳐야 하는지 알 수 없습니다.

13. Concurrency는 queue를 빨리 비우는 값이 아니라 downstream 보호 한도다

Lambda의 maximum concurrency를 크게 설정하면 backlog는 빨리 줄 수 있지만 결제사 rate limit, RDS connection과 DynamoDB partition capacity를 동시에 압박합니다. 필요한 concurrency는 target 처리량과 처리 시간으로 계산하고 downstream quota보다 낮게 제한합니다.

Required concurrency
  approximately target messages per second x p95 processing seconds

Downstream-safe concurrency
  = min(payment concurrency budget,
        database connection budget,
        idempotency store budget,
        Lambda account budget)

Event source maximum concurrency
  <= downstream-safe concurrency

batch size 10이 곧 10개의 결제를 병렬 호출한다는 뜻은 아닙니다. 예시 handler는 batch 안에서 순차 처리합니다. 내부 병렬화를 추가한다면 invocation concurrency와 batch parallelism의 곱을 downstream request rate로 계산해야 합니다.

14. DLQ는 실패를 해결하지 않고 처리 경로에서 격리한다

DLQ에 들어간 message는 보존됐지만 주문 문제는 해결되지 않았습니다. 고객에게는 결제가 지연됐고, inventory reservation이 만료될 수 있으며, 운영팀은 message가 사라지기 전에 원인을 수정해야 합니다.

flowchart LR source[Source queue] --> retry[Bounded attempts] retry -->|success| done[Business completion] retry -->|max receives exceeded| dlq[Dead-letter queue] dlq --> triage[Classify and redact] triage --> fix[Deploy root-cause fix] fix --> canary[Canary redrive] canary --> reconcile[Business reconciliation]

DLQ alarm은 queue depth가 1 이상일 때 빠르게 알리되, page 여부는 주문 중요도와 자동 복구 가능성에 따라 정합니다. message body 전체를 Slack이나 ticket에 복사하지 않고 event ID, schema version, error class와 receive count만 전달합니다.

15. Redrive 전에 root cause와 중복 안전성을 다시 검증한다

  1. producer contract, consumer bug, dependency 장애와 capacity 중 원인을 분류합니다.
  2. 대표 message를 격리된 fixture로 재현하고 payload의 민감 정보를 제거합니다.
  3. 수정 version에서 duplicate와 post-side-effect crash test를 다시 통과합니다.
  4. 현재 source traffic과 downstream headroom을 확인합니다.
  5. 낮은 redrive velocity로 시작하고 업무 invariant를 관찰합니다.
  6. 오류가 재발하면 move task를 취소하고 자동 반복을 중단합니다.
DLQ_ARN="arn:aws:sqs:ap-northeast-2:123456789012:order-events-dlq"
REPLAY_ARN="arn:aws:sqs:ap-northeast-2:123456789012:order-events-replay"

aws sqs start-message-move-task \
  --source-arn "$DLQ_ARN" \
  --destination-arn "$REPLAY_ARN" \
  --max-number-of-messages-per-second 5

aws sqs list-message-move-tasks \
  --source-arn "$DLQ_ARN" \
  --max-results 1

destination을 생략하면 원래 source queue로 돌릴 수 있지만, production traffic과 즉시 섞이면 재발 원인과 부하를 분리하기 어렵습니다. 같은 queue type의 제한된 replay queue에서 canary consumer로 확인한 뒤 source redrive를 확대하는 방식을 선택할 수 있습니다. redrive된 message는 새 message ID와 enqueue time을 받으므로 업무 key와 최초 발생 시각은 payload 또는 별도 ledger에 유지합니다.

16. FIFO와 DLQ를 함께 쓸 때는 순서 손실을 의식한다

FIFO queue에서 한 message가 처리되지 않으면 같은 message group의 뒤 항목이 막힙니다. DLQ로 옮기면 pipeline은 진행되지만 업무 순서는 끊어질 수 있습니다. AWS도 순서가 절대적으로 중요하다면 FIFO queue에 DLQ를 사용하는 것이 적합하지 않을 수 있다고 안내합니다.

주문 상태를 CREATED, PAID, SHIPPED 순서로 적용해야 한다면 consumer는 aggregateVersion을 비교합니다. version 3이 DLQ로 이동한 뒤 version 4가 도착했다면 무조건 진행하지 않고, current state를 조회해 보류하거나 reconciliation workflow로 넘깁니다.

17. 관측은 queue, function, idempotency와 business 네 층으로 나눈다

DLQ로 자동 이동한 message는 DLQ의 NumberOfMessagesSent와 일치하지 않을 수 있으므로 이 지표 하나를 ingress count로 사용하지 않습니다. 주문 완료 지연은 occurredAt부터 실제 업무 완료 시각까지 application metric으로 측정합니다.

20. 비용은 SQS 요청 수보다 중복 side effect까지 포함한다

Monthly processing cost
  = SQS send receive delete and redrive requests
  + Lambda invocations and duration
  + DynamoDB idempotency reads writes and storage
  + KMS requests when applicable
  + logs metrics and traces
  + outbox relay and cleanup
  + duplicate external API calls and reconciliation labor

batch size를 키우면 Lambda invocation overhead는 줄지만 한 invocation의 처리 시간과 부분 실패 surface가 커집니다. visibility timeout을 잘못 설정해 성공 message가 반복되면 SQS와 Lambda 비용보다 결제사 호출과 운영 조사 비용이 더 클 수 있습니다. 비용 최적화는 멱등성 제거가 아니라 duplicate rate, batch 효율과 log volume을 함께 줄이는 방향이어야 합니다.

22. 아직 production-grade라고 주장하지 않는 범위

  • 이 글의 latency, concurrency, visibility와 redrive 수치는 실제 workload의 측정값이 아닙니다.
  • transactional outbox relay의 lease, pagination, cleanup과 장애 복구 코드를 구현하지 않았습니다.
  • 결제사의 실제 idempotency key 보존 기간과 동일 key·다른 payload 동작을 검증하지 않았습니다.
  • Lambda timeout 직전의 external API unknown result를 production sandbox에서 재현하지 않았습니다.
  • 대규모 backlog와 production traffic이 동시에 존재할 때 downstream quota를 부하 테스트하지 않았습니다.
  • Multi-Region active-active 주문 처리와 Region 간 idempotency 저장소 일관성을 다루지 않았습니다.
  • 고객 알림, 재고 reservation 만료와 환불까지 포함한 end-to-end 보상 workflow를 구현하지 않았습니다.

이 상태에서 말할 수 있는 것은 "SQS-Lambda 주문 처리의 운영 계약을 설계했다"까지입니다. 실제 duplicate injection, dependency outage, DLQ redrive와 reconciliation 결과가 채워져야 production-grade라는 주장이 완성됩니다.

23. 마무리

SQS 기반 주문 처리의 목표는 message를 한 번만 받는 것이 아닙니다. message가 여러 번 도착하고 consumer가 어디서든 종료될 수 있다는 전제에서 주문, 결제와 재고의 업무 효과를 한 번만 적용하고, 해결되지 않은 message를 조사 가능한 상태로 격리하는 것입니다.

멱등성은 duplicate를 숨기는 코드 한 줄이 아니라 producer transaction, consumer lock, 외부 side effect와 reconciliation을 관통하는 업무 계약입니다. DLQ는 그 계약이 실패했을 때 조사를 시작하는 지점입니다.
