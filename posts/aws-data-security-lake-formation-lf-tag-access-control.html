AWS · Data Security · Lake Formation

[AWS/Data Security] 데이터 레이크 테이블이 수천 개로 늘어나면 권한은 어떻게 관리할까? - Lake Formation LF-Tag 기반 접근 제어

데이터 레이크가 커지면 테이블과 컬럼마다 권한을 직접 연결하는 방식은 운영 한계에 부딪힌다. Lake Formation LF-Tag는 권한 기준을 개별 리소스 이름에서 Department, Sensitivity, Domain 같은 리소스 속성으로 바꿔 permission model을 확장 가능하게 만든다.

Amazon S3 기반 데이터 레이크를 운영하다 보면 처음에는 권한 관리가 어렵지 않다.

부서별로 접근 가능한 테이블이 몇 개뿐이라면 각 IAM Role에 필요한 리소스 권한을 직접 부여하면 된다.

flowchart TB finance[Finance Role] --> sales[sales_table] finance --> revenue[revenue_table] finance --> forecast[forecast_table] hr[HR Role] --> employee[employee_table] hr --> payroll[payroll_table]

하지만 데이터 레이크가 커지면 이야기가 달라진다.

테이블이 수백 개에서 수천 개로 증가하고, 부서가 50개 이상이며, 각 부서에 수백 명의 사용자가 있다면 개별 테이블과 컬럼 단위로 권한을 직접 관리하는 방식은 빠르게 복잡해진다.

이때 사용할 수 있는 것이 AWS Lake Formation의 LF-Tag 기반 접근 제어다.

1. 왜 단순한 리소스 단위 권한 부여가 문제가 될까?

다음과 같은 환경을 생각해보자.

flowchart TB lake[Data Lake] --> tables[800+ Tables
향후 수천 개로 증가] lake --> columns[여러 Columns] org[Departments] --> finance2[Finance] org --> hr2[HR] org --> marketing[Marketing] org --> ops[Operations] org --> many[50+ departments]

각 부서는 자신에게 필요한 특정 테이블과 컬럼에만 접근해야 한다.

작은 환경에서는 직접 권한을 지정하는 방식도 충분하다.

flowchart TB finance3[Finance Role] --> tableA[table_a] finance3 --> tableB[table_b] finance3 --> tableC[table_c] hr3[HR Role] --> tableD[table_d] hr3 --> tableE[table_e]

하지만 리소스가 계속 늘어나면 관리해야 하는 permission mapping 수도 함께 증가한다.

Resources x Departments x Permission Rules

테이블이 수천 개로 늘어나면 새로운 테이블이 추가될 때마다 기존 권한 정책을 수정해야 할 수도 있다.

이 방식은 운영 비용이 크고, 권한 누락이나 과도한 권한 부여 같은 실수도 발생하기 쉽다.

2. LF-Tag 기반 접근 제어

Lake Formation은 데이터 카탈로그 리소스에 LF-Tag를 부착할 수 있다.

예를 들어 테이블에 다음과 같은 태그를 지정할 수 있다.

Table: sales_2026

LF-Tags
- Department = Finance
- DataType   = Revenue
- Sensitivity = Internal

사용자나 IAM Role에는 특정 리소스 이름 대신 태그 조건에 대한 권한을 부여할 수 있다.

FinanceRole

Allow access when:
Department = Finance

그러면 Finance 태그가 붙은 새로운 테이블이 추가되더라도 개별 테이블 이름을 permission policy에 추가할 필요가 없다.

flowchart TB table1[Table A
Department=Finance] --> financeRole[Finance Role] table2[Table B
Department=Finance] --> financeRole table3[Table C
Department=Finance] --> financeRole newTable[New Table
Department=Finance] --> financeRole

즉 권한 관리 단위가 resource에서 attribute 또는 tag로 바뀐다.

flowchart LR resource[Resource-based Permission] --> tag[Attribute / Tag-based Permission]

3. RBAC에서 ABAC로

이 구조는 ABAC(Attribute-Based Access Control) 관점으로 이해할 수 있다.

전통적인 리소스 기반 권한 관리는 role과 resource를 직접 연결한다.

flowchart TB role[Role] --> ra[Resource A] role --> rb[Resource B] role --> rc[Resource C]

반면 태그 기반 접근 제어는 role을 attribute condition에 연결하고, 해당 조건에 맞는 리소스가 접근 대상이 된다.

flowchart TB role2[Role] --> condition[Attribute Condition] condition --> matched[Matching Resources]

예를 들어 다음처럼 tag taxonomy를 설계할 수 있다.

Department
- Finance
- HR
- Marketing
- Operations

Sensitivity
- Public
- Internal
- Restricted

Domain
- Customer
- Revenue
- Employee

그리고 Finance 분석가에게 다음 조건을 적용할 수 있다.

Department = Finance
AND
Sensitivity != Restricted

이 방식은 리소스 수가 많아질수록 장점이 커진다.

4. Lake Formation과 IAM의 역할은 다르다

주의할 점은 LF-Tag가 IAM을 완전히 대체하는 것은 아니라는 점이다.

IAM은 여전히 AWS 서비스와 API 자체에 접근할 수 있는 권한을 제어한다.

Can user call Athena?
Can user access Glue APIs?
Can user assume this role?

반면 Lake Formation은 데이터 레이크 안에서 어떤 database, table, column에 접근할 수 있는지를 세밀하게 제어한다.

flowchart TB user[User] --> role3[IAM Role] role3 --> athena[Amazon Athena] athena --> permission[Lake Formation Permission] permission --> catalog[Glue Data Catalog] catalog --> s3[S3 Data]

즉 IAM과 Lake Formation은 경쟁 관계가 아니라 서로 다른 계층의 권한을 담당한다.

5. 왜 Athena와 잘 어울릴까?

S3 기반 데이터 레이크에서는 Amazon Athena를 사용하면 별도의 분석 서버나 클러스터를 운영하지 않고도 SQL로 데이터를 조회할 수 있다.

flowchart TB user2[User] --> athena2[Athena] athena2 --> catalog2[Glue Data Catalog] catalog2 --> lakeFormation[Lake Formation] lakeFormation --> s32[S3]

따라서 다음과 같은 요구사항에는 잘 맞는다.

S3 Data Lake
+ 많은 Tables
+ 많은 Departments
+ Fine-grained Permission
+ 낮은 운영 부담

별도의 Redshift 클러스터나 EMR 클러스터를 부서마다 생성하는 것보다 운영 구조가 훨씬 단순하다.

6. 왜 부서마다 Redshift 클러스터를 만들지 않을까?

부서별로 Redshift cluster를 하나씩 만들면 물리적으로 workload와 데이터를 분리할 수는 있다.

flowchart TB dept1[Department 1] --> rs1[Redshift Cluster] dept2[Department 2] --> rs2[Redshift Cluster] dept3[Department 3] --> rs3[Redshift Cluster] dept50[Department 50+] --> rs50[Redshift Cluster]

하지만 50개 이상의 부서가 있다면 cluster 운영, scaling, patch, cost, data synchronization, permission management가 모두 늘어난다.

원래 요구사항은 데이터 레이크의 테이블과 컬럼에 대한 접근 제어인데, 이를 위해 수십 개의 별도 분석 클러스터를 만드는 것은 지나치게 무겁다.

7. 왜 일반 Lake Formation 권한보다 LF-Tag가 더 적합할까?

Lake Formation은 태그 없이도 특정 테이블에 직접 권한을 줄 수 있다.

flowchart TB finance4[FinanceRole] --> table001[table_001] finance4 --> table019[table_019] finance4 --> table083[table_083]

이 방식도 동작한다. 하지만 문제는 확장성이다.

테이블 수가 적으면 direct permission이 간단할 수 있지만, 수천 개로 증가할 예정이라면 계속해서 리소스별 권한을 관리해야 한다.

LF-Tag를 사용하면 다음 구조로 관리할 수 있다.

flowchart TB create[Table 생성] --> tagTable[Department=Finance 태그 부여] tagTable --> included[기존 Finance Role 정책에 자동 포함]

중요한 차이는 다음과 같다.

Direct Permission
= 리소스를 하나씩 관리

LF-Tag Permission
= 리소스의 속성을 관리

8. 권한 모델 선택 기준

다음 조건이 함께 나타나면 LF-Tag 기반 권한을 먼저 검토할 수 있다.

flowchart TB manyTables[많은 Tables] --> lfTag[LF-Tag Access Control] manyUsers[많은 Users / Departments] --> lfTag fine[Fine-grained Access] --> lfTag opsCost[운영 비용 최소화] --> lfTag growth[앞으로 계속 확장] --> lfTag

반대로 테이블 수가 적고 권한 구조가 단순하다면 직접적인 Lake Formation permission도 충분할 수 있다.

LF-Tag의 핵심은 단순히 더 보안이 좋다는 것이 아니다.

대규모 데이터 레이크에서 permission management 자체를 확장 가능하게 만드는 것.

9. 구조 정리

전체 구조를 단순화하면 다음과 같다.

flowchart TB users[Users] --> roles[Department IAM Roles] roles --> athena3[Amazon Athena] athena3 --> lakeFormation2[AWS Lake Formation] lakeFormation2 --> tagPermission[LF-Tag Permission] tagPermission --> glue[AWS Glue Data Catalog] glue --> s3lake[Amazon S3 Data Lake]

예를 들어 테이블에 부서 태그가 붙어 있다면 접근 권한은 다음처럼 결정된다.

flowchart TB tableA2[Table A
Department=Finance] --> financeRole2[Finance Role] tableB2[Table B
Department=Finance] --> financeRole2 tableC2[Table C
Department=HR] --> hrRole2[HR Role] tableD2[Table D
Department=Marketing] --> marketingRole[Marketing Role]

새로운 Finance 테이블이 생겨도 동일한 LF-Tag만 부여하면 기존 permission model에 포함할 수 있다.

10. 마무리

작은 데이터 레이크에서는 리소스마다 직접 권한을 부여하는 방식이 가장 이해하기 쉽다.

하지만 데이터 레이크가 성장하면 권한 관리 자체가 새로운 확장성 문제가 된다.

수천 개 Tables
x 수십 개 Departments
x 다수의 Permission Rules

환경에서 리소스 이름을 하나씩 관리하는 것은 지속하기 어렵다.

Lake Formation의 LF-Tag 기반 접근 제어는 권한의 기준을 개별 리소스에서 리소스의 속성으로 바꾼다.

flowchart LR resource2[Resource-based
이 Table에 접근 가능] --> tag2[Tag-based
Department=Finance인 모든 Table에 접근 가능]

따라서 대규모 S3 데이터 레이크에서는 단순히 데이터를 어디에 저장할지만큼이나 권한 정책을 어떻게 확장 가능하게 관리할 것인가가 중요한 설계 문제가 된다.

이런 상황에서 LF-Tag 기반 접근 제어는 수천 개의 테이블과 여러 조직을 개별 정책으로 연결하는 대신, 태그를 중심으로 permission model을 단순화할 수 있는 방법이다.
