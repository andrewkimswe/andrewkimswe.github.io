[AWS/Networking] Private EC2가 S3에 접근하는데 NAT Gateway가 꼭 필요할까? - Gateway VPC Endpoint로 비용 줄이기

Private Subnet의 EC2가 S3에 접근한다고 해서 항상 NAT Gateway가 필요한 것은 아니다. 목적지가 S3라면 Gateway VPC Endpoint로 경로를 분리해 비용과 보안 경계를 함께 개선할 수 있다.

Private Subnet의 EC2 인스턴스가 Amazon S3에 접근해야 한다면 가장 먼저 NAT Gateway를 떠올릴 수 있다.

flowchart TB ec2[Private EC2] --> nat[NAT Gateway] nat --> s3[Amazon S3]

이 구조는 정상적으로 동작한다. 하지만 EC2가 같은 AWS 리전의 S3에 대량으로 접근한다면 질문이 달라진다.

AWS 내부 서비스인 S3에 접근하기 위해 꼭 NAT Gateway를 거쳐야 할까?

그럴 필요는 없다. Amazon S3는 Gateway VPC Endpoint를 지원한다.

1. NAT Gateway를 통한 S3 접근

Private Subnet의 EC2는 일반적으로 Internet Gateway로 직접 인터넷에 접근할 수 없다. 외부로 나가야 한다면 NAT Gateway를 사용할 수 있다.

flowchart TB subgraph private[Private Subnet] ec21[EC2] end subgraph public[Public Subnet] nat2[NAT Gateway] end ec21 -->|0.0.0.0/0| nat2 nat2 --> igw[Internet Gateway] igw --> external[External Service]

문제는 EC2가 주로 접근하는 대상이 S3인 경우다. NAT Gateway에는 시간당 비용뿐 아니라 처리한 데이터에 따른 비용도 발생한다.

S3로 많은 데이터를 전송한다면 NAT 경로 때문에 불필요한 데이터 처리 비용이 커질 수 있다.

2. Gateway VPC Endpoint

VPC Endpoint를 사용하면 VPC와 지원되는 AWS 서비스 사이를 private하게 연결할 수 있다. S3에서는 Gateway Endpoint를 사용할 수 있다.

flowchart TB ec22[Private EC2] -->|S3 Traffic| endpoint[Gateway VPC Endpoint] endpoint --> s32[Amazon S3]

NAT Gateway를 거칠 필요가 없고 Internet Gateway도 필요하지 않다. 즉 S3 접근 경로를 AWS 네트워크 안에서 처리할 수 있다.

3. Route Table에서 무엇이 달라질까?

기존 Private Subnet의 route table이 다음과 같다고 해보자.

Destination       Target

10.0.0.0/16       local
0.0.0.0/0         NAT Gateway

Gateway VPC Endpoint를 생성하고 route table과 연결하면 S3를 위한 route가 추가된다.

Destination       Target

10.0.0.0/16       local
S3 Prefix List    vpce-xxxxx
0.0.0.0/0         NAT Gateway
flowchart TB traffic[Private EC2 Traffic] --> dest{Destination} dest -->|S3 Prefix List| endpoint2[Gateway Endpoint] dest -->|0.0.0.0/0| nat3[NAT Gateway]

즉 S3 트래픽만 NAT Gateway에서 분리할 수 있다.

4. 왜 비용이 줄어들까?

NAT Gateway는 관리가 편리하지만 처리하는 트래픽에 비용이 발생한다. 애플리케이션이 S3에서 지속적으로 데이터를 읽으면 NAT Gateway가 그 데이터를 처리한다.

flowchart LR before[Before
EC2 -> NAT Gateway -> S3] --> after[After
EC2 -> Gateway Endpoint -> S3]

S3 Gateway Endpoint는 NAT Gateway처럼 시간당 NAT 비용과 NAT 데이터 처리 비용을 발생시키는 구조가 아니다. S3/DynamoDB 트래픽을 NAT에서 분리하는 것은 대표적인 AWS 네트워크 비용 최적화 방법이다.

5. 보안 측면에서도 장점이 있다

Gateway Endpoint를 사용하면 S3 접근을 인터넷 경로에 의존하지 않아도 된다.

flowchart TB ec23[Private EC2] --> vpce[VPC Endpoint] vpce --> s33[S3]

그리고 VPC Endpoint Policy를 통해 endpoint에서 접근 가능한 S3 리소스를 제한할 수도 있다. S3 Bucket Policy에서도 특정 VPC Endpoint를 통한 요청만 허용하도록 제한하는 설계를 고려할 수 있다.

6. 다른 선택지는 왜 덜 직접적인가?

NAT Instance는 비용을 낮출 수 있지만 OS patch, instance sizing, failure handling, scaling, availability, security configuration을 직접 관리해야 한다.

Internet Gateway로 바꾸는 것도 문제의 핵심을 해결하지 않는다. S3가 목적지라면 굳이 인터넷 접근 구조로 바꿀 이유가 없다.

요구사항이 보안이나 중복성을 손상시키지 않고 S3 접근 비용을 줄이는 것이라면 S3 Gateway Endpoint가 훨씬 직접적이다.

7. Gateway Endpoint와 Interface Endpoint

설계에서는 Gateway Endpoint와 Interface Endpoint의 대상 서비스, 비용, 연결 방식을 구분해야 한다.

구분주요 대상구조
Gateway EndpointAmazon S3, DynamoDBRoute Table과 연결
Interface EndpointSQS, SNS, Secrets Manager 등PrivateLink 기반 ENI 생성
flowchart TB s3dynamo[S3 / DynamoDB] --> gateway[Gateway Endpoint] services[Many AWS Services] --> interface[Interface Endpoint]

8. NAT Gateway 자체가 항상 사라지는 것은 아니다

S3 Gateway Endpoint를 만들었다고 해서 NAT Gateway가 무조건 필요 없어지는 것은 아니다. EC2가 GitHub, 외부 API, 패키지 저장소 같은 인터넷 서비스에도 접근해야 한다면 outbound internet connectivity가 필요할 수 있다.

flowchart TB s3traffic[S3 Traffic] --> gateway2[Gateway Endpoint] internet[Internet Traffic] --> nat4[NAT Gateway]

해당 workload가 S3 같은 VPC Endpoint 지원 서비스에만 접근한다면 NAT Gateway 자체를 제거할 가능성도 생긴다.

9. 네트워크 경로 선택 기준

Private Subnet의 workload가 같은 Region의 Amazon S3에 접근하고 NAT Gateway 처리 비용을 줄이면서 private path를 유지해야 한다면 Gateway VPC Endpoint를 먼저 검토한다.

flowchart TB privateEc2[Private EC2] --> s3Endpoint[S3 Gateway VPC Endpoint] s3Endpoint --> s34[S3]

Private S3 트래픽에 NAT 비용을 내고 있다면 Gateway Endpoint부터 확인한다.

10. 마무리

NAT Gateway는 Private Subnet에서 외부 네트워크로 나가는 대표적인 방법이지만, 모든 AWS 서비스 트래픽을 NAT를 통해 보낼 필요는 없다.

특히 S3와 DynamoDB는 Gateway VPC Endpoint를 지원한다. S3 트래픽을 NAT Gateway에서 분리하면 비용과 보안 경로를 동시에 개선할 수 있다.

이 문제에서 중요한 것은 단순히 VPC Endpoint라는 서비스를 암기하는 것이 아니다. 트래픽의 목적지가 어디인지 보고, 굳이 NAT를 통과해야 하는 트래픽인지 판단하는 것이다.
