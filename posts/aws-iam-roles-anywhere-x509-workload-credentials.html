데이터센터의 백업 에이전트가 매일 결과를 S3에 업로드하고 CloudWatch에 실행 상태를 기록한다고 가정해보겠습니다. 가장 빠른 구현은 IAM User의 Access Key를 서버에 저장하는 것입니다. 시간이 지나면 같은 Key가 이미지, 설정 관리 도구와 장애 대응 문서에 복제되고, 어느 프로세스가 사용했는지와 언제 폐기해야 하는지 알기 어려워집니다.

IAM Roles Anywhere는 X.509 인증서와 private key로 요청을 서명하고, 검증된 workload에 IAM Role의 임시 자격 증명을 발급합니다. 그러나 Access Key 파일을 인증서 파일로 교체하는 데서 끝내면 credential lifecycle 문제는 그대로 남습니다. 이 글은 실제 production 도입 회고가 아니라 설계와 검증 계획이며, 아래 수치는 실측값이나 AWS SLA가 아닌 초기 acceptance target입니다.

1. 문제는 Access Key 저장이 아니라 workload identity다

핵심 질문은 "Key를 어디에 숨길까"가 아닙니다. 어떤 workload가 어떤 근거로 AWS Role을 사용할 수 있고, 인증서와 서버가 교체되거나 침해됐을 때 얼마나 빨리 권한을 회수할 수 있는가입니다.

flowchart LR workload[On-prem backup agent] --> helper[Credential helper] helper -->|X.509 signed CreateSession| ra[IAM Roles Anywhere] ra -->|Temporary credentials| workload workload --> s3[S3 backup prefix] workload --> cw[CloudWatch metrics]

임시 자격 증명은 노출 시간을 줄이지만, 인증서 private key가 장기간 복제 가능하거나 CA가 모든 workload에 같은 subject를 발급한다면 강한 identity라고 보기 어렵습니다. PKI와 IAM 양쪽의 통제를 함께 설계해야 합니다.

2. 요구사항과 비요구사항을 먼저 고정한다

이 사례의 요구사항은 다음과 같습니다.

  • 온프레미스 백업 에이전트에 장기 AWS Access Key를 저장하지 않습니다.
  • Workload마다 식별 가능한 X.509 identity를 발급하고 private key를 복제할 수 없게 보관합니다.
  • 허용된 CA의 인증서 중에서도 정확한 SAN URI와 issuer만 Role을 사용할 수 있습니다.
  • 발급된 AWS session은 최소 권한과 제한된 duration을 가집니다.
  • 인증서 만료, 회전, 폐기와 CRL 반영 상태를 지속적으로 관찰합니다.
  • Private key 침해 시 신규 session 발급 차단과 기존 session 권한 차단을 구분해 수행합니다.

사람의 Console 로그인, 다른 AWS account의 workload, 모든 서버의 원격 관리와 PKI 자체 구축은 비요구사항입니다. 사람은 workforce federation을 사용하고, 다른 AWS account의 workload는 native IAM Role을 우선 사용합니다.

3. Access Key, OIDC, SSM과 Roles Anywhere를 비교한다

이 환경에는 workload 인증서를 발급하고 회전하는 기존 enterprise PKI가 있으므로 Roles Anywhere를 선택합니다. VPN은 API 경로를 만들 뿐 IAM credential을 발급하지 않고, SSM 등록 identity는 임의의 application SDK 권한 모델을 대신하지 않습니다. 반대로 PKI가 없고 Kubernetes의 OIDC workload identity가 이미 안정적이라면 Roles Anywhere를 위해 새 CA를 만드는 결정은 과할 수 있습니다.

4. 인증서를 STS 자격 증명으로 교환하는 흐름

sequenceDiagram participant W as Workload participant H as aws_signing_helper participant R as IAM Roles Anywhere participant S as AWS STS participant A as AWS API W->>H: Request credentials H->>H: Sign request with private key H->>R: CreateSession + certificate chain R->>R: Validate signature, chain, CRL and profile R->>S: AssumeRole + tags + source identity S-->>R: Temporary credentials R-->>H: Access key, secret, token, expiration H-->>W: Standard credential JSON W->>A: SigV4 API request

CreateSession은 X.509로 서명된 요청을 검증한 뒤 IAM Role session으로 교환하는 경계입니다. 인증서는 AWS API를 직접 호출하는 credential이 아니며, 발급된 Access Key ID, Secret Access Key와 Session Token이 일반 SigV4 요청에 사용됩니다.

5. Trust Anchor, Profile과 Role은 서로 다른 경계다

구성 요소답하는 질문주요 실패
Trust Anchor어느 CA chain을 신뢰하는가?너무 넓은 CA bundle, 만료, 비활성화
Profile어느 Role과 session policy를 사용할 수 있는가?과도한 Role 목록, 긴 duration
Role Trust Policy어느 anchor와 certificate attribute를 신뢰하는가?SourceArn과 attribute condition 누락
Role Permission Policy발급된 session이 무엇을 할 수 있는가?Resource와 action 범위 과다
Resource Policy대상 resource가 이 session을 허용하는가?Role policy와 다른 우회 경로

한 계층에서 Allow됐다는 이유로 전체 요청이 허용되는 것이 아닙니다. 반대로 CreateSession이 실패했을 때 S3 Bucket Policy부터 보는 것도 순서가 틀립니다. Credential 발급 경계와 발급 후 AWS API authorization을 분리합니다.

6. CA를 신뢰하는 것과 workload를 허용하는 것은 다르다

Trust Anchor에 등록한 CA 또는 그 하위 CA가 발급한 유효한 인증서는 trust chain을 통과할 수 있습니다. Role Trust Policy에 추가 조건이 없다면 같은 CA의 다른 용도 인증서까지 Role을 assume할 수 있는 범위가 생깁니다.

flowchart TB root[Enterprise Root CA] --> workloadCa[Workload Intermediate CA] root --> userCa[User Certificate CA] workloadCa --> backup[Backup workload certificate] workloadCa --> billing[Billing workload certificate] userCa --> laptop[Employee certificate] anchor[Roles Anywhere Trust Anchor] -. trust only .-> workloadCa role[Backup Role Trust Policy] -. exact SAN URI .-> backup

가능하면 전체 enterprise root보다 workload 전용 intermediate CA를 Trust Anchor로 등록합니다. 그래도 backup과 billing workload가 같은 intermediate를 쓴다면 SAN URI, issuer CN과 Role을 함께 제한합니다. 인증서 발급 정책 자체도 허용된 subject와 SAN namespace를 검증해야 합니다.

7. 인증서 속성을 authorization contract로 만든다

이 설계에서는 subject를 비워두지 않고 CN=backup-agent-17처럼 unique workload instance를 기록하며, authorization용 안정된 identity는 spiffe://corp.example/backup/prod SAN URI에 둡니다. 인증서를 재발급해 serial number가 바뀌어도 workload class의 권한 계약은 유지할 수 있습니다.

필드사용 목적변경 주기
Subject CN개별 workload 추적과 source identityInstance 교체 시
SAN URIRole authorization과 workload class서비스 책임 변경 시
Issuer CN허용된 issuance path 확인Intermediate CA 교체 시
Serial NumberSession name, 인증서·CloudTrail correlation인증서 재발급 시

Profile의 attribute mapping이 해당 field와 specifier를 session principal tag로 전달해야 Trust Policy의 조건이 평가됩니다. Mapping에서 SAN URI를 제거하면서 Trust Policy만 남기면 안전하게 deny되지만, 반대로 조건을 지우면 같은 CA의 인증서가 넓게 허용될 수 있습니다.

8. Trust Policy에서 confused deputy와 광범위한 CA 신뢰를 막는다

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Service": "rolesanywhere.amazonaws.com"
    },
    "Action": [
      "sts:AssumeRole",
      "sts:TagSession",
      "sts:SetSourceIdentity"
    ],
    "Condition": {
      "ArnEquals": {
        "aws:SourceArn": "arn:aws:rolesanywhere:ap-northeast-2:111122223333:trust-anchor/TA_ID"
      },
      "StringEquals": {
        "aws:SourceAccount": "111122223333",
        "aws:PrincipalTag/x509Issuer/CN": "Corp-Workload-CA-v2",
        "aws:PrincipalTag/x509SAN/URI": "spiffe://corp.example/backup/prod"
      }
    }
  }]
}

aws:SourceArn은 정확한 Trust Anchor를, aws:SourceAccount는 해당 anchor의 account를 제한해 service principal을 통한 confused deputy 범위를 줄입니다. Certificate attribute condition은 그 anchor 아래에서 backup workload만 선택합니다. 세 Action 중 하나라도 빠지면 Roles Anywhere가 source identity와 session tag를 설정하는 과정에서 실패할 수 있습니다.

9. Profile은 Role 권한을 더 좁히는 session boundary다

Profile은 사용할 수 있는 Role ARN, credential duration, managed 또는 inline session policy와 attribute mapping을 정의합니다. Session permission은 Role permission과 Profile session policy의 교집합이므로 Profile에서 권한을 추가할 수는 없고 더 줄일 수만 있습니다.

flowchart LR cert[Certificate attributes] --> trust[Role trust conditions] profile[Profile role list] --> assume[CreateSession allowed?] trust --> assume rolePolicy[Role permissions] --> intersection[Permission intersection] sessionPolicy[Profile session policy] --> intersection assume --> intersection intersection --> aws[S3 and CloudWatch APIs]

하나의 Profile에 수백 개 Role을 넣으면 certificate와 Role의 대응 관계가 흐려집니다. 이 사례에서는 workload class마다 Profile과 Role을 1:1로 두고, custom role session name은 받지 않아 certificate serial 기반 기본 session name의 audit 일관성을 유지합니다.

10. Trust Anchor, Role과 Profile을 IaC로 고정한다

Parameters:
  WorkloadCaCertificatePem:
    Type: String
    NoEcho: true

Resources:
  WorkloadTrustAnchor:
    Type: AWS::RolesAnywhere::TrustAnchor
    Properties:
      Name: corp-workload-ca-v2
      Enabled: true
      Source:
        SourceType: CERTIFICATE_BUNDLE
        SourceData:
          X509CertificateData: !Ref WorkloadCaCertificatePem
      NotificationSettings:
        - Channel: ALL
          Enabled: true
          Event: CA_CERTIFICATE_EXPIRY
          Threshold: 60
        - Channel: ALL
          Enabled: true
          Event: END_ENTITY_CERTIFICATE_EXPIRY
          Threshold: 14

  BackupAgentRole:
    Type: AWS::IAM::Role
    Properties:
      MaxSessionDuration: 3600
      AssumeRolePolicyDocument:
        Version: "2012-10-17"
        Statement:
          - Effect: Allow
            Principal:
              Service: rolesanywhere.amazonaws.com
            Action:
              - sts:AssumeRole
              - sts:TagSession
              - sts:SetSourceIdentity
            Condition:
              ArnEquals:
                aws:SourceArn: !GetAtt WorkloadTrustAnchor.TrustAnchorArn
              StringEquals:
                aws:SourceAccount: !Ref AWS::AccountId
                aws:PrincipalTag/x509Issuer/CN: Corp-Workload-CA-v2
                aws:PrincipalTag/x509SAN/URI: spiffe://corp.example/backup/prod

  BackupProfile:
    Type: AWS::RolesAnywhere::Profile
    Properties:
      Name: backup-agent-prod
      Enabled: true
      DurationSeconds: 3600
      AcceptRoleSessionName: false
      RoleArns:
        - !GetAtt BackupAgentRole.Arn
      AttributeMappings:
        - CertificateField: x509Issuer
          MappingRules:
            - Specifier: CN
        - CertificateField: x509SAN
          MappingRules:
            - Specifier: URI
      SessionPolicy: !Sub |
        {"Version":"2012-10-17","Statement":[
          {"Effect":"Allow","Action":["s3:PutObject"],
           "Resource":["arn:${AWS::Partition}:s3:::corp-backup-prod/onprem/*"]}
        ]}

예시의 CA certificate는 secret이 아니지만 배포 로그에서 긴 PEM이 불필요하게 노출되지 않도록 parameter 취급을 제한했습니다. 실제 Role에는 S3 multipart upload에 필요한 action, 암호화에 사용하는 KMS 권한과 CloudWatch 권한을 요구사항에 맞춰 추가하고, Bucket Policy와 KMS Key Policy에서도 동일한 Role 경계를 검증해야 합니다.

11. credential helper를 표준 credential provider로 연결한다

[profile onprem-backup]
region = ap-northeast-2
credential_process = /opt/aws/rolesanywhere/aws_signing_helper credential-process \
  --certificate /etc/workload-pki/backup-agent.pem \
  --private-key 'pkcs11:object=backup-agent-key;type=private' \
  --intermediates /etc/workload-pki/intermediate-chain.pem \
  --trust-anchor-arn arn:aws:rolesanywhere:ap-northeast-2:111122223333:trust-anchor/TA_ID \
  --profile-arn arn:aws:rolesanywhere:ap-northeast-2:111122223333:profile/PROFILE_ID \
  --role-arn arn:aws:iam::111122223333:role/BackupAgentRole \
  --session-duration 3600

AWS CLI와 SDK는 표준 credential_process 결과를 읽고 만료 전에 다시 credential을 요청할 수 있습니다. Application code에 임시 credential을 직접 파싱하거나 환경 변수로 주입하는 logic을 추가하지 않습니다. Helper binary는 승인된 version과 checksum을 artifact registry에 고정하고, upgrade는 certificate signing과 refresh canary를 통과시킵니다.

update mode는 credential을 AWS credentials file에 기록하므로 file permission과 cleanup 책임이 생깁니다. serve mode는 memory에서 자동 refresh하지만 localhost endpoint에 접근 가능한 같은 host의 다른 process도 credential을 받을 수 있습니다. 일반 SDK에는 credential_process를 기본으로 두고, mode 변경은 threat model을 다시 검토합니다.

12. Private Key를 파일로 배포하지 않는다

Roles Anywhere에서 장기 secret의 역할은 Access Key에서 certificate private key로 이동합니다. PEM key를 golden image나 configuration repository에 넣으면 임시 AWS credential의 장점이 크게 줄어듭니다.

  • 가능하면 TPM, HSM 또는 PKCS#11 token에서 non-exportable key를 생성합니다.
  • Credential helper process만 key operation을 사용할 수 있도록 OS 권한과 service account를 제한합니다.
  • CSR 생성, certificate install과 old certificate 제거를 자동화하되 private key material은 전송하지 않습니다.
  • Backup image와 core dump에 key가 포함되지 않는지 복구 테스트에서 확인합니다.
  • --no-verify-ssl은 운영 설정과 runbook에서 금지합니다.

TPM handle이나 token PIN도 credential입니다. Host root가 탈취된 상황까지 막는다고 과장하지 않고, key export 방지와 원격 사용 난이도를 높이는 통제로 평가합니다.

13. Session duration은 보안과 가용성의 예산이다

Roles Anywhere session duration은 15분에서 12시간 범위로 요청할 수 있으며, 실제 duration은 Profile과 CreateSession 요청값 중 작은 값이 사용됩니다. 이 값이 Role의 MaxSessionDuration보다 크면 요청은 실패합니다.

짧은 session긴 session
노출된 credential의 최대 생존 시간 감소Roles Anywhere 또는 network 장애 중 application 지속 시간 증가
CreateSession 빈도와 fleet 동시 refresh 증가폐기 후 남는 기존 session window 증가
CA·helper 문제를 더 빨리 발견문제를 늦게 발견하고 만료 직전 집중될 수 있음

초기값은 1시간으로 두고 helper가 만료 5분 전보다 충분히 앞서 갱신되는지 관찰합니다. 해당 Region의 기본 CreateSession quota는 초당 20건이므로, fleet 재시작과 certificate rotation 때 refresh를 jitter 없이 동시에 시작하지 않습니다. 실제 quota와 workload 수로 peak 요청률을 계산한 뒤 Service Quotas 증설 여부를 결정합니다.

14. Network path와 identity 발급을 분리한다

flowchart TB workload[On-prem workload] --> choice{Credential endpoint path} choice -->|Public HTTPS| public[Regional Roles Anywhere endpoint] choice -->|VPN or Direct Connect| vpce[Interface VPC Endpoint] vpce --> ra[IAM Roles Anywhere API] public --> ra ra --> sts[STS session] sts --> aws[AWS service endpoint]

Public regional endpoint를 사용해도 TLS로 보호되지만, 조직 정책이 private path를 요구하면 VPN 또는 Direct Connect를 통해 com.amazonaws.region.rolesanywhere Interface VPC Endpoint에 접근할 수 있습니다. Endpoint Policy는 CreateSession과 관리 API의 접근 범위를 줄이는 추가 경계가 됩니다.

Roles Anywhere endpoint가 private이어도 S3와 CloudWatch API 경로는 별도로 필요합니다. Credential 발급 성공과 business API 호출 성공을 같은 network check로 합치면 장애 위치를 찾기 어렵습니다.

15. 인증서 회전과 폐기를 하나의 상태 기계로 만든다

stateDiagram-v2 [*] --> Requested Requested --> Issued: CSR and policy approved Issued --> Installed: Key binding verified Installed --> Active: CreateSession canary passes Active --> Rotating: Renewal window opens Rotating --> Active: New certificate passes and old is removed Active --> Revoked: Compromise or decommission Rotating --> Revoked: Rotation fails or owner rejects Revoked --> Archived: CRL imported and sessions handled Archived --> [*]

Inventory에는 subject, SAN URI, serial, issuer, notBefore, notAfter, owner, host, environment와 last successful authentication을 저장합니다. 새 certificate를 설치한 뒤 CreateSession과 실제 S3 canary를 통과시키고, old certificate가 더 이상 사용되지 않는 것을 확인한 후 제거합니다.

Trust Anchor certificate 자체의 회전은 end-entity 회전보다 영향 범위가 큽니다. 새 CA chain을 사전에 등록하고 dual trust 기간을 거친 뒤 old anchor를 비활성화합니다. AWS Private CA trust anchor의 validity 변경은 UpdateTrustAnchor로 Roles Anywhere에 반영해야 합니다.

16. CRL 반영과 기존 STS session 차단을 구분한다

Roles Anywhere는 imported CRL을 CreateSession 전에 확인합니다. CRL Distribution Point callback이나 OCSP 조회를 대신 수행하지 않으므로 CA에서 certificate를 revoke한 것만으로 AWS의 CRL resource가 자동 갱신된다고 가정하면 안 됩니다.

sequenceDiagram participant I as Incident responder participant C as Certificate Authority participant R as Roles Anywhere CRL participant S as Existing STS session I->>C: Revoke certificate C-->>I: Updated CRL I->>R: Import or Update CRL R-->>I: New CreateSession denied I->>S: Revoke role sessions or apply explicit deny S-->>I: Existing credentials denied

CRL은 compromised certificate의 신규 session 발급을 막습니다. 이미 발급된 temporary credential은 만료 전까지 남을 수 있으므로 긴급 대응에는 Role session revoke 또는 aws:TokenIssueTime 기반 explicit deny가 필요합니다. Role session revoke는 같은 Role의 정상 workload도 함께 중단할 수 있어 영향 범위와 복구 절차를 사전에 훈련해야 합니다.

21. Rollout과 rollback은 Access Key 제거까지 포함한다

flowchart LR inventory[1. Inventory keys and workloads] --> canary[2. Issue canary certificate] canary --> dual[3. Run Roles Anywhere beside old key] dual --> batch[4. Migrate in bounded batches] batch --> gate{Refresh, deny and revoke tests pass?} gate -->|no| rollback[Return credential provider to old path] gate -->|yes| disable[5. Disable old access key] disable --> observe[6. Observe one full job cycle] observe --> delete[7. Delete key and close exception]

Rollback은 Trust Anchor 전체를 끄는 작업이 아닙니다. 문제가 생긴 batch의 credential provider만 이전 경로로 되돌리고, 원인이 certificate, helper, policy, network 중 어디인지 분리합니다. Old Access Key는 즉시 삭제하지 않고 비활성화 상태로 한 번의 full workload cycle을 관찰한 뒤 제거합니다.

단, 침해 대응에서는 availability를 위해 old key를 되살리지 않습니다. 별도의 break-glass Role과 단기 승인 절차를 사용하고 모든 사용을 CloudTrail에 남깁니다.

22. 비용은 서비스 요금보다 PKI 운영 경계에서 발생한다

Monthly workload identity cost
  = CA fixed and certificate issuance cost
  + HSM, TPM or secure key storage operations
  + private network path and interface endpoint cost
  + CloudTrail, CloudWatch, EventBridge and log retention
  + certificate inventory, rotation and incident labor
  + test environment and recovery drills

Access Key 방식은 표면적인 발급 비용이 작아 보이지만 rotation ticket, secret distribution, 이미지 재빌드와 유출 조사 비용이 숨어 있습니다. Roles Anywhere 도입안은 AWS 청구서만 비교하지 않고 workload당 certificate 수, renewal 빈도, HSM operation, private endpoint AZ 수와 월 운영 시간을 포함합니다.

초기 budget은 월 예측 대비 실제 비용 오차 15% 이내, certificate 한 장당 수동 작업 0건을 목표로 둡니다. 자동화가 되지 않아 workload 수에 비례해 ticket이 늘어난다면 기술적으로 연결됐어도 운영 모델은 통과하지 못한 것입니다.

25. 아직 production-grade라고 주장하지 않는 범위

  • 이 글의 latency, availability, CRL과 revocation 목표는 실제 fleet에서 측정한 결과가 아닙니다.
  • 실제 enterprise CA, HSM과 IAM Roles Anywhere를 연결한 end-to-end 환경을 배포하지 않았습니다.
  • Host root 침해, TPM 교체와 disaster recovery 상황에서 key와 certificate 복구를 검증하지 않았습니다.
  • Region endpoint 장애와 fleet 전체 동시 재시작이 겹치는 복합 실패를 부하 테스트하지 않았습니다.
  • CRL pipeline의 CA별 발행 주기와 실패 시 escalation을 구현하지 않았습니다.
  • 여러 account와 Region에 Trust Anchor, Profile과 Role을 배포하는 governance를 자동화하지 않았습니다.
  • OIDC workload federation과의 운영 비용을 실제 조직 데이터로 비교하지 않았습니다.

이 범위가 남아 있다면 "Access Key 없이 임시 credential을 발급할 수 있다"고 말할 수는 있지만 "외부 workload identity를 운영한다"고 주장할 수는 없습니다. Certificate inventory, rotation 기록, negative test, revocation drill과 실제 비용을 채워야 운영 결과가 됩니다.

26. 마무리

IAM Roles Anywhere의 핵심은 X.509 certificate를 AWS credential로 바꾸는 기능 자체가 아닙니다. 기존 PKI의 workload identity를 Trust Anchor로 연결하고, Profile과 Role에서 권한을 좁히며, certificate와 STS session의 서로 다른 수명 주기를 운영하는 데 있습니다.

장기 Access Key를 없앤 뒤 남는 질문은 "인증서를 발급했는가"가 아니라 "누가 어떤 certificate로 어느 Role을 받았고, 침해 시 신규 발급과 기존 session을 얼마나 빨리 멈출 수 있는가"입니다.
