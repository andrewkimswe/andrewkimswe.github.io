RAG · Answer Evaluation · LLM-as-a-Judge

[RAG] Hit@k가 높으면 좋은 RAG일까? - Retrieval과 Answer Quality를 따로 평가해본 과정

Retrieval metric이 높아도 최종 답변이 항상 좋은 것은 아니다. 필요한 evidence를 찾았는지와 그 evidence로 좋은 답을 만들었는지를 분리해 평가한 과정을 정리한다.

2026.08.12 RAG Evaluation LLM Judge

CloudOps RAG의 frozen configuration은 작은 held-out set에서 다음 retrieval 결과를 기록했다.

Hit@1 = 7/8
Hit@3 = 8/8
MRR = 0.9375

처음 보면 꽤 좋아 보인다. 그렇다면 최종 답변도 거의 모두 정확해야 할까? 실제 human answer evaluation 결과는 달랐다.

Dimension Score
Correctness 15/22 = 1.36/2
Completeness 13/22 = 1.18/2
Faithfulness 21/22 = 1.91/2
Source Support 18/22 = 1.64/2

좋은 retrieval과 좋은 answer는 같은 문제가 아니다.

1. RAG에는 최소 두 개의 문제가 있다

flowchart TB question[Question] retriever[Retriever] evidence[Evidence] generator[Generator] answer[Answer] question --- retriever retriever --- evidence evidence --- generator generator --- answer
Retrieval Failure
Wrong 또는 missing evidence 때문에 generator가 틀린 근거를 받는다.
Generation Failure
Correct evidence가 있어도 답변이 incomplete하거나 incorrect할 수 있다.

두 문제를 하나의 end-to-end accuracy만으로 측정하면 원인을 알기 어렵다.

2. Retrieval Evaluation의 질문

Retrieval metric이 답하려는 것은 필요한 근거 문서를 찾았는가이다.

  • Hit@k
  • MRR
  • Multi Any-Hit
  • Multi All-Hit
  • threshold accept/reject

하지만 이 metric은 generator가 해당 문서의 내용을 제대로 사용했는지 알려주지 않는다. 그래서 answer evaluation이 별도로 필요하다.

3. Answer Evaluation의 질문

Answer evaluation은 검색된 evidence를 사용해 좋은 답을 만들었는가를 본다.

Dimension 질문
Correctness 질문에 대한 핵심 내용이 사실적으로 맞는가?
Completeness 중요한 요소를 빠뜨리지 않았는가?
Faithfulness 답변이 retrieved context에 근거하는가?
Source Support 제시된 source가 실제 답변을 충분히 뒷받침하는가?

4. Faithfulness와 Correctness는 다르다

어떤 답변은 retrieved context에 매우 충실할 수 있다. 하지만 retrieval 자체가 잘못됐다면 generator는 충실하게 틀린 답을 만들 수 있다.

flowchart TB question[Question] wrong[Wrong Context] faithful[Faithful Generator] bad[Faithfully Wrong Answer] question --- wrong wrong --- faithful faithful --- bad

실제 eval_027에서는 ConfigMap 중심 질문에 Secrets 중심 context가 검색됐다. Generator는 context에서 벗어나지 않았지만 질문이 요구한 ConfigMap 문제를 제대로 해결하지 못했다.

Grounded answer라고 해서 correct answer인 것은 아니다.

5. Expected Document가 없어도 답할 수 있다

반대 사례도 있었다. eval_045에서는 label에 지정된 exact expected document가 Top-k에 없었지만, 다른 Auto Scaling 문서가 필요한 evidence를 충분히 포함하고 있었다.

Document Metric
expected document가 없으므로 miss로 볼 수 있다.
Answer Support
다른 source가 충분한 evidence를 제공했다면 성공일 수 있다.

이 사례는 document relevance와 evidence sufficiency가 다르다는 점을 보여준다.

6. Diagnostic Answer Set

Answer evaluation은 retrieval dataset 전체 50개가 아니라 14개 diagnostic subset에서 수행했다.

14 Questions
11 Generated Answers
3 Fallback Cases

목적은 broad benchmark가 아니라 현재 pipeline에서 answer failure가 어떤 형태로 나타나는지 확인하는 것이었다.

7. Human Review 결과

11개 generated answer에 대해 사람이 직접 correctness, completeness, faithfulness, source support를 검토했다. 특히 completeness가 낮았고, 이는 단순 hallucination보다 다른 문제가 많았다는 의미다.

  • 비교 항목 하나를 누락한다.
  • 필요한 diagnostic step을 빠뜨린다.
  • 여러 evidence 중 일부만 사용한다.
  • 질문의 모든 sub-question에 답하지 않는다.

8. Failure를 원인별로 분류하기

Failure Type Count
Generation-side failure 4
Retrieval + Generation 2
Retrieval failure 1
No material failure 4

Retrieval 문제라면 chunking, embedding, query rewriting, reranking, hybrid retrieval, diversification을 검토할 수 있다. Generation 문제라면 prompt, context formatting, instruction, model, answer planning, citation behavior를 봐야 한다.

9. LLM-as-a-Judge

사람이 모든 answer를 반복 평가하는 것은 비용이 크다. 따라서 evaluator LLM에게 rubric 기반 평가를 맡길 수 있다.

flowchart TB question[Question] context[Retrieved Context] candidate[Candidate Answer] rubric[Rubric] judge[Judge LLM] score[Score] question --- judge context --- judge candidate --- judge rubric --- judge judge --- score 
{
  "correctness": 2,
  "completeness": 1,
  "faithfulness": 2,
  "source_support": 2
}

반복 실험에서 정형화된 score를 만들 수 있다는 것이 장점이지만, Judge도 모델이므로 그대로 믿을 수는 없다.

10. Judge Calibration

CloudOps RAG에서는 Judge 결과를 사람이 직접 평가한 결과와 비교했다. 작은 sample에서 39/44 exact agreement, 44/44 within one point를 기록했다.

이는 judge의 일반적 신뢰성을 증명하는 결과가 아니라, 현재 rubric과 diagnostic set에서 어느 정도 일치하는지 확인한 calibration snapshot이다.

flowchart TB human[Human Evaluation] rubric[Rubric Definition] calibration[Judge Calibration] auto[Automated Repeated Evaluation] audit[Periodic Human Audit] human --- rubric rubric --- calibration calibration --- auto auto --- audit

11. Retrieval과 Generation을 독립적으로 실험하기

RAG generation을 개선할 때 retrieval 결과까지 함께 바뀌면 원인을 알기 어렵다. Retrieval context를 고정하고 prompt 또는 model만 바꾸는 controlled experiment가 필요하다. 

Fixed Retrieval Context
Prompt A: Answer A
Prompt B: Answer B
Model C: Answer C

반대로 retrieval 실험에서는 generator를 거치지 않고 Hit@k, MRR 같은 retrieval metric만 비교할 수 있다.

12. Fallback도 평가 대상이다

CloudOps RAG는 low-confidence query에서 LLM을 호출하지 않는다. 따라서 fallback은 failure exception이 아니라 정상적인 system behavior다. 

Top-1 L2 > threshold
Fallback
Generation skipped

Held-out의 작은 snapshot에서는 8/8 in-scope accepted, 2/2 out-of-scope rejected였다.

정리

CloudOps RAG의 answer evaluation에서 가장 인상적이었던 결과는 faithfulness 1.91/2와 correctness 1.36/2의 차이였다. 이 차이는 RAG 품질을 단순히 hallucination이 적다는 말로 설명할 수 없다는 것을 보여준다.

Retrieval quality와 answer quality는 관련되어 있지만 동일하지 않다. LLM-as-a-Judge 역시 유용한 자동화 도구지만, 먼저 human evaluation과 비교해 현재 rubric에서 어느 정도 믿을 수 있는지 확인해야 한다.
