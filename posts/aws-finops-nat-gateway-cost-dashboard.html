[AWS/FinOps] NAT Gateway 비용은 어디서 발생할까? - CUR, Athena, QuickSight로 비용 대시보드 만들기

AWS Organizations 환경에서 NAT Gateway 비용이 증가했을 때 월말 청구서만 보면 원인을 찾기 어렵다. 비용 데이터를 S3에 저장하고 Athena로 분석한 뒤 QuickSight 대시보드로 연결하는 구조를 정리한다.

2026.08.14 AWS FinOps Athena

AWS를 여러 계정으로 운영하다 보면 월말 청구서의 총액만 확인하는 것으로는 비용 문제를 찾기 어렵다. 예를 들어 AWS Organizations 아래에 여러 계정과 애플리케이션이 있고 NAT Gateway 비용이 예상보다 크게 증가했다고 해보자.

AWS Cost Explorer에서 비용을 확인할 수는 있지만, 운영 조직에서는 조금 더 구체적인 요구가 생길 수 있다.

  • 이번 달 NAT Gateway 비용은 지금까지 얼마인가?
  • 어떤 AWS 계정에서 비용이 많이 발생했는가?
  • 어느 Region에서 비용이 증가했는가?
  • 특정 날짜부터 비용이 급격하게 증가했는가?
  • 이 데이터를 매일 경영진이 볼 수 있는 대시보드로 만들 수 있는가?

이런 경우 AWS의 비용 데이터를 S3에 저장하고 SQL로 분석한 뒤 BI 대시보드로 시각화하는 구조를 만들 수 있다.

flowchart TB org[AWS Organizations] cur[Cost and Usage Report] s3[Amazon S3] glue[AWS Glue Data Catalog] athena[Amazon Athena] qs[Amazon QuickSight] dashboard[FinOps Dashboard] org --- cur cur --- s3 s3 --- glue glue --- athena athena --- qs qs --- dashboard

이번 글에서는 이 구조를 이용해 NAT Gateway 비용을 계정, Region, 날짜별로 분석하는 FinOps 대시보드를 어떻게 설계할 수 있는지 정리한다.

1. Cost Explorer만으로 부족한 경우

AWS Cost Explorer는 AWS 비용을 빠르게 확인하기 좋은 서비스다. 하지만 더 세밀한 비용 분석이나 자체적인 BI 환경이 필요하다면 raw billing data에 직접 접근할 필요가 있다.

예를 들어 다음과 같은 분석을 하고 싶을 수 있다.

Dimension 질문
Account 어떤 계정에서 NAT Gateway 비용이 가장 많이 발생했는가?
Region 어느 Region에서 비용이 증가했는가?
Date 특정 날짜부터 비용 spike가 있었는가?
Usage Type 비용이 고정성 요금인지 데이터 처리 요금인지 구분할 수 있는가?

이런 분석에서는 AWS Cost and Usage Report 계열의 상세 비용 데이터를 queryable dataset으로 만드는 방식이 유용하다.

3. 왜 Athena인가?

S3에 비용 데이터가 있다고 해서 바로 SQL을 실행할 수 있는 것은 아니다. Athena를 사용하면 S3에 저장된 데이터를 대상으로 serverless SQL query를 수행할 수 있다. 별도의 분석용 EC2나 데이터베이스 서버를 계속 운영할 필요가 없다. 

SELECT
    usage_account_id,
    region,
    usage_date,
    SUM(unblended_cost) AS nat_gateway_cost
FROM cost_usage
WHERE
    usage_date >= DATE_TRUNC('month', CURRENT_DATE)
    AND usage_type LIKE '%NatGateway%'
GROUP BY
    usage_account_id,
    region,
    usage_date
ORDER BY
    usage_date,
    nat_gateway_cost DESC;

실제 CUR/CUR 2.0 테이블의 컬럼명과 usage type 표현은 보고서 형식과 Athena 테이블 정의에 따라 달라질 수 있다.

중요한 것은 SQL 문법 자체보다 filter, group, aggregate로 비용을 분석하는 구조다.

4. Month-to-Date 비용 계산

경영진이 자주 요구하는 지표 중 하나가 MTD, 즉 Month-to-Date 비용이다. 예를 들어 9월 17일이라면 9월 1일부터 9월 17일까지의 누적 비용만 계산한다. 

SELECT
    SUM(unblended_cost) AS mtd_nat_gateway_cost
FROM cost_usage
WHERE
    usage_date >= DATE_TRUNC('month', CURRENT_DATE)
    AND usage_date <= CURRENT_DATE
    AND usage_type LIKE '%NatGateway%';

결과는 QuickSight에서 KPI visual로 표현할 수 있다.

이번 달 현재까지 누적된 NAT Gateway 비용
Daily Average
월 누적 비용을 현재까지의 일수로 나눈 평균 비용

5. 계정별 비용 분석

AWS Organizations를 사용한다면 전체 비용만 보는 것보다 어느 계정에서 비용이 발생했는지가 중요하다. 

SELECT
    usage_account_id,
    SUM(unblended_cost) AS nat_gateway_cost
FROM cost_usage
WHERE
    usage_date >= DATE_TRUNC('month', CURRENT_DATE)
    AND usage_type LIKE '%NatGateway%'
GROUP BY
    usage_account_id
ORDER BY
    nat_gateway_cost DESC;

이 결과를 보면 단순히 NAT Gateway 비용이 높다는 말에서 끝나는 것이 아니라 Production 계정이 전체 NAT Gateway 비용의 대부분을 차지한다는 식으로 조사 범위를 좁힐 수 있다.

6. Region별 비용

다음 단계는 Region이다.

SELECT
    region,
    SUM(unblended_cost) AS nat_gateway_cost
FROM cost_usage
WHERE
    usage_date >= DATE_TRUNC('month', CURRENT_DATE)
    AND usage_type LIKE '%NatGateway%'
GROUP BY
    region
ORDER BY
    nat_gateway_cost DESC;

여러 Region을 사용하는 조직이라면 예상하지 못한 Region에서 지속적인 비용이 발생하는지도 확인할 수 있다.

7. NAT Gateway 비용을 하나의 숫자로만 보면 안 되는 이유

NAT Gateway 비용을 분석할 때 중요한 점은 비용이 단순히 NAT Gateway 하나를 만들었기 때문만은 아니라는 것이다. 일반적으로 비용 분석에서는 gateway running-related charge와 data processing-related charge를 구분해서 보는 것이 유용하다.

Gateway Running
NAT Gateway 리소스가 존재하고 동작하는 데서 발생하는 비용
Data Processing
NAT Gateway를 통과하는 데이터 처리량에 따라 증가하는 비용

비용이 증가했다면 NAT Gateway 개수가 늘었는지와 NAT Gateway를 통과하는 데이터가 늘었는지는 서로 다른 문제다. 이 둘을 분리하지 않으면 잘못된 최적화를 할 수 있다.

8. NAT Gateway 비용이 증가하는 흔한 Architecture

예를 들어 private subnet의 EC2가 S3에 접근한다고 해보자.

flowchart TB ec2[Private EC2] nat[NAT Gateway] igw[Internet Gateway] s3[Amazon S3] ec2 --- nat nat --- igw igw --- s3

이 구조에서는 S3와 통신하기 위해 NAT Gateway를 거치는 트래픽이 생길 수 있다. 하지만 S3는 Gateway VPC Endpoint를 사용할 수 있다.

flowchart TB ec2[Private EC2] endpoint[S3 Gateway Endpoint] s3[Amazon S3] ec2 --- endpoint endpoint --- s3

비용 대시보드의 목적은 단순히 숫자를 보여주는 것이 아니라 어떤 계정, Region, workload, network path를 조사해야 하는지 찾는 것이다.

11. QuickSight와 Athena의 역할을 혼동하지 않기

이 구조에서 QuickSight가 S3 파일을 직접 분석하는 것이 핵심은 아니다.

Amazon S3
Raw cost data를 저장한다.
Amazon Athena
SQL query를 수행하는 분석 계층이다.
Amazon QuickSight
BI dashboard를 제공하는 표현 계층이다.

12. DataSync가 아닌 이유

AWS DataSync는 데이터를 이동하기 위한 서비스다. On-premises storage에서 S3로 데이터를 옮기거나 AWS storage 간 대규모 데이터 이동에 사용할 수 있다. 하지만 S3에 있는 비용 데이터를 SQL로 분석한다는 문제를 해결하는 서비스는 아니다.

필요한 것은 data movement가 아니라 query engine이다.

13. CloudWatch Dashboard가 아닌 이유

CloudWatch는 application/infrastructure monitoring에 강하다. CPUUtilization, RequestCount, Latency, ErrorRate, Custom Metrics, Logs 같은 운영 지표를 다루기에 적합하다.

Operational Monitoring
CloudWatch가 자연스럽다.
Cost Analytics / BI
Athena와 QuickSight 조합이 더 자연스럽다.

14. 여러 AWS 계정의 비용을 중앙에서 분석하기

Organizations를 사용하는 환경에서는 중앙 billing data를 기반으로 여러 계정을 분석할 수 있다.

flowchart TB billing[Management / Billing Account] cost[Cost Data] s3[Amazon S3] athena[Athena Dataset] qs[QuickSight] billing --- cost cost --- s3 s3 --- athena athena --- qs

또는 별도의 data collection/analytics account를 두어 비용 분석 workload를 application account와 분리할 수 있다.

15. FinOps Dashboard에서 더 발전시킬 수 있는 것

  • 전월 동일 기간 대비 MTD 비용 비교
  • 비용 증가율 계산
  • Account별 budget 대비 actual cost 비교
  • Daily cost baseline 기반 spike detection
  • Team, Application, Environment, Cost Center tag 기반 분석

비용 allocation tag가 잘 관리된다면 account-level FinOps에서 application-level FinOps로 발전시킬 수 있다.

16. 비용 대시보드만으로 Root Cause를 알 수 있을까?

아니다. CUR 기반 분석은 무엇이, 언제, 어느 계정과 Region에서, 얼마나 비용을 만들었는지 알려주는 데 강하다.

하지만 어떤 EC2가 정확히 어떤 목적지로 몇 GB를 전송했는지 같은 네트워크 원인을 모두 설명해주지는 않는다. 실제 root-cause analysis에서는 VPC Flow Logs, application metrics, infrastructure metadata 같은 추가 데이터가 필요할 수 있다.

17. 비용 최적화도 Architecture 문제다

FinOps를 단순히 돈을 덜 쓰는 활동으로 생각하기 쉽다. 하지만 NAT Gateway 비용을 분석하면 결국 architecture로 돌아온다. VPC Endpoint를 사용할 수 있는지, Cross-AZ traffic이 발생하는지, 불필요한 NAT Gateway가 남아 있는지 조사하게 된다.

따라서 비용 데이터는 architecture decision을 검증하는 또 하나의 operational signal이다.

마치며

AWS 비용 최적화는 월말 청구서를 보고 숫자를 줄이는 작업만은 아니다. 비용 데이터를 지속적으로 수집하고 분석하면 infrastructure가 실제로 어떻게 사용되고 있는지를 관찰할 수 있다.

NAT Gateway를 예로 들면 CUR/Cost Data, S3, Athena, QuickSight라는 단순한 pipeline만으로도 월 누적 비용, 일별 비용 변화, 계정별 비용, Region별 비용, 비용 spike를 분석할 수 있다. 그리고 여기서 발견한 이상 징후는 다시 architecture investigation으로 연결된다.

측정할 수 있어야 개선할 수 있다.
