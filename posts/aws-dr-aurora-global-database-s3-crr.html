[AWS/DR] 글로벌 전자상거래의 데이터 복원력 설계 - Aurora Global Database와 S3 CRR

주문·결제 데이터와 상품 이미지는 같은 복제 전략을 쓰기 어렵습니다. Aurora Global Database와 S3 CRR로 데이터 유형별 DR 경계를 나눕니다.

2026.08.27AWSDRAuroraS3

글로벌 전자상거래 시스템에서는 주문, 결제, 고객 정보와 상품 이미지가 같은 장애 모델을 갖지 않습니다. 트랜잭션 데이터는 정합성과 관계형 모델이 중요하고, 이미지는 대량 객체 저장과 배포 경로가 중요합니다.

flowchart LR tx[주문 결제 고객 정보] --> aurora[Aurora Global Database] obj[상품 이미지 객체] --> s3[S3 Bucket] s3 --> crr[Cross-Region Replication] aurora --> secondary[Aurora Secondary Region] crr --> replica[S3 Replica Bucket]

1. 먼저 데이터 성격을 분리한다

주문과 결제 데이터는 transaction, consistency, join, relational model이 핵심입니다. 반면 상품 이미지는 binary object이고, object 단위 저장과 대량 복제, CDN 연동이 더 중요합니다.

데이터요구사항더 자연스러운 저장소
주문·결제·고객 정보정합성, 트랜잭션, 관계형 조회Aurora
상품 이미지대량 객체, 복제, lifecycle, CDN 연동S3

2. Multi-AZ와 Cross-Region DR은 장애 범위가 다르다

RDS Multi-AZ는 같은 Region 안의 AZ 장애를 다루는 고가용성 기능입니다. 하지만 요구사항이 여러 지리적 위치에서 지속적인 운영이라면 Region 단위 장애와 failover를 별도로 설계해야 합니다.

flowchart TB subgraph regionA[Region A] az1[AZ A Primary] az2[AZ B Standby] end subgraph regionB[Region B] dr[DR Environment] end az1 --> az2 regionA -. Region 장애 고려 .-> regionB

3. Aurora Global Database의 역할

Aurora Global Database는 하나의 primary region과 하나 이상의 secondary region으로 Aurora cluster를 구성합니다. 주된 쓰기는 primary에서 수행하고, secondary는 global read와 cross-region disaster recovery 기반으로 사용됩니다.

flowchart LR app[Global Application] --> primary[Aurora Primary Cluster] primary -->|Cross-Region Replication| secondary[Aurora Secondary Cluster] secondary --> read[Regional Read or DR Promotion]

4. 이미지 데이터는 S3 CRR로 분리한다

상품 이미지 같은 대량 객체를 DB blob에 넣으면 database size, backup, replication, I/O 부담이 커집니다. DB에는 image_key만 저장하고 실제 binary object는 S3에 두는 편이 자연스럽습니다.

flowchart LR product[Product Table] --> key[image_key] key --> bucket[S3 Primary Bucket] bucket -->|CRR| replica[S3 Replica Bucket]

5. DynamoDB Global Tables가 항상 답은 아니다

DynamoDB Global Tables는 강력한 글로벌 NoSQL 기능이지만, 핵심 데이터가 관계형 트랜잭션 중심이라면 데이터 모델 자체를 바꿔야 합니다. 4MB가 넘는 이미지를 DynamoDB item으로 직접 저장하는 것도 적합하지 않습니다.

Relational Transaction -> Aurora Global Database
Large Object -> S3 + Cross-Region Replication

6. EFS가 아니라 S3를 선택하는 이유

EFS는 Linux workload에서 공유 POSIX filesystem이 필요할 때 좋은 선택입니다. 하지만 상품 이미지처럼 대량의 durable object를 저장하고 replication, lifecycle, CDN 연동까지 고려한다면 S3가 더 직접적인 선택입니다.

7. RPO와 RTO까지 같이 봐야 한다

Aurora Global Database와 S3 CRR은 장애 시점에 처음 데이터를 복사하는 구조가 아니라, cross-region copy를 미리 유지하는 구조입니다. 이 덕분에 더 낮은 RPO와 RTO를 목표로 설계하기 쉽습니다.

데이터 replication은 DR의 핵심 구성 요소지만, compute, networking, DNS, secrets, deployment, monitoring, failover procedure까지 있어야 전체 DR 전략이 됩니다.

8. 전체 구조

flowchart TB user[Global Users] --> dns[Route 53 or Global Routing] dns --> appA[Application Region A] dns -. failover .-> appB[Application Region B] appA --> auroraA[Aurora Primary] appA --> s3A[S3 Primary] auroraA --> auroraB[Aurora Secondary] s3A --> s3B[S3 Replica] appB --> auroraB appB --> s3B

9. SAA에서 빠르게 판단하는 기준

문제에 relational transaction과 global 또는 multi-region 요구사항이 함께 나오면 Aurora Global Database를 먼저 떠올릴 수 있습니다. large image나 object와 cross-region 복제가 함께 나오면 S3 CRR이 자연스럽습니다.

마무리

글로벌 복원력 설계의 핵심은 모든 데이터를 한 서비스에 몰아넣는 것이 아닙니다. 데이터 모델을 분리하고, 각 계층에 맞는 replication mechanism을 선택하는 것입니다.
