LLM · Architecture · Orchestration

[LLM] API 호출부터 LangChain까지 - LLM 애플리케이션의 구조 이해하기

LLM을 애플리케이션에 붙인다는 것은 단순히 모델 API를 한 번 호출하는 일이 아니다. 모델을 실행하는 serving layer와, 그 결과를 서비스 흐름으로 조합하는 orchestration layer를 나누어 정리한다.

2026.08.08 LLM LangChain Architecture

LLM을 애플리케이션에 적용한다고 하면 가장 먼저 떠올릴 수 있는 코드는 단순하다.

response = model.invoke("What is RAG?")

하지만 실제 서비스에서 이 한 줄 뒤에는 모델을 실행하기 위한 추론 인프라가 존재하고, 앞에는 프롬프트 구성이나 출력 처리, 여러 단계의 호출을 연결하기 위한 애플리케이션 로직이 존재한다.

즉 실제 LLM 애플리케이션은 단순히 하나의 모델을 호출하는 것보다 넓은 구조를 가진다.

flowchart TB app[Application] orchestration[LLM Orchestration] endpoint[Model API Endpoint] serving[LLM Serving Infrastructure] gpu[GPU / Model] app --- orchestration orchestration --- endpoint endpoint --- serving serving --- gpu

이 글에서는 로컬 환경에서 LLM을 실행하는 것부터 Hosted Endpoint를 사용하는 이유, 그리고 LangChain을 이용해 여러 처리 단계를 하나의 파이프라인으로 구성하는 과정까지 정리한다.

1. LLM을 로컬에서 실행한다는 것

일반적인 프로그램과 달리 대규모 언어 모델을 실행하려면 상당한 컴퓨팅 자원이 필요하다. 모델의 파라미터가 증가하면 model weight를 메모리에 올리는 데 필요한 RAM 또는 VRAM도 증가한다.

Memory
모델 weight와 실행 상태를 올릴 RAM 또는 VRAM이 필요하다.
Compute
토큰을 생성하는 동안 충분한 연산 자원이 필요하다.
Cost
모델 크기와 처리량이 커질수록 추론 비용이 증가한다.
flowchart TB app[Application] local[Local Model] gpu[GPU] app --- local local --- gpu

충분한 GPU가 있다면 직접 모델을 실행할 수 있다. 하지만 CPU나 일반 소비자용 GPU 환경에서는 큰 모델을 그대로 실행하기 어려울 수 있다. 이 경우 작은 모델을 선택하거나 quantization 등을 통해 모델의 자원 요구량을 줄여야 한다.

2. Hosted LLM Endpoint

모델을 직접 실행하는 대신 외부 인프라에서 실행 중인 모델에 API 요청을 보낼 수 있다. OpenAI API나 NVIDIA가 제공하는 모델 API 등이 대표적인 예다.

flowchart TB client[Client] endpoint[LLM API Endpoint] inference[Inference Infrastructure] model[Model] gpu[GPU] client --- endpoint endpoint --- inference inference --- model model --- gpu

개발자는 모델을 직접 GPU에 배포하지 않고도 API를 통해 inference 결과를 받을 수 있다.

response = requests.post(
    endpoint,
    headers=headers,
    json={
        "messages": [
            {
                "role": "user",
                "content": "Explain RAG"
            }
        ]
    }
)

복잡한 모델 실행 과정이 API 뒤로 숨겨진 것이다.

3. Endpoint 뒤에서는 무엇이 일어날까?

API를 호출한다고 해서 단순히 하나의 모델 프로세스에 요청이 전달되는 것만을 의미하지 않는다. 대규모 LLM 서비스에서는 여러 사용자의 요청을 안정적으로 처리해야 한다.

flowchart TB users[Users] endpoint[API Endpoint] auth[Authentication] routing[Request Routing] serving[Inference Serving] modelA[Model Instance A] modelB[Model Instance B] modelC[Model Instance C] gpuA[GPU] gpuB[GPU] gpuC[GPU] users --- endpoint endpoint --- auth auth --- routing routing --- serving serving --- modelA serving --- modelB serving --- modelC modelA --- gpuA modelB --- gpuB modelC --- gpuC

이 계층에서는 서비스에 따라 인증, 요청 라우팅, 요청 스케줄링, 스트리밍, 모델 인스턴스 관리 등의 기능이 수행될 수 있다. 우리가 사용하는 model.invoke(...) 같은 간단한 호출 뒤에는 별도의 LLM Serving Infrastructure가 존재한다.

4. Hosted API를 사용하는 이유

Hosted Endpoint의 가장 큰 장점은 모델 인프라를 직접 운영하지 않아도 된다는 것이다. 개발자는 GPU provisioning, model deployment, inference server, scaling을 처음부터 직접 구축하지 않고 애플리케이션 개발에 집중할 수 있다.

기준 Hosted Endpoint Self-hosted
초기 구축 간단 복잡
GPU 관리 Provider 중심 직접 관리
Scaling Provider 기능 활용 직접 설계
모델 제어 상대적으로 제한 높음
데이터 통제 Provider 정책 고려 높음
운영 부담 낮음 높음

직접 운영하면 모델 선택 및 수정, 데이터 통제, 인프라 구성 등에 더 많은 자유를 얻을 수 있다. Hosted API와 Self-hosting은 어느 하나가 항상 우월하다기보다 요구사항에 따라 선택할 문제다.

5. 실제 LLM 애플리케이션은 모델 호출 하나로 끝나지 않는다

가장 단순한 LLM 애플리케이션은 입력을 받아 모델에 전달하고 출력하는 구조다.

flowchart TB input[Input] llm[LLM] output[Output] input --- llm llm --- output

하지만 실제 서비스에서는 모델에 사용자의 입력을 그대로 전달하는 경우보다 그 전후에 여러 로직이 추가되는 경우가 많다.

flowchart TB user[User Input] prompt[Prompt Template] llm[LLM] parser[Output Parser] app[Application] user --- prompt prompt --- llm llm --- parser parser --- app

이제 문제는 모델 자체가 아니라 여러 처리 단계를 어떻게 구성할 것인가로 확장된다. 여기서 LangChain 같은 orchestration framework가 등장한다.

6. LangChain은 LLM을 실행하는 서비스가 아니다

처음 LangChain을 접하면 LangChain 자체가 모델을 실행한다고 오해하기 쉽다. 하지만 LangChain의 주요 역할은 GPU infrastructure를 제공하는 것이 아니라, LLM을 포함한 여러 구성 요소를 애플리케이션에서 연결하고 조합하기 위한 abstraction을 제공하는 것이다.

flowchart TB app[Application] langchain[LangChain] endpoint[Model Endpoint] serving[Inference Infrastructure] gpu[GPU] app --- langchain langchain --- endpoint endpoint --- serving serving --- gpu

LLM Serving과 LLM Orchestration은 서로 다른 문제를 해결한다.

7. Prompt, LLM, Parser

가장 단순한 LLM pipeline을 생각해보자.

flowchart TB input[Input] prompt[Prompt Template] llm[LLM] parser[Output Parser] input --- prompt prompt --- llm llm --- parser

Prompt Template은 입력 데이터를 실제 모델에 전달할 prompt로 변환한다. 예를 들어 {"topic": "Amazon S3"} 같은 입력을 다음 prompt로 바꿀 수 있다. 

Explain Amazon S3 to a beginner.
Keep the explanation under five sentences.

그 결과를 LLM에 전달하고, 모델의 응답을 다시 Output Parser로 처리한다.

8. LangChain의 Runnable

LangChain에서는 이러한 실행 가능한 구성 요소들을 Runnable이라는 공통 인터페이스로 다룰 수 있다. LangChain Expression Language에서는 다음처럼 표현할 수 있다. 

chain = prompt | model | parser

이제 애플리케이션은 각각을 따로 호출할 필요 없이 전체 pipeline을 하나의 실행 가능한 구성 요소로 사용할 수 있다.

result = chain.invoke({
    "topic": "Amazon S3"
})
Prompt
입력을 모델이 이해할 수 있는 지시문으로 변환한다.
Model
텍스트를 생성하거나 중간 판단 결과를 만든다.
Parser
모델 응답을 애플리케이션이 다룰 수 있는 형태로 변환한다.

9. 왜 굳이 Chain으로 만드는가?

단순한 모델 호출 하나만 있다면 response = model.invoke(prompt)만으로 충분할 수 있다. LangChain 같은 abstraction의 장점은 처리 단계가 증가하면서 나타난다.

flowchart TB user[User] classifier[Classifier] technical[Technical Chain] billing[Billing Chain] general[General Chain] response[Response] user --- classifier classifier --- technical classifier --- billing classifier --- general technical --- response billing --- response general --- response

Classifier 역시 LLM일 수 있다. 또는 중간에 일반 Python 함수를 넣을 수도 있다. 이처럼 LLM은 애플리케이션의 하나의 component가 된다.

10. Internal Processing과 User Response를 분리할 수 있다

모델이 생성하는 모든 결과를 사용자에게 직접 보여줄 필요는 없다. 첫 번째 모델 호출은 사용자의 질문을 분류하는 데만 사용할 수 있고, 그 결과는 다음 chain을 선택하는 내부 판단값이 될 수 있다. 

{
  "category": "cloud"
}
flowchart TB classifier[Classifier] category["category = cloud"] chain[Cloud Expert Chain] response[User Response] classifier --- category category --- chain chain --- response

즉 LLM의 출력은 항상 최종 자연어 응답일 필요가 없다. 다른 프로그램이 소비하는 중간 결과가 될 수도 있다. 이 관점은 복잡한 LLM 애플리케이션을 설계할 때 중요하다.

11. Streaming

LLM은 전체 응답을 생성한 뒤 한 번에 반환할 수도 있지만, 생성되는 token을 순차적으로 전달할 수도 있다. 실제 모델의 총 처리 시간이 같더라도 사용자가 첫 번째 결과를 보기까지의 시간을 줄일 수 있기 때문에 UX 측면에서 중요하다.

flowchart TB request[Request] tokenA[Token] tokenB[Token] tokenC[Token] response[Response] request --- tokenA tokenA --- tokenB tokenB --- tokenC tokenC --- response 
for chunk in chain.stream(input):
    print(chunk)

12. Orchestration은 모델의 능력을 애플리케이션으로 확장한다

LLM 자체는 기본적으로 입력을 받아 출력을 생성한다. 하지만 실제 애플리케이션에서는 모델 주변에 여러 기능을 구성할 수 있다.

flowchart TB user[User] router[Router] llm[LLM] fn[Function] chain[Another Chain] parser[Parser] final[User Response] user --- router router --- llm router --- fn router --- chain chain --- parser llm --- final fn --- final parser --- final

이를 통해 하나의 모델에게 모든 역할을 맡기는 대신 다음 요소를 각각의 단계로 분리할 수 있다.

  • Prompt 구성
  • 분류
  • Routing
  • 데이터 변환
  • 여러 모델 호출
  • Python 함수 실행
  • Output parsing

13. LangChain은 Serving Layer가 아니다

전체 구조를 다시 보면 각 기술의 역할이 명확해진다.

flowchart TB app[Application
Prompt / Router / Parser] langchain[LangChain] endpoint[Model API Endpoint
Authentication / Routing / Serving] compute[Compute Infrastructure
GPU + Model Weights] app --- langchain langchain --- endpoint endpoint --- compute
Application / Orchestration
LangChain, prompt, parser, routing, application logic을 다룬다.
Model Serving
API endpoint, authentication, request routing, inference server를 다룬다.
Compute
GPU와 model weights가 위치하는 계층이다.

14. Gradio와 LangServe는 어디에 들어갈까?

LLM pipeline을 만들었다면 이를 실제 사용자가 이용할 수 있는 형태로 노출해야 한다. Gradio는 빠르게 사용자 인터페이스를 구성하는 데 사용할 수 있고, LangServe는 LangChain Runnable을 API 형태로 노출하는 데 사용할 수 있다.

flowchart TB user[User] gradio[Gradio UI] client[Client] langserve[LangServe
HTTP API] runnable[LangChain Runnable] endpoint[LLM Endpoint] user --- gradio client --- langserve gradio --- runnable langserve --- runnable runnable --- endpoint

즉 모델을 호출하는 코드를 작성하는 것에서 끝나는 것이 아니라 Model, Chain, API, Application으로 발전시킬 수 있다.

15. 전체 구조

지금까지의 내용을 하나의 구조로 합치면 다음과 같다.

flowchart TB user[User] ui[UI / Client
Gradio] langserve[LangServe
REST API] langchain[LangChain
Prompt / Router / LLM / Parser] endpoint[Hosted LLM Endpoint] inference[Inference Infrastructure
Model + GPU] user --- ui ui --- langserve langserve --- langchain langchain --- endpoint endpoint --- inference

단순히 LLM API를 호출한다고 생각했던 구조가 실제로는 여러 계층으로 나뉘어 있다는 것을 볼 수 있다.

16. 정리

LLM 애플리케이션을 처음 만들 때는 보통 Prompt, LLM, Response로 시작한다. 하지만 서비스가 복잡해질수록 prompt 구성, classification, routing, function 실행, parsing, streaming 같은 여러 단계가 필요해진다.

Hosted Endpoint
모델 실행 인프라를 추상화한다.
LangChain
LLM 애플리케이션의 처리 단계를 연결하고 orchestration한다.
Gradio
사용자 인터페이스를 빠르게 만든다.
LangServe
Chain을 API로 제공한다.

결국 중요한 것은 LLM 자체와 LLM을 사용하는 애플리케이션을 구분하는 것이다. 모델은 입력을 받아 출력을 생성하지만, 실제 서비스에서는 그 주변에 인증, 프롬프트 구성, routing, parsing, streaming, API serving 등의 구성 요소가 필요하다.

LLM 애플리케이션을 설계한다는 것은 단순히 좋은 모델을 선택하는 것에서 끝나지 않는다. 모델을 어떤 인프라에서 실행하고, 어떤 인터페이스로 호출하며, 여러 처리 단계를 어떻게 조합해 하나의 서비스로 만들 것인지 설계하는 것까지 포함한다.
