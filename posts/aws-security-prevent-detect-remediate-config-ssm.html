[AWS/Security] 보안 정책은 탐지만 해서는 부족하다 - IAM, AWS Config, Systems Manager로 Prevent·Detect·Remediate 만들기

보안 정책은 탐지만으로 끝나지 않습니다. IAM으로 예방하고, AWS Config로 평가하고, Systems Manager로 안전하게 복구하는 운영 loop를 설계합니다.

2026.08.28AWSSecurityConfigSSM

클라우드 보안 정책은 탐지만으로 끝나지 않습니다. 실제 운영에서는 위반을 줄이고, 현재 상태를 평가하고, 안전한 범위에서 복구하는 loop가 필요합니다.

flowchart LR prevent[Prevent] --> detect[Detect] detect --> remediate[Remediate] remediate --> verify[Verify] verify --> detect

1. 예시: 모든 EBS 볼륨은 암호화되어야 한다

문서에 정책을 적어두는 것만으로는 부족합니다. 누군가 실수로 암호화 옵션을 끈 채 볼륨을 만들 수도 있고, 예외 계정이나 과거 리소스가 이미 남아 있을 수도 있습니다.

2. Prevent: IAM으로 잘못된 생성을 줄인다

가장 좋은 보안 위반은 애초에 발생하지 않는 위반입니다. IAM policy나 Organizations 환경의 guardrail을 통해 허용되지 않은 리소스 생성을 제한할 수 있습니다.

flowchart TB actor[User or Role] --> iam[IAM Policy] iam --> allowed[Encrypted EBS Allowed] iam -. deny .-> blocked[Unencrypted EBS Denied]

3. IAM만으로 충분하지 않은 이유

IAM은 앞으로의 행동을 제한하지만 현재 존재하는 리소스 상태를 모두 설명하지는 못합니다. 기존 리소스, 다른 자동화 경로, 정책 변경, 예외 계정 때문에 non-compliant resource는 여전히 존재할 수 있습니다.

4. Detect: AWS Config로 현재 상태를 평가한다

AWS Config는 resource configuration을 기록하고 rule을 통해 compliance 상태를 평가합니다. EBS 볼륨이 암호화되어 있는지 같은 configuration compliance 문제에는 Config가 직접적인 도구입니다.

flowchart TB ebs[EBS Volume] --> config[AWS Config Rule] config --> compliant[COMPLIANT] config --> non[NON_COMPLIANT]

5. CloudTrail, EventBridge, Config를 구분한다

서비스답하는 질문
CloudTrail누가 어떤 API를 호출했는가?
EventBridge어떤 이벤트가 발생했는가?
AWS Config현재 리소스 구성이 정책을 준수하는가?

6. Remediate: Systems Manager Automation으로 반복 작업을 줄인다

위반 리소스가 발견되면 사람이 매번 ticket을 보고 수정할 수도 있습니다. 하지만 정책이 명확하고 조치가 안전하다면 Systems Manager Automation runbook으로 remediation을 연결할 수 있습니다.

flowchart TB config[AWS Config] --> non[NON_COMPLIANT] non --> ssm[SSM Automation Runbook] ssm --> action[Remediation Action] action --> config

7. EventBridge와 Lambda만으로 직접 만들 수도 있다

CreateVolume event를 EventBridge로 받고 Lambda에서 encryption check와 remediation을 수행하는 구조도 가능합니다. 하지만 이 경우 event pattern, state tracking, compliance history, retry, evaluation logic을 직접 만들어야 합니다.

요구사항이 지속적인 compliance evaluation이라면 AWS Config가 더 직접적입니다. EventBridge와 Lambda는 특정 event reaction에 더 가깝습니다.

8. Macie나 Inspector가 아닌 이유

Macie는 주로 S3 민감 데이터 탐지에 강하고, Inspector는 EC2, container image, Lambda의 취약점과 노출 평가가 중심입니다. EBS 암호화 여부 같은 configuration compliance에는 AWS Config가 더 맞습니다.

9. 자동 Remediation의 안전장치

자동화를 무조건 적용하면 안 됩니다. destructive action은 더 큰 장애를 만들 수 있으므로 idempotency, blast radius, rollback, approval, logging, failure handling을 함께 설계해야 합니다.

flowchart LR detect[Detect] --> notify[Notify] notify --> approval[Human Approval] approval --> remediate[Remediate] remediate --> log[Log and Verify]

10. Organizations 환경으로 확장하기

계정이 여러 개라면 account 단위 정책이 아니라 organization-wide guardrail, centralized compliance, automated remediation 관점으로 확장해야 합니다.

11. SAA에서 빠르게 판단하는 기준

Block creation -> IAM or SCP
Check compliance -> AWS Config
Fix violation -> Systems Manager Automation or Lambda

마무리

보안은 alert를 많이 만드는 일이 아닙니다. Policy, enforcement, verification, remediation이 하나의 반복 가능한 운영 체계로 이어질 때 실제 governance에 가까워집니다.
