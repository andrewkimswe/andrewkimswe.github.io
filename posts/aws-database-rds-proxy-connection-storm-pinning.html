서버리스 API에 트래픽이 몰렸을 때 Lambda 동시 실행 수는 빠르게 증가합니다. 그런데 데이터베이스는 같은 속도로 연결 수를 늘릴 수 없습니다. API Gateway와 Lambda는 정상인데 RDS에서 Too many connections, 연결 시간 초과와 메모리 압박이 먼저 발생하는 이유입니다.

이 글은 실제 프로덕션 장애 회고가 아니라, Lambda와 RDS for MySQL 사이의 connection storm을 통제 가능한 시스템으로 바꾸기 위한 설계와 검증 계획입니다. 아래의 숫자는 실측 결과가 아니라 초기 acceptance target입니다. 실제 환경에서 부하 테스트를 수행한 뒤 결과 열을 채우기 전까지 성능 개선을 달성했다고 주장하지 않습니다.

1. 장애를 Lambda 문제가 아니라 연결 예산 초과로 정의한다

요청 하나가 실행 환경 하나와 데이터베이스 연결 하나를 요구한다고 가정하면, Lambda의 확장은 곧 연결 수의 급증이 됩니다. 평소 30개의 실행 환경을 사용하던 API가 행사 시작과 함께 500개로 늘어나면 애플리케이션 컴퓨팅은 확장되지만 DB의 max_connections와 연결 생성 CPU 비용은 그대로입니다.

flowchart LR clients[Traffic burst] --> api[API Gateway] api --> lambda[Lambda concurrency
30 to 500] lambda -->|new connection per environment| rds[(RDS MySQL)] rds --> limit{Connection budget} limit -->|exceeded| errors[Timeouts and
connection errors]

관찰되는 증상은 비슷해도 원인은 네 가지로 나뉩니다.

원인관찰 신호잘못된 대응
연결 수 한도DB DatabaseConnections가 상한에 근접Lambda timeout만 증가
연결 생성 비용짧은 요청에서도 DB CPU와 connect latency 증가쿼리 튜닝만 수행
긴 트랜잭션연결이 반환되지 않고 borrow latency 증가Proxy pool 크기만 확대

핵심 지표는 Lambda 동시 실행 수 자체가 아니라 DB가 감당할 수 있는 연결 예산과 한 연결이 점유되는 시간입니다.

2. 연결 수를 계산하지 않으면 작은 pool도 장애를 만든다

컨테이너나 EC2에서는 프로세스 하나의 connection pool이 작아 보여도 전체 합계가 문제가 됩니다. Lambda에서는 실행 환경마다 독립적인 연결이나 작은 pool이 만들어질 수 있어 더 쉽게 증폭됩니다.

Direct connection upper bound
  = active execution environments
  x connections per environment
  x database users or tenant-specific pools

Example
  500 environments x 1 connection = 500 client connections
  100 ECS tasks x pool size 10 = 1,000 client connections

애플리케이션 pool을 10에서 5로 줄이는 것은 도움이 되지만, task 수가 20배 늘면 합계는 다시 한도를 넘습니다. 따라서 계산에는 인스턴스 하나의 pool 크기가 아니라 최대 replica 수, Lambda reserved concurrency, 배치 worker와 운영자 연결까지 포함해야 합니다.

DB 연결 한도 전체를 애플리케이션에 주지도 않습니다. 장애조사, migration, monitoring, failover 후 재연결을 위한 headroom을 남겨야 합니다. 이 글의 초기 정책은 RDS Proxy가 사용할 수 있는 DB 연결을 max_connections의 70%로 제한하고, 나머지를 운영과 예외 workload에 남기는 것입니다. 70%는 보편적인 정답이 아니라 부하 테스트를 시작하기 위한 값입니다.

3. 네 가지 선택지를 비교하고 Proxy의 책임을 제한한다

선택지장점한계선택 조건
DB instance 확장코드 변경이 거의 없고 즉시 한도 증가연결 폭증 원인은 남고 비용이 계속 증가CPU·메모리·쿼리 처리량도 함께 부족할 때
애플리케이션 pool추가 서비스 비용이 없음Lambda·다수 replica에서는 pool이 분산되어 합계가 증가고정된 소수의 장기 실행 프로세스
RDS Proxy관리형 pooling, multiplexing, 연결 제한과 failover 추상화추가 비용, latency, pinning과 엔진 제약짧고 독립적인 트랜잭션이 많은 burst workload
데이터 계층 재설계HTTP 기반 데이터 API나 비관계형 저장소로 연결 문제 제거 가능가장 큰 코드·데이터 모델 변경장기적인 재설계가 이미 필요한 경우

여기서는 Lambda가 짧은 트랜잭션으로 MySQL에 접근하며, 갑작스러운 연결 증가가 주된 병목이라는 조건에서 RDS Proxy를 선택합니다. Proxy는 느린 SQL을 빠르게 만들지 않고, lock contention이나 잘못된 index도 해결하지 않습니다. 책임은 연결 생성·재사용·DB 보호·failover 연결 처리로 한정합니다.

4. Pooling과 multiplexing은 같은 말이 아니다

RDS Proxy에는 Client에서 Proxy로 향하는 연결과 Proxy에서 DB로 향하는 연결이 따로 존재합니다. Proxy는 DB 연결을 pool에 보관하고, transaction이 끝났을 때 안전하다면 다른 Client transaction에 재사용합니다. 이 transaction 단위 재사용이 multiplexing입니다.

flowchart LR subgraph clients[Client connections] l1[Lambda 1] l2[Lambda 2] l3[Lambda 3] ln[Lambda N] end subgraph proxy[RDS Proxy] queue[Borrow queue] pool[Connection pool] end subgraph database[RDS MySQL] d1[DB connection 1] d2[DB connection 2] dm[DB connection M] end l1 --> queue l2 --> queue l3 --> queue ln --> queue queue --> pool pool --> d1 pool --> d2 pool --> dm

N개의 Client 연결이 반드시 N개의 DB 연결을 뜻하지 않는 것이 Proxy의 가치입니다. 하지만 transaction이 오래 지속되거나 session 상태에 의존하면 한 Client가 한 DB 연결을 계속 점유합니다. 이때는 연결 수를 줄이지 못한 채 Proxy 비용과 hop만 추가될 수 있습니다.

5. 네트워크 경계는 Lambda, Proxy, DB 세 단계로 나눈다

Proxy는 데이터베이스와 같은 VPC에 배치하고 여러 가용 영역의 private subnet을 사용합니다. 보안 그룹은 애플리케이션이 DB endpoint로 직접 우회하지 못하도록 단계별로 연결합니다.

flowchart LR lambda[Lambda SG] -->|TCP 3306| proxy[RDS Proxy SG] proxy -->|TCP 3306| db[RDS DB SG] lambda -. blocked .-> db secret[Secrets Manager] --> proxy metrics[CloudWatch] --- proxy
  • Proxy SG의 inbound는 Lambda SG만 source로 허용합니다.
  • DB SG의 inbound는 Proxy SG만 허용합니다.
  • Canary 기간에는 별도 direct-test SG 규칙을 잠시 유지하고 종료일을 기록합니다.
  • 함수와 Proxy subnet의 IP 여유를 배포 전에 확인합니다.
  • 인터넷 egress가 필요하지 않다면 Secrets Manager와 CloudWatch 접근 경로도 VPC endpoint 또는 조직의 승인된 egress로 통제합니다.

RDS Proxy를 사용하면서 Lambda SG에서 DB SG로 직접 접근을 계속 허용하면 일부 함수가 환경 변수나 배포 drift 때문에 Proxy를 우회할 수 있습니다. 관측 지표가 좋아 보여도 전체 workload가 Proxy를 사용한다는 보장이 없어집니다.

6. Secrets Manager와 IAM 인증의 역할을 분리한다

Proxy가 DB에 연결할 때는 Secrets Manager의 database credential을 사용할 수 있습니다. Client에서 Proxy까지는 password 인증 또는 IAM database authentication을 선택할 수 있습니다. 여기서는 Lambda에 장기 password를 전달하지 않기 위해 Client-to-Proxy IAM 인증을 요구합니다.

sequenceDiagram participant L as Lambda participant IAM as IAM/RDS Auth participant P as RDS Proxy participant S as Secrets Manager participant D as RDS MySQL L->>IAM: Generate short-lived auth token L->>P: Connect with TLS and token P->>S: Read approved DB secret P->>D: Borrow or create DB connection D-->>L: Transaction result through Proxy

Lambda execution role에는 모든 database user가 아니라 특정 Proxy resource ID와 DB user에 대한 rds-db:connect만 부여합니다. Proxy service role에는 승인된 Secret의 secretsmanager:GetSecretValue와 필요한 KMS decrypt 권한만 부여합니다. Secret rotation을 활성화했다면 Proxy와 DB 양쪽에서 새 credential이 정상화되는지를 별도 canary query로 확인합니다.

7. CloudFormation으로 연결 상한과 borrow timeout을 코드화한다

다음은 핵심 리소스만 남긴 예시입니다. 실제 stack에는 subnet, security group, DB resource와 KMS 조건을 조직 표준에 맞게 연결해야 합니다.

Resources:
  ProxyRole:
    Type: AWS::IAM::Role
    Properties:
      AssumeRolePolicyDocument:
        Version: "2012-10-17"
        Statement:
          - Effect: Allow
            Principal:
              Service: rds.amazonaws.com
            Action: sts:AssumeRole
      Policies:
        - PolicyName: ReadDatabaseSecret
          PolicyDocument:
            Version: "2012-10-17"
            Statement:
              - Effect: Allow
                Action: secretsmanager:GetSecretValue
                Resource: !Ref DbSecretArn

  OrderApiProxy:
    Type: AWS::RDS::DBProxy
    Properties:
      DBProxyName: order-api-proxy
      EngineFamily: MYSQL
      RequireTLS: true
      RoleArn: !GetAtt ProxyRole.Arn
      VpcSubnetIds: !Ref PrivateSubnetIds
      VpcSecurityGroupIds:
        - !Ref ProxySecurityGroup
      Auth:
        - AuthScheme: SECRETS
          SecretArn: !Ref DbSecretArn
          IAMAuth: REQUIRED

  ProxyTargetGroup:
    Type: AWS::RDS::DBProxyTargetGroup
    Properties:
      DBProxyName: !Ref OrderApiProxy
      TargetGroupName: default
      DBInstanceIdentifiers:
        - !Ref DbInstanceIdentifier
      ConnectionPoolConfigurationInfo:
        MaxConnectionsPercent: 70
        MaxIdleConnectionsPercent: 35
        ConnectionBorrowTimeout: 5

MaxConnectionsPercent는 DB의 max_connections 대비 Proxy가 만들 수 있는 연결 비율입니다. ConnectionBorrowTimeout을 무작정 늘리면 error는 줄어 보여도 사용자 요청이 queue에서 오래 기다릴 수 있습니다. API latency budget보다 작은 값에서 시작하고, 연결 대기가 정상 처리로 회복될 수 있는 범위인지 부하 테스트로 결정합니다.

8. Lambda도 Client 연결을 재사용하고 timeout을 짧게 둔다

Proxy가 있다고 매 invocation마다 Client 연결을 새로 만들 이유는 없습니다. Lambda execution environment가 재사용되는 동안 연결을 보관하되, 끊어진 연결은 짧은 timeout으로 다시 생성합니다.

import os
import boto3
import pymysql

DB_HOST = os.environ["DB_PROXY_ENDPOINT"]
DB_USER = os.environ["DB_USER"]
DB_NAME = os.environ["DB_NAME"]
DB_PORT = 3306

rds = boto3.client("rds")
connection = None


def get_connection():
    global connection

    if connection is not None:
        try:
            connection.ping(reconnect=False)
            return connection
        except Exception:
            connection = None

    token = rds.generate_db_auth_token(
        DBHostname=DB_HOST,
        Port=DB_PORT,
        DBUsername=DB_USER,
    )
    connection = pymysql.connect(
        host=DB_HOST,
        user=DB_USER,
        password=token,
        database=DB_NAME,
        port=DB_PORT,
        connect_timeout=2,
        read_timeout=2,
        write_timeout=2,
        ssl={"ca": "/opt/rds-ca.pem"},
        autocommit=False,
    )
    return connection


def handler(event, context):
    global connection
    conn = get_connection()
    try:
        with conn.cursor() as cursor:
            cursor.execute(
                "SELECT status FROM orders WHERE order_id = %s",
                (event["order_id"],),
            )
            row = cursor.fetchone()
        conn.commit()
        return {"status": row[0] if row else "NOT_FOUND"}
    except Exception:
        conn.rollback()
        connection = None
        raise

/opt/rds-ca.pem은 Lambda Layer 또는 container image에 현재 RDS CA bundle을 포함했다는 전제의 경로입니다. Lambda execution role에는 대상 Proxy DB user로 접속할 수 있는 rds-db:connect 권한도 필요합니다. 인증서 검증이나 IAM 권한을 생략해 연결 문제를 우회하지 않습니다.

이 예시의 timeout 값 역시 초기값입니다. 무조건 재시도하지 않고 authentication error, connection exhaustion, transient failover를 분류해야 합니다. 사용자 요청 안에서의 재시도는 1회처럼 작게 제한하고, 전체 latency budget을 넘기기 전에 실패를 반환합니다.

9. 처음 실패하기 쉬운 접근은 작은 pool을 각 함수에 두는 것이다

처음에는 함수 내부에 pool을 만들면 연결 문제가 해결될 것처럼 보입니다. 하지만 Lambda execution environment가 500개 생성되고 각 환경이 하나의 idle connection만 보관해도 DB에는 500개가 남습니다. pool이 로컬에서는 효율적이어도 전체 시스템에서는 분산된 연결 재고가 됩니다.

두 번째 실패는 DB instance class와 max_connections만 늘리는 것입니다. connection storm의 임계점은 늦출 수 있지만, 행사 규모가 다시 증가하면 같은 형태로 재발합니다. CPU와 memory headroom이 실제 query workload에도 부족하다면 instance 확장이 필요하지만, 연결 생성만 문제라면 비용 대비 효과를 따로 측정해야 합니다.

세 번째 실패는 Proxy 도입 후 direct endpoint를 영구적으로 열어두는 것입니다. 일부 서비스가 direct endpoint를 사용하면 Proxy 지표와 DB 지표가 어긋나고 장애 원인 추적이 어려워집니다.

10. Session pinning은 Proxy를 비싼 pass-through로 만든다

Proxy는 다음 transaction이 이전 session 상태에 의존하지 않을 때 DB 연결을 다른 Client에 빌려줄 수 있습니다. MySQL에서 user variable 설정, temporary table, named lock, 일부 prepared statement와 큰 SQL text 같은 동작은 session pinning을 유발할 수 있습니다.

flowchart TD tx[Transaction completed] --> state{Session state remains?} state -->|no| return[Return DB connection
to shared pool] state -->|yes| pin[Pin DB connection
to client session] pin --> pressure[Less multiplexing
higher borrow latency]

예를 들어 tenant ID를 session variable에 넣는 방식은 편하지만 연결 재사용을 제한할 수 있습니다.

-- Pinning 위험: transaction 이후에도 session state가 남는다.
SET @tenant_id = 'tenant-42';
SELECT * FROM orders WHERE tenant_id = @tenant_id;

-- 선호: 요청 값을 query parameter로 전달한다.
SELECT * FROM orders WHERE tenant_id = ?;

ORM과 driver가 애플리케이션 코드 밖에서 session initialization, prepared statement 또는 health-check query를 실행할 수도 있습니다. 따라서 SQL 코드 리뷰만으로 끝내지 않고 Proxy enhanced logging과 DatabaseConnectionsCurrentlySessionPinned를 canary gate에 포함합니다.

11. 부하 실험은 direct, proxy, pinned 세 집단으로 나눈다

Proxy 전후 숫자 하나만 비교하면 원인을 설명하기 어렵습니다. 같은 DB와 query를 사용하고 endpoint와 session behavior만 바꾼 세 집단을 비교합니다.

집단연결 경로목적
A. Direct baselineLambda → RDS현재 connection error와 DB 부하 기록
B. Proxy multiplexedLambda → Proxy → RDS짧은 stateless transaction의 재사용 효과 측정
C. Proxy pinnedLambda → Proxy → RDS + session statepinning이 이점을 얼마나 상쇄하는지 확인

부하는 세 단계로 고정합니다.

  1. Warm-up: 50 RPS로 5분 실행하여 Lambda environment와 연결을 준비합니다.
  2. Burst: 10초 안에 500 RPS로 올리고 2분 유지합니다.
  3. Recovery: 50 RPS로 낮춘 뒤 DB 연결과 borrow latency가 baseline으로 돌아오는 시간을 측정합니다.

각 요청은 같은 index query와 짧은 transaction을 사용합니다. Proxy의 효과와 query plan 변화를 섞지 않기 위해 데이터셋, SQL, Lambda memory, Region과 RDS instance class를 고정합니다.

12. 성공 기준은 API latency와 DB 보호를 함께 본다

Proxy가 DB 연결 수를 줄였더라도 API가 오래 queue에서 대기하면 성공이 아닙니다. 반대로 p95 latency가 낮아도 DB 연결을 상한까지 사용한다면 다음 burst를 버틸 여유가 없습니다.

13. CloudWatch에서는 연결 수보다 연결 재사용률을 본다

대시보드는 Lambda, Proxy, DB 세 계층을 같은 시간축에 배치합니다.

마지막 값이 높다고 자동으로 좋은 것은 아닙니다. Client가 idle connection만 많이 유지할 수도 있기 때문입니다. API latency, transaction rate와 DB load를 함께 봐야 합니다. CloudWatch label에는 request ID, order ID, tenant ID를 넣지 않고 endpoint, operation, error class처럼 제한된 값만 사용합니다.

14. Failover 실험은 연결 유지와 transaction 실패를 구분한다

RDS Proxy는 DB writer 변경을 추적하고 Client의 idle connection을 유지할 수 있습니다. 그러나 장애 시점에 실행 중이던 SQL이나 transaction까지 성공시키는 것은 아닙니다. 애플리케이션은 transaction 실패를 받고 멱등하게 재시도할 준비가 필요합니다.

sequenceDiagram participant C as Client participant P as RDS Proxy participant B as Primary DB participant G as Standby DB C->>P: Begin transaction P->>B: Execute write B--xP: Failover starts P--xC: In-flight transaction fails P->>G: Connect to promoted writer C->>P: Bounded idempotent retry P->>G: Execute write G-->>C: Success

Sandbox의 Multi-AZ DB에서 maintenance window를 잡고 강제 failover를 수행합니다. Direct 집단과 Proxy 집단에 같은 부하를 보내면서 마지막 성공 write, 첫 실패, 새 writer의 첫 성공 write 시각을 기록합니다. 운영 DB에서 예고 없이 실행해서는 안 됩니다.

# Sandbox 또는 승인된 복구 훈련에서만 실행
aws rds reboot-db-instance \
  --db-instance-identifier sandbox-orders \
  --force-failover

검증 대상은 DNS lookup 시간만이 아닙니다. Client connection 재생성 수, in-flight transaction 실패율, retry 이후 중복 write, 정상 latency로 회복하는 시간까지 포함합니다.

Borrow latency 경보만 보고 MaxConnectionsPercent를 올리면 DB가 보호 한도를 잃을 수 있습니다. 먼저 누가 연결을 오래 점유하는지 확인한 뒤, DB CPU와 memory headroom이 증명될 때만 상한을 변경합니다.

16. Canary rollout에는 direct endpoint로 돌아가는 경로가 필요하다

flowchart LR baseline[0. Direct baseline] --> provision[1. Provision Proxy] provision --> canary[2. Canary alias 5%] canary --> gate{SLO and pinning pass?} gate -->|no| rollback[Shift traffic to direct alias] gate -->|yes| ramp[3. 25% to 50% to 100%] ramp --> observe[4. Observe one peak cycle] observe --> restrict[5. Remove normal direct DB access]
  1. 현재 endpoint, connection pool 설정, session SQL과 peak connection 수를 inventory합니다.
  2. Direct와 Proxy Lambda alias를 동일한 코드로 만들고 DB_HOST만 다르게 둡니다.
  3. 5% traffic에서 authentication, latency, pinning과 오류 분류를 확인합니다.
  4. 한 단계마다 최소 한 번의 정상 peak와 인위적 burst를 통과한 뒤 비율을 높입니다.
  5. 100% 전환 후에도 한 번의 peak cycle 동안 direct rollback 경로를 유지합니다.
  6. 관찰 기간이 끝나면 일반 workload의 direct DB SG 접근을 제거하고 break-glass 절차만 남깁니다.

Rollback은 Proxy를 삭제하는 작업이 아닙니다. Lambda alias traffic을 검증된 direct endpoint 구성으로 되돌리는 작업입니다. Direct 경로도 credential, TLS와 connection limit이 준비되어 있어야 하며, rollback 때문에 원래 connection storm을 더 크게 만들지 않도록 reserved concurrency를 함께 낮춥니다.

17. 비용 판단은 Proxy와 다음 DB 증설 비용을 비교한다

Provisioned RDS와 Aurora에서 RDS Proxy는 DB의 vCPU를 기준으로 시간당 과금되고, Aurora Serverless에서는 ACU 기준으로 과금됩니다. 추가 Proxy endpoint는 PrivateLink 비용도 만들 수 있습니다. 따라서 요청 수만 보고 비용을 계산하지 않습니다.

Monthly Proxy cost
  = billable database capacity x regional Proxy rate x active hours
  + additional Proxy endpoint cost
  + monitoring and test traffic cost

Decision guardrail
  Proxy monthly cost
  < next DB class upgrade delta + expected incident cost reduction

DB instance를 키우지 않고도 연결 폭증을 흡수했다는 이유만으로 비용 절감이라고 부르면 안 됩니다. Proxy 비용, DB class 유지 비용, failover 개선과 운영 시간을 함께 비교합니다. 반대로 Proxy를 사용한 뒤 DB를 낮은 class로 바로 축소하지 않습니다. 먼저 CPU, memory, query latency가 한 peak cycle 이상 안정적인지 확인합니다.

18. 설정 변경도 성능 회귀로 취급한다

다음 변경은 canary 부하 테스트 없이 바로 배포하지 않습니다.

  • ORM이나 MySQL driver의 major version 변경
  • Session initialization query와 SET 문 추가
  • Prepared statement mode 변경
  • MaxConnectionsPercent, idle connection과 borrow timeout 변경
  • Lambda reserved concurrency 또는 ECS replica 상한 변경
  • DB instance class, max_connections, failover 구성 변경
# release-gate.yml - 도구 독립적인 운영 계약 예시
rds_proxy_gate:
  load_profile: burst-500-rps
  require:
    api_success_rate: ">= 99.9%"
    api_p95_ms: "<= 500"
    db_connection_utilization_p99: "<= 70%"
    borrow_latency_p95_ms: "<= 100"
    pinned_connection_ratio_p95: "< 5%"
    setup_failures: 0
  rollback_on:
    - authentication_regression
    - pinning_regression
    - latency_budget_exceeded

이 YAML은 특정 CI 제품 문법이 아니라 merge와 rollout을 막을 판단 기준입니다. 실험 결과는 commit SHA, Lambda alias, Proxy 설정 revision, DB class와 데이터셋 버전을 함께 저장해야 재현할 수 있습니다.

Pinning은 DB팀만의 문제가 아니고 connection limit은 애플리케이션팀만의 문제도 아닙니다. Proxy 설정과 Client 동작이 함께 결정하는 결과이므로 두 팀이 같은 dashboard와 release gate를 소유해야 합니다.

20. 아직 production-grade라고 주장하지 않는 범위

  • 이 글의 acceptance target은 실제 AWS 환경에서 측정된 결과가 아닙니다.
  • MySQL workload를 기준으로 했으며 PostgreSQL과 SQL Server의 pinning 조건은 다릅니다.
  • 실제 데이터 크기, lock contention, query plan과 tenant별 traffic skew를 재현하지 않았습니다.
  • Secret rotation 중 장기 연결과 failover가 겹치는 복합 장애를 검증하지 않았습니다.
  • Region별 RDS Proxy 단가와 PrivateLink 비용을 실제 월간 사용량으로 계산하지 않았습니다.
  • 최소 한 번의 planned failover와 peak-cycle 관찰 전에는 direct endpoint 접근을 완전히 제거할 수 없습니다.

이 범위가 남아 있는 상태에서 말할 수 있는 것은 "Proxy 구성을 만들었다"까지입니다. L5 수준의 운영 주장이 되려면 위 실험의 결과, 실패한 canary와 수정 이력, 승인된 SLO를 실제 값으로 남겨야 합니다.

21. 마무리

RDS Proxy의 목적은 Lambda와 RDS 사이에 서비스를 하나 더 놓는 것이 아닙니다. 무제한에 가까운 애플리케이션 확장과 유한한 DB 연결 사이에 예산, queue, load shedding과 failover 경계를 만드는 것입니다.

Proxy 도입의 성공 기준은 endpoint가 연결되는지가 아닙니다. Burst에서도 사용자 latency budget을 지키면서 DB 연결 headroom을 남기고, session pinning이 그 효과를 무너뜨리지 않는지를 증명하는 것입니다.
