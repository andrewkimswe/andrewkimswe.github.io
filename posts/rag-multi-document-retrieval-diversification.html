RAG · Multi-Document Retrieval · Diversification

[RAG] Top-k를 늘렸는데 왜 필요한 문서를 못 찾을까? - Duplicate Chunk와 Retrieval Diversification

Top-k를 늘리면 더 많은 근거를 얻을 것 같지만, 같은 문서의 유사 chunk가 상위 결과를 점유하면 필요한 문서를 모두 모으지 못할 수 있다. duplicate occupancy와 diversification 실험을 정리한다.

2026.08.13 RAG Retrieval Diversification

RAG에서 필요한 문서를 놓치면 가장 먼저 떠올리기 쉬운 해결책은 top_k를 늘리는 것이다. CloudOps RAG에서도 k=3에서 k=5로 늘렸을 때 development multi-document All-Hit이 0/6에서 2/6으로 개선됐다.

하지만 frozen configuration을 평가하면서 더 중요한 문제가 드러났다.

Multi Any-Hit@5 = 3/3
Multi All-Hit@5 = 0/3

필요한 문서 중 하나는 찾지만, 필요한 문서를 모두 함께 가져오는 데 실패한 것이다. 분석 결과 강한 가설은 같은 문서의 여러 chunk가 Top-k 자리를 반복해서 점유하는 duplicate occupancy였다.

1. Hit@k가 숨기는 문제

Question이 Doc A와 Doc B를 모두 필요로 하는데 검색 결과가 다음과 같다고 해보자.

1. Doc A / Chunk 3
2. Doc A / Chunk 4
3. Doc A / Chunk 2
4. Doc A / Chunk 5
5. Doc A / Chunk 1

일반 Hit@5는 expected document 하나 이상이 있으므로 성공으로 볼 수 있다. 하지만 실제로 필요한 Doc B는 없다. multi-document question에서는 metric을 분리해야 한다.

2. Multi Any-Hit과 Multi All-Hit

Metric 의미
Any-Hit Expected document 중 하나라도 있으면 성공한다.
All-Hit Expected document가 모두 있어야 성공한다.

CloudOps troubleshooting에서는 여러 공식 문서를 함께 봐야 하는 질문이 있었기 때문에 All-Hit이 중요한 metric이었다.

3. Frozen Configuration의 결과

Split Multi Any-Hit@5 Multi All-Hit@5
Development 6/6 2/6
Held-out 3/3 0/3

패턴은 아예 관련 문서를 못 찾는다기보다 관련 문서 하나는 찾는데 필요한 모든 evidence를 못 모으는 쪽에 가까웠다.

4. Top-5의 실제 다양성

Held-out Top-5 결과를 분석하자 다음 값을 얻었다.

Average unique document count = 2.10
Average duplicate chunk count = 2.90
Duplicate ratio = 0.58

Top-5는 다섯 개의 독립 evidence source를 의미하지 않는다.

같은 문서에서 의미가 비슷한 chunk가 여러 개 생성되면 query embedding과 모두 높은 similarity를 가질 수 있다.

5. 왜 Duplicate Chunk가 생기는가

Overlap chunking은 문맥 단절을 줄이지만 서로 비슷한 chunk를 만든다. Query가 해당 주제와 강하게 관련되면 같은 document의 여러 chunk가 상위권에 모일 수 있다.

Dense Retrieval
각 chunk를 독립 vector로 보고 가장 가까운 것을 반환한다.
RAG Context
같은 근거가 반복되면 context budget이 중복으로 소비된다.

6. Retrieval Depth와 Evidence Diversity

단순히 k를 늘리면 relevant document가 추가될 가능성은 있지만 context도 함께 커진다. 따라서 multi-document retrieval에서는 몇 개의 chunk를 가져오는가뿐 아니라 chunk가 얼마나 다양한지도 봐야 한다.

7. Duplicate-Occupancy Hypothesis

Multi-document All-Hit 실패의 원인 중 하나는 동일 문서의 여러 chunk가 Top-k 슬롯을 점유하는 것이다.

여기서 중요한 표현은 원인이다가 아니라 원인 중 하나일 가능성이 있다는 점이다. relevant document가 raw candidate pool 자체에 없다면 diversity 후처리로는 해결할 수 없다.

8. 가장 단순한 실험: Per-Document Cap

가설을 빠르게 확인하기 위해 새로운 retriever를 처음부터 구현하기보다 간단한 post-processing을 적용했다.

한 document에서 최대 2개 chunk만 Top-5에 허용

Dense similarity order는 유지하면서 같은 document가 Top-k를 과도하게 점유하지 못하게 한다.

Metric Baseline cap=2
Multi All-Hit@5 2/6 4/6
Average unique documents 1.975 2.95
Duplicate ratio 0.605 0.365

결과는 duplicate-occupancy hypothesis와 일치했다.

9. 바로 Production에 적용하지 않은 이유

이 실험은 frozen held-out evaluation을 본 이후 development set에서 수행한 post-hoc experiment다. 따라서 cap=2가 held-out 성능을 개선했다고 말할 수 없다. 새로운 untouched validation set이 필요하다.

flowchart TB frozen[Frozen Config] heldout[Held-out Evaluation] failure[Failure Observed] hypothesis[Hypothesis] posthoc[Dev Post-hoc Experiment] frozen --- heldout heldout --- failure failure --- hypothesis hypothesis --- posthoc

10. Retrieval Failure를 두 단계로 나누기

Failure 상황 개선 후보
Candidate Generation Relevant document가 candidate pool에 없다. better embedding, query rewriting, hybrid retrieval, larger candidate depth
Candidate Selection Relevant document가 있지만 final Top-k에서 밀린다. MMR, reranking, document diversification, per-document cap

11. MMR, Reranking, Hybrid Retrieval

Maximum Marginal Relevance는 relevance뿐 아니라 이미 선택된 결과와의 중복도 고려한다. Reranker는 query와 candidate를 함께 보면서 더 정밀하게 relevance를 평가할 수 있다. Hybrid retrieval은 dense embedding이 놓칠 수 있는 error code나 resource name 같은 lexical signal을 보완한다.

MMR
이미 선택된 결과와 너무 비슷한 candidate에 penalty를 준다.
Reranking
Top-N candidate를 더 비싼 relevance model로 다시 정렬한다.
Hybrid Retrieval
Dense retrieval과 BM25 또는 keyword retrieval을 결합한다.

12. Metadata-aware Retrieval

Corpus에 provider, category, resource 같은 metadata가 있다면 검색 공간을 줄일 수 있다. 하지만 잘못된 metadata classification은 relevant document를 검색 전에 제거할 수 있으므로 filter 정확성도 별도로 평가해야 한다. 

{
  "provider": "kubernetes",
  "category": "configuration",
  "resource": "configmap"
}

13. Chunking과 Diversification의 연결

Duplicate 문제는 retriever만의 문제가 아니다. 앞 단계의 chunking도 영향을 준다.

flowchart TB chunking[Chunking] distribution[Embedding Distribution] pool[Candidate Pool] diversity[Diversification] chunking --- distribution distribution --- pool pool --- diversity

Small chunks와 large overlap은 비슷한 vector를 많이 만들고 duplicate retrieval probability를 높일 수 있다.

14. Context Quality를 어떻게 볼 것인가

RAG에서 context quality를 Top-k similarity score만으로 정의하면 부족하다.

  • Relevance
  • Coverage
  • Diversity
  • Non-redundancy
  • Source Quality

특히 multi-document question에서는 coverage가 중요하다. 필요한 evidence가 A, B, C라면 A에 대한 비슷한 다섯 chunk보다 A/B/C를 포함하는 context가 더 유용하다.

정리

Top-k를 늘리는 것은 쉬운 개선처럼 보이지만 Top-5가 다섯 개의 독립 evidence source를 보장하지 않는다. 같은 문서의 duplicate chunk가 상위 결과를 점유하면 multi-document completeness가 낮아질 수 있다.

Per-document cap 실험은 duplicate occupancy가 실제 failure mode 중 하나일 가능성을 보여줬다. 다만 이 결과는 post-hoc development experiment이므로 새로운 validation set에서 다시 확인해야 한다. RAG 개선은 숫자를 올리는 일만이 아니라 어떤 failure mode를 어떤 실험으로 검증했는지 분리해 설명하는 일이다.
