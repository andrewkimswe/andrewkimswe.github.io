AWS · Kubernetes · Hybrid

[AWS/Kubernetes] 온프레미스 Kubernetes를 AWS 방식으로 운영하려면? - EKS Hybrid Nodes와 EKS Anywhere 비교

온프레미스 workload와 network 제어권은 유지하되 Kubernetes control plane 운영 부담을 줄이고 싶다면 선택지는 EKS Hybrid Nodes와 EKS Anywhere로 갈린다. 핵심은 Kubernetes를 어디에서 실행하느냐가 아니라 control plane, data plane, network의 책임 경계를 어디에 두느냐다.

2026.08.20 AWS Kubernetes EKS Hybrid Nodes

Kubernetes를 온프레미스에서 운영하고 있다고 가정해보자.

회사 데이터센터에는 이미 물리 서버나 VM이 있고, 보안이나 데이터 위치 요구사항 때문에 workload 자체를 AWS로 옮기기는 어렵다.

문제는 application workload만 운영하는 것이 아니라 Kubernetes control plane까지 직접 관리해야 한다는 점이다.

flowchart TB subgraph onprem[On-Premises] cp[Kubernetes Control Plane
API Server / etcd / Scheduler] workers[Worker Nodes
kubelet / runtime / application pods] cp --> workers end

여기서 요구사항이 하나 추가된다.

서버와 네트워크는 계속 온프레미스에서 관리하되 Kubernetes control plane의 운영 부담은 줄이고 싶다.

이 요구사항에서 먼저 검토할 수 있는 선택지가 Amazon EKS Hybrid Nodes다.

1. EKS Hybrid Nodes란?

일반적인 Amazon EKS에서는 AWS가 Kubernetes control plane을 관리하고 EC2나 Fargate 같은 AWS compute에서 workload를 실행한다.

EKS Hybrid Nodes는 여기서 data plane의 위치를 온프레미스까지 확장한다.

flowchart TB subgraph aws[AWS Region] eks[Amazon EKS Control Plane
API Server / etcd / Scheduler
AWS Managed] end subgraph dc[On-Premises] node1[Hybrid Node] node2[Hybrid Node] node3[Hybrid Node] apps[Application Pods
Customer Managed] node1 --> apps node2 --> apps node3 --> apps end eks <--> conn[VPN or Direct Connect] conn <--> node1 conn <--> node2 conn <--> node3

핵심은 간단하다.

flowchart LR cp[Control Plane] --> aws[AWS] worker[Worker Nodes] --> onprem[On-Premises]

즉 기존 온프레미스 서버를 계속 사용하면서 Kubernetes control plane의 가용성, 확장성, 운영 부담을 Amazon EKS에 넘길 수 있다.

2. 일반 EKS와 무엇이 다른가?

일반적인 EKS는 managed control plane과 AWS compute가 같은 AWS 환경 안에서 만난다.

flowchart TB eks[EKS Control Plane] --> compute[EC2 or Fargate] compute --> pods[Pods]

반면 Hybrid Nodes에서는 managed control plane은 AWS에 있고, worker node는 온프레미스에 남는다.

flowchart TB eks[EKS Control Plane] --> network[Hybrid Connectivity] network --> server[On-Prem VM or Bare Metal] server --> pods[Pods]

따라서 Hybrid Nodes의 핵심은 Kubernetes를 온프레미스에 새로 설치하는 것이 아니다.

AWS에서 관리되는 EKS cluster에 온프레미스 compute를 node로 연결하는 것에 가깝다.

3. 그러면 EKS Anywhere는 무엇인가?

여기서 가장 헷갈리는 서비스가 Amazon EKS Anywhere다.

이름만 보면 Hybrid Nodes와 비슷해 보이지만, 가장 큰 차이는 control plane이 어디에 있고 누가 관리하느냐다.

EKS Anywhere에서는 Kubernetes cluster 전체가 사용자의 infrastructure에서 실행된다.

flowchart TB subgraph onprem[On-Premises] anywhere[EKS Anywhere] cp[Kubernetes Control Plane] worker[Worker Nodes] app[Applications] anywhere --> cp cp --> worker worker --> app end owner[Customer Managed] --> anywhere

AWS는 EKS Anywhere를 Kubernetes 관리 소프트웨어로 제공하지만, Amazon EKS의 managed control plane을 사용하는 구조는 아니다.

따라서 사용자는 cluster lifecycle과 underlying infrastructure를 계속 관리해야 한다.

4. EKS Hybrid Nodes vs EKS Anywhere

둘을 비교하면 차이는 명확해진다.

구분 EKS Hybrid Nodes EKS Anywhere
Control Plane 위치 AWS Region On-Premises
Control Plane 관리 AWS 고객
Worker 위치 On-Premises / Edge On-Premises / Edge
기존 VM 활용 가능 가능
AWS 연결 필요 필수는 아님
Air-gapped 환경 부적합 상대적으로 적합
Kubernetes 관리 부담 상대적으로 낮음 상대적으로 높음
핵심 목적 AWS EKS와 온프레미스 compute 연결 온프레미스 자체 Kubernetes 운영

결국 가장 중요한 질문은 이것이다.

Control plane을 AWS에 둘 수 있는가?

가능하다면 Hybrid Nodes가 강력한 선택지가 된다. 반대로 AWS와 안정적으로 연결할 수 없는 환경이라면 이야기가 달라진다.

5. 네트워크가 중요한 이유

Hybrid Nodes에서 control plane은 AWS에 있고 worker는 온프레미스에 있다.

따라서 둘 사이의 안정적인 private connectivity가 architecture의 전제가 된다.

flowchart TB eks[AWS EKS Control Plane] <--> vpn[Site-to-Site VPN
or Direct Connect] vpn <--> nodes[On-Premises Nodes]

즉 Hybrid Nodes는 온프레미스 Kubernetes를 인터넷이나 AWS 연결 없이 독립적으로 운영하는 서비스가 아니다.

AWS의 EKS control plane과 온프레미스 node 사이에 안정적인 연결이 필요하다.

연결이 자주 끊기거나 disconnected, disrupted, intermittent, limited 환경을 전제로 한다면 EKS Anywhere를 고려하는 편이 더 자연스럽다.

6. 책임 경계는 어디에 있는가?

EKS가 control plane을 관리한다고 해서 온프레미스 infrastructure 전체를 AWS가 관리하는 것은 아니다.

flowchart TB subgraph aws[AWS Responsibility] managedCp[Kubernetes Control Plane] availability[Control Plane Availability] scaling[Control Plane Scaling] end subgraph customer[Customer Responsibility] hardware[On-Prem Hardware or VM] os[Operating System] network[Local Network and Firewall] cidr[Node / Pod CIDR and Routing] workload[Application Workload] end

온프레미스의 physical server, VM, OS, local network, firewall, node CIDR, pod CIDR, routing은 여전히 고객이 관리해야 한다.

따라서 Hybrid Nodes의 가치는 온프레미스 infrastructure에 대한 제어권은 유지하면서 Kubernetes 관리 부담의 일부를 AWS에 넘기는 것이라고 볼 수 있다.

7. Hybrid Kubernetes에서는 CIDR 설계도 중요하다

Control plane과 worker가 서로 다른 네트워크에 존재하기 때문에 IP address range도 신경 써야 한다.

예를 들어 AWS VPC, 온프레미스 node network, pod network가 서로 겹치지 않도록 설계해야 한다.

flowchart LR vpc[AWS VPC
10.0.0.0/16] node[On-Prem Node CIDR
10.10.0.0/16] pod[On-Prem Pod CIDR
10.20.0.0/16] service[Kubernetes Service CIDR] vpc --- node node --- pod pod --- service

특히 Hybrid Nodes에서는 VPC CIDR, remote node CIDR, remote pod CIDR, Kubernetes service CIDR 사이의 충돌을 피해야 한다.

네트워크 연결이 존재한다는 것만으로 충분한 것이 아니라 각 network 사이에 필요한 routing과 firewall configuration도 함께 구성되어야 한다.

8. Hybrid Nodes Gateway

Hybrid Kubernetes에서 가장 까다로운 부분 중 하나는 결국 networking이다.

AWS VPC의 workload와 온프레미스 Pod가 서로 통신하려면 remote Pod network까지 routable하게 구성해야 하는 상황이 생길 수 있다.

AWS는 이를 단순화하기 위해 EKS Hybrid Nodes Gateway도 제공한다.

flowchart TB subgraph aws[AWS VPC] cloud[EKS / Cloud Nodes] gateway[Hybrid Nodes Gateway] cloud <--> gateway end gateway <--> vxlan[VXLAN] subgraph onprem[On-Premises] cilium[Cilium] hybrid[Hybrid Nodes] pods[Pods] cilium --> hybrid hybrid --> pods end vxlan <--> cilium

Gateway는 VPC와 Hybrid Node의 Pod 사이 networking 일부를 자동화해 복잡한 routing 변경 부담을 줄일 수 있다.

다만 이것 역시 AWS와 온프레미스 사이의 기본적인 private connectivity 자체를 없애주는 것은 아니다.

9. EKS on Outposts와는 무엇이 다른가?

또 하나 헷갈릴 수 있는 선택지가 AWS Outposts다.

Outposts는 AWS infrastructure 자체를 고객 데이터센터에 설치하는 방식이다.

flowchart TB hybrid[EKS Hybrid Nodes] --> customerCompute[Customer-owned VM or Server] outposts[EKS on Outposts] --> awsCompute[EC2 on AWS Outposts]

Hybrid Nodes에서는 기존에 가지고 있는 물리 또는 가상 머신을 사용할 수 있다.

반면 Outposts에서는 AWS Outposts의 compute infrastructure를 사용한다.

따라서 이미 자체 서버가 있고 이를 Kubernetes worker로 활용하고 싶다는 조건에서는 Hybrid Nodes가 더 직접적인 선택지가 된다.

10. 요구사항을 다시 보면

현재 상태가 온프레미스 VM과 self-managed Kubernetes라면 회사가 원하는 것은 보통 다음과 같이 정리된다.

flowchart TB current[Current State
On-Prem VM + Self-managed Kubernetes] req1[Keep workload on-premises] req2[Keep local network control] req3[Reuse existing infrastructure] req4[Reduce Kubernetes management burden] target[EKS Hybrid Nodes] current --> req1 current --> req2 current --> req3 current --> req4 req1 --> target req2 --> target req3 --> target req4 --> target

이 요구사항이라면 AWS EKS control plane과 hybrid connectivity를 통해 기존 온프레미스 VM을 Hybrid Node로 연결하는 구조가 가장 자연스럽다.

따라서 정답은 Amazon EKS Hybrid Nodes다.

11. 다른 선택지가 아닌 이유

EKS Anywhere

EKS Anywhere도 기존 온프레미스 VM에서 Kubernetes를 운영할 수 있다.

하지만 control plane 역시 고객 infrastructure에 있기 때문에 Kubernetes cluster lifecycle 관리 책임이 계속 고객에게 남는다.

문제에서 Kubernetes cluster의 전반적인 관리 부담을 줄이고 싶다고 했다면 Hybrid Nodes가 더 적합하다.

Self-managed Kubernetes on Outposts

Outposts에서도 Kubernetes를 실행할 수 있다.

하지만 문제에서는 이미 존재하는 온프레미스 VM을 활용하면서 infrastructure control을 유지하려고 한다.

여기에 별도의 Outposts infrastructure와 self-managed Kubernetes를 도입하는 것은 요구사항에 비해 복잡하다.

Private VPC의 Self-managed Kubernetes

단순히 EC2에 Kubernetes를 직접 설치한다고 control plane 관리 문제가 해결되는 것은 아니다.

온프레미스 self-managed Kubernetes에서 EC2 self-managed Kubernetes로 위치만 옮긴 셈이다.

Kubernetes 자체의 관리 부담을 줄이려는 요구사항과 맞지 않는다.

13. 정리

Hybrid Kubernetes를 선택할 때 단순히 온프레미스에서 Kubernetes를 실행하는지만 보면 EKS Anywhere와 Hybrid Nodes를 구분하기 어렵다.

더 중요한 질문은 control plane을 어디에 두고 누가 관리할 것인가다.

flowchart TB question[Control Plane] question --> aws[AWS] question --> onprem[On-Premises] aws --> hybrid[EKS Hybrid Nodes] onprem --> anywhere[EKS Anywhere]

EKS Hybrid Nodes는 AWS가 Kubernetes control plane을 관리하면서 기존 온프레미스 서버를 worker node로 사용할 수 있게 한다.

온프레미스 compute와 network에 대한 제어권은 유지하면서 Kubernetes control plane의 운영 부담을 줄이고 싶다면 EKS Hybrid Nodes를 고려할 수 있다.

반대로 AWS와 지속적으로 연결할 수 없는 isolated 또는 air-gapped 환경이라면 control plane까지 로컬에서 운영하는 EKS Anywhere가 더 적합하다.

결국 Hybrid Kubernetes에서도 핵심은 Kubernetes를 어디에서 실행하는가가 아니다. Control plane, data plane, network의 책임 경계를 어디에 그을 것인가가 architecture 선택을 결정한다.
