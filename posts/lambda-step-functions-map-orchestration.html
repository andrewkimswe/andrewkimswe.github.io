[AWS] Lambda 반복 호출을 Step Functions Map으로 분리하기 - Serverless Orchestration 설계

하나의 Lambda가 반복문으로 여러 작업을 호출하는 구조는 작게 시작하기 쉽지만, 작업량이 늘어나면 Timeout, Retry, Error Handling 책임이 한 함수 안에 몰린다. Step Functions Map 상태로 오케스트레이션을 분리하는 설계를 정리한다.

2026.08.03 AWS Lambda Step Functions

서버리스 애플리케이션을 만들다 보면 하나의 Lambda 함수가 여러 작업을 순차적으로 호출하는 구조를 쉽게 만들 수 있다.

예를 들어 등록되지 않은 디바이스 ID를 조회한 뒤, 각 디바이스를 활성화하는 작업을 수행한다고 가정해보자.

flowchart TB retrieve[Retrieve Lambda] d1[Activate Lambda
device-1] d2[Activate Lambda
device-2] d3[Activate Lambda
device-3] more[More devices] retrieve --- d1 retrieve --- d2 retrieve --- d3 retrieve --- more

초기에는 단순하고 구현하기 쉬운 구조다. 하지만 처리해야 할 디바이스가 증가하면 문제가 생긴다.

flowchart TB targets[처리 대상 증가] loop[Lambda 내부 반복 횟수 증가] runtime[전체 실행시간 증가] timeout[Lambda Timeout 위험] targets --- loop loop --- runtime runtime --- timeout

이런 경우 작업의 오케스트레이션 책임을 Lambda 내부 코드에서 분리하고, AWS Step Functions의 Map 상태를 사용할 수 있다.

1. 기존 구조의 문제

다음과 같은 Lambda 함수가 있다고 가정한다.

def handler(event, context):
    device_ids = get_unregistered_devices()

    for device_id in device_ids:
        activate_device(device_id)

논리적으로는 간단하다. 하지만 Retrieve Lambda가 처리할 데이터를 조회하고, 모든 하위 작업의 실행까지 직접 제어한다. 즉 비즈니스 로직과 오케스트레이션 로직이 결합되어 있다.

Retrieve Lambda
데이터 조회, 반복문 관리, Activate 호출, 실패 처리, 전체 실행시간 관리

처리 대상이 적을 때는 문제가 없지만 작업량이 증가하면 하나의 Lambda 실행시간에 전체 처리가 종속된다. Lambda의 최대 실행시간은 제한되어 있기 때문에 장기적으로 확장하기 어렵다.

2. Step Functions로 Orchestration 분리

구조를 다음과 같이 변경할 수 있다.

flowchart TB step[AWS Step Functions] retrieve[Retrieve Lambda] list[device_id list] map[Map State] a1[Activate Lambda] a2[Activate Lambda] a3[Activate Lambda] step --- retrieve retrieve --- list list --- map map --- a1 map --- a2 map --- a3

Retrieve Lambda는 처리 대상만 반환한다.

{
  "devices": [
    "device-001",
    "device-002",
    "device-003"
  ]
}

Step Functions가 이 배열을 받아 Map 상태를 이용해 각 항목에 대해 Activate Lambda를 실행한다. 이렇게 하면 Lambda 함수 자체가 반복 작업 전체를 관리할 필요가 없다.

3. Map State

Step Functions의 Map 상태는 배열이나 데이터 집합의 각 항목에 동일한 워크플로를 적용할 때 사용할 수 있다.

flowchart LR input[Input
device-001
device-002
device-003] map[Map State] activate[Activate Lambda
per item] input --- map map --- activate

Amazon States Language로 단순화하면 다음과 같은 형태다.

{
  "StartAt": "RetrieveDevices",
  "States": {
    "RetrieveDevices": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Next": "ActivateDevices"
    },

    "ActivateDevices": {
      "Type": "Map",
      "ItemsPath": "$.Payload.devices",
      "Iterator": {
        "StartAt": "ActivateDevice",
        "States": {
          "ActivateDevice": {
            "Type": "Task",
            "Resource": "arn:aws:states:::lambda:invoke",
            "End": true
          }
        }
      },
      "End": true
    }
  }
}

핵심은 반복문이 Lambda 코드가 아니라 워크플로 정의에 있다는 점이다.

4. Lambda 내부 반복문과 무엇이 다른가?

Lambda 직접 반복
전체 작업이 하나의 Lambda 실행시간 안에 끝나야 하며 실패 처리도 직접 구현해야 한다.
Step Functions Map
각 작업을 독립적인 실행 단위로 다루고 상태와 실행 흐름을 워크플로에서 관리한다.

Step Functions가 상태와 실행 흐름을 관리하기 때문에 Lambda는 개별 비즈니스 작업에 집중할 수 있다.

5. 병렬 처리

Map 상태의 장점 중 하나는 여러 작업을 병렬로 실행할 수 있다는 점이다.

flowchart LR sequential[Sequential
A, B, C, D] parallel[Map
A / B / C / D] result[Reduced total runtime
when tasks are independent] sequential --- parallel parallel --- result

물론 항상 최대 병렬성이 좋은 것은 아니다. Downstream 시스템이 DynamoDB, RDS 또는 외부 API라면 과도한 병렬 호출이 오히려 병목을 만들 수 있다. 따라서 동시 실행 수를 제어하는 것이 중요하다.

6. Concurrency 제어

예를 들어 Activate Lambda가 외부 API를 호출한다고 가정해보자. 수천 개의 작업을 한 번에 실행하면 외부 API의 Rate Limit을 초과할 수 있다. 

"MaxConcurrency": 20
flowchart TB tasks[5000 Tasks] limit[동시에 최대 20개] protect[Downstream 보호] tasks --- limit limit --- protect

즉 Step Functions는 단순히 병렬성을 높이는 서비스라기보다 병렬성을 제어하는 orchestration layer로 사용할 수 있다.

7. Retry와 Error Handling

Lambda 내부에서 다른 Lambda를 반복 호출하면 실패 처리를 직접 구현해야 한다.

for device_id in device_ids:
    try:
        activate(device_id)
    except Exception:
        retry(...)

Step Functions에서는 이를 워크플로 정의에 포함할 수 있다.

"Retry": [
  {
    "ErrorEquals": [
      "Lambda.ServiceException",
      "Lambda.TooManyRequestsException"
    ],
    "IntervalSeconds": 2,
    "MaxAttempts": 3,
    "BackoffRate": 2
  }
]

또한 재시도 후에도 실패한다면 Catch를 이용해 별도의 처리 경로로 보낼 수 있다.

flowchart TB activate[Activate Lambda] retry[Retry] catchState[Catch] failure[Failure Handler] activate --- retry retry --- catchState catchState --- failure

따라서 재시도 정책이 애플리케이션 코드와 분리된다.

8. Lambda는 Worker, Step Functions는 Orchestrator

이 구조에서 역할을 명확하게 나눌 수 있다.

Lambda
개별 작업 수행
Step Functions
어떤 작업을 언제, 몇 번, 어떤 순서로 실행할지 관리
flowchart TB before[Before
Lambda owns business logic, loop, retry, error handling, workflow state] afterLambda[After
Lambda owns business logic] afterStep[Step Functions owns loop, retry, error handling, workflow state] before --- afterLambda before --- afterStep

이렇게 하면 Lambda 함수가 더 작고 독립적인 컴포넌트가 된다.

9. EventBridge Scheduler와는 무엇이 다른가?

EventBridge Scheduler는 특정 시간이나 주기에 작업을 실행하는 데 적합하다.

EventBridge Scheduler
언제 시작할 것인가
Step Functions
작업들을 어떻게 실행할 것인가

두 서비스를 함께 사용할 수도 있다.

flowchart TB scheduler[EventBridge Scheduler] step[AWS Step Functions] retrieve[Retrieve] map[Map] activate[Activate Lambdas] scheduler --- step step --- retrieve retrieve --- map map --- activate

10. 언제 Step Functions Map이 적합한가?

대표적으로 다음과 같은 경우 사용할 수 있다.

여러 객체 처리
S3 Object List를 순회하며 각 객체를 변환한다.
사용자별 작업 수행
User List를 순회하며 알림이나 상태 변경 작업을 수행한다.
디바이스 일괄 처리
Device IDs를 순회하며 Activate Device 작업을 수행한다.
데이터 Batch 처리
Dataset을 순회하며 Transform 또는 Validate 작업을 수행한다.

공통점은 하나의 큰 작업을 여러 독립적인 작은 작업으로 나눌 수 있다는 것이다.

정리

Lambda 내부에서 반복문을 사용해 여러 Lambda를 호출하는 구조는 작은 규모에서는 단순하고 효과적이다. 하지만 작업 수가 증가하면 전체 실행시간이 하나의 Lambda에 종속되고, Timeout과 재시도 관리 문제가 발생할 수 있다.

이때 AWS Step Functions의 Map 상태를 이용하면 작업의 오케스트레이션을 Lambda 밖으로 분리할 수 있다.

flowchart TB old[기존
Lambda Loop with Lambda Calls] improved[개선
Step Functions Map with Lambda Workers] old --- improved

이를 통해 다음과 같은 장점을 얻을 수 있다.

  • Lambda 실행시간과 전체 Batch 처리시간 분리
  • 병렬 실행 및 동시성 제어
  • Retry와 Error Handling 중앙 관리
  • Workflow 상태 가시성 확보
  • Lambda 비즈니스 로직 단순화

Lambda: Worker

Step Functions: Orchestrator

서버리스 시스템에서도 작업량이 증가할수록 단순한 함수 호출 구조보다 실행 흐름과 상태를 관리하는 orchestration layer가 중요해진다.
