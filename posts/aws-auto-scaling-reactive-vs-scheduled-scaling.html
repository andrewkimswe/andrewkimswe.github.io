[AWS/Auto Scaling] CPU가 99%가 된 뒤 Scale-out하면 왜 늦을까? - Reactive Scaling과 Scheduled Scaling

CPU가 높아진 뒤 scale-out을 시작하면 Auto Scaling은 정상 동작해도 사용자는 이미 지연과 오류를 경험할 수 있다. 반복되는 트래픽 spike에서는 빠르게 반응하는 것보다 부하 전에 capacity를 준비하는 전략이 더 중요하다.

2026.08.22 AWS Auto Scaling Scheduled Scaling

Auto Scaling을 처음 배우면 흔히 다음과 같은 구조를 떠올린다.

flowchart TB cpu[CPU 상승] --> alarm[CloudWatch Alarm] alarm --> scaling[Auto Scaling] scaling --> ec2[EC2 증가]

CPU가 높아지면 인스턴스를 늘리면 된다. 논리적으로는 맞다.

하지만 실제 운영 환경에서는 CPU가 높아진 것을 확인한 뒤 scale-out을 시작하면 이미 늦을 수 있다.

특히 트래픽 증가 시점이 매일 반복되고 예측 가능하다면 reactive scaling보다 더 적절한 방법이 있다.

1. 문제 상황

다음과 같은 웹 애플리케이션이 있다고 하자.

flowchart TB users[Users] --> alb[Application Load Balancer] alb --> asg[Auto Scaling Group] asg --> ec21[EC2] asg --> ec22[EC2] asg --> ec23[EC2]

평상시에는 문제가 없다.

하지만 매주 평일 오전 8시가 되면 사용자들이 동시에 로그인한다.

CloudWatch를 확인해보니 다음과 같은 패턴이 반복된다.

07:00  CPU 25%
07:30  CPU 30%
08:00  CPU 99%
08:10  CPU 99%
09:00  CPU 35%

CPU가 99%까지 올라가는 동안 응답 지연과 application error가 발생한다.

이 상황에서 단순히 CPU가 99%가 되면 scale-out한다고 설정하면 문제를 해결할 수 있을까?

2. Reactive Scaling에는 시간이 필요하다

CPU 기반 scaling policy는 기본적으로 문제가 발생한 후 반응하는 구조다.

flowchart TB traffic[Traffic 증가] --> cpu2[CPU 증가] cpu2 --> metric[Metric 수집] metric --> threshold[Threshold 초과 확인] threshold --> policy[Scaling Policy 실행] policy --> launch[새 EC2 시작] launch --> boot[OS Boot] boot --> app[Application 시작] app --> health[Health Check 통과] health --> target[ALB Target 등록] target --> serve[실제 Traffic 처리]

이 모든 과정에는 시간이 필요하다.

문제는 scale-out이 실패한 것이 아니다.

Scale-out이 완료되기 전에 서비스가 이미 과부하 상태에 들어간 것이다.

3. CPU 99%는 너무 늦은 신호일 수 있다

CPU는 대표적인 reactive metric이다.

CPU가 99%라는 것은 곧 부하가 커질 것이라는 예측 신호가 아니라, 이미 부하가 매우 커졌다는 상태 신호에 가깝다.

IF CPU >= 99%
THEN Scale Out

특히 인스턴스 시작 시간이 긴 애플리케이션에서는 더 그렇다.

flowchart TB saturated[CPU 99%] --> start[Scale-out 시작] start --> wait[2~5분 대기] wait --> ready[Capacity 확보]

그 몇 분 동안 사용자는 느린 응답이나 오류를 경험할 수 있다.

4. 트래픽이 예측 가능하다면 Scheduled Scaling

이번 상황에서 중요한 단서는 매주 평일 오전 8시에서 9시 사이라는 점이다.

트래픽 급증이 우연히 발생하는 것이 아니라 반복되는 패턴이라면, 부하가 발생하기 전에 capacity를 미리 늘릴 수 있다.

flowchart TB schedule[07:45 Scheduled Scaling] --> desired[Desired Capacity 증가] desired --> launch2[EC2 시작] launch2 --> health2[Health Check 완료] health2 --> surge[08:00 Login Surge] surge --> ready2[이미 추가 Capacity 준비됨]

이것이 Scheduled Scaling의 핵심이다.

5. Reactive vs Scheduled Scaling

두 방식을 비교하면 차이가 명확하다.

flowchart LR load[Load 발생] --> metric2[Metric 상승] metric2 --> reactive[Reactive Scale-out] expected[예상된 Load 발생 전] --> capacity[Capacity 미리 증가] capacity --> scheduled[Scheduled Scaling]
방식 장점 주의할 점
Reactive Scaling 예상하지 못한 부하에 대응 가능하고 실제 workload를 기준으로 자동 조절할 수 있다. 항상 반응 시간이 필요하므로 갑작스러운 burst에는 늦을 수 있다.
Scheduled Scaling 반복되는 traffic spike에 미리 대비하고 instance startup delay의 영향을 줄일 수 있다. 트래픽 패턴이 예측 가능해야 하며 실제 workload가 달라지면 capacity가 과하거나 부족할 수 있다.

6. 둘 중 하나만 써야 하는 것은 아니다

실제 환경에서는 Scheduled Scaling과 reactive scaling을 함께 사용할 수 있다.

flowchart TB pre[07:45 Scheduled Scaling
Desired = 10] --> surge2[08:00 Login Surge] surge2 --> unexpected[08:20 예상보다 Traffic 증가] unexpected --> tracking[Target Tracking] tracking --> scale14[Desired = 14]

Scheduled Scaling은 예상 가능한 baseline capacity를 준비하고, reactive policy는 예상보다 크거나 작은 변화에 대응한다.

flowchart LR scheduled2[Scheduled Scaling] --> expected2[Expected Load 대응] tracking2[Target Tracking] --> unexpected2[Unexpected Load 대응] expected2 --> combined[Combined Strategy] unexpected2 --> combined

이 조합이 더 현실적인 경우가 많다.

7. Target Tracking은 무엇인가?

Auto Scaling에서 많이 사용하는 방식 중 하나가 Target Tracking이다.

예를 들어 Average CPU를 50%로 설정하면 Auto Scaling이 해당 수준을 유지하도록 capacity를 조절한다.

flowchart TB high[CPU > 50%] --> scaleOut[Scale Out] low[CPU < 50%] --> scaleIn[Scale In]

이 방식은 일반적인 workload 변화에 대응하기 좋다.

하지만 마찬가지로 metric 변화 이후 반응하는 방식이므로 갑작스러운 burst에는 startup delay가 영향을 줄 수 있다.

8. Step Scaling은 언제 사용할까?

Step Scaling은 metric의 크기에 따라 scaling 폭을 다르게 설정할 수 있다.

CPU 60~70%  -> +1 instance
CPU 70~85%  -> +3 instances
CPU > 85%   -> +5 instances

즉 부하가 클수록 더 공격적으로 확장할 수 있다.

하지만 이 역시 metric 발생 후 scaling이라는 reactive 구조 자체는 동일하다.

따라서 반복적으로 정확한 시간에 발생하는 spike라면 Scheduled Scaling이 더 직접적인 해결책일 수 있다.

9. Predictive Scaling과는 무엇이 다른가?

AWS Auto Scaling에는 Predictive Scaling도 있다.

Scheduled Scaling이 사람이 알고 있는 일정에 따라 capacity를 설정한다면 Predictive Scaling은 과거의 workload pattern을 분석해 미래 capacity를 예측한다.

flowchart TB history[Historical Traffic] --> analysis[Pattern Analysis] analysis --> prediction[Future Load Prediction] prediction --> capacity2[Capacity 미리 준비]

둘의 차이는 다음과 같이 볼 수 있다.

Scheduled Scaling
= "매일 8시에 트래픽이 늘어난다는 것을 내가 알고 있음"

Predictive Scaling
= "과거 데이터를 기반으로 시스템이 트래픽 패턴을 예측"

문제처럼 정확한 시간대가 이미 명확하게 알려져 있다면 Scheduled Scaling이 매우 단순하고 직접적인 해결책이다.

10. CloudFront를 추가하면 해결되지 않을까?

ALB 앞에 CloudFront를 배치하면 static content나 cache 가능한 응답에 대해서는 origin 부하를 줄일 수 있다.

하지만 문제의 workload가 사용자 로그인처럼 dynamic request라면 CloudFront cache만으로 근본적인 compute capacity 문제를 해결하기 어렵다.

flowchart TB login[User Login] --> auth[Authentication] auth --> logic[Dynamic Application Logic] logic --> ec2app[EC2 Application Server]

결국 요청이 application server까지 도달해야 하기 때문이다.

11. ElastiCache를 사용하면 해결되지 않을까?

ElastiCache도 특정 workload에서는 매우 효과적이다.

예를 들어 반복되는 DB read가 병목이라면 Redis로 database load를 줄일 수 있다.

flowchart TB app2[Application] --> redis[Redis / ElastiCache] redis --> db[Database]

하지만 이번 문제에서는 병목 원인이 명확하다.

08:00
모든 EC2 CPU -> 99%

그리고 이 패턴이 일정하게 반복된다.

따라서 가장 직접적인 문제는 compute capacity를 부하가 발생하기 전에 준비하는 것이다.

12. SAA에서 구분하는 방법

시험에서는 다음처럼 생각하면 빠르다.

flowchart TB question{Traffic pattern은 어떤가?} unknown[예측 불가능한 트래픽] --> target[Target Tracking / Step Scaling] scheduledTime[매일 또는 매주 특정 시간 반복] --> scheduled3[Scheduled Scaling] historical[반복 패턴은 있지만 schedule 직접 관리가 부담] --> predictive[Predictive Scaling] question --> unknown question --> scheduledTime question --> historical

핵심은 load가 발생했는지만 보는 것이 아니라, load가 언제 발생할지 알고 있는지까지 보는 것이다.

13. 전체 흐름

Reactive scaling만 사용하면 다음 흐름이 된다.

flowchart TB login2[08:00 Login Surge] --> cpu99[CPU 99%] cpu99 --> error[Latency / Error] error --> trigger[Scaling Trigger] trigger --> launch3[EC2 Launch] launch3 --> added[Capacity 증가]

Scheduled scaling을 사용하면 흐름이 달라진다.

flowchart TB trigger2[07:45 Scaling Trigger] --> launch4[EC2 Launch] launch4 --> added2[Capacity 증가] added2 --> login3[08:00 Login Surge] login3 --> ok[Ready]

두 구조의 가장 큰 차이는 scale-out의 속도가 아니라 scale-out을 시작하는 시점이다.

14. 마무리

Auto Scaling은 단순히 CPU가 높아지면 EC2를 늘리는 기능으로만 이해하면 부족하다.

실제 시스템에서는 새로운 capacity가 service에 투입되기까지 시간이 필요하다.

flowchart LR launch5[Launch] --> boot2[Boot] boot2 --> init[Application Initialization] init --> check[Health Check] check --> register[Traffic Registration]

따라서 갑작스러운 traffic spike에서는 metric threshold에 도달한 뒤 scale-out하는 방식만으로는 사용자가 느끼는 장애를 완전히 막지 못할 수 있다.

특히 부하가 매일 또는 매주 반복된다면 대응 방법은 훨씬 단순하다.

부하가 발생한 뒤 확장하는 것이 아니라, 부하가 발생하기 전에 capacity를 준비한다.

Scheduled Scaling은 바로 이 문제를 해결한다.

결국 Auto Scaling 전략을 선택할 때 중요한 것은 단순히 어떤 metric을 사용할지가 아니다.

Reactive
"지금 시스템이 얼마나 바쁜가?"

Predictive / Scheduled
"곧 시스템이 얼마나 바빠질 것인가?"

이 두 질문을 구분해야 한다.

예측 가능한 workload라면 가장 좋은 scaling은 빠르게 반응하는 scaling이 아니라, 미리 준비되어 있는 scaling일 수 있다.
