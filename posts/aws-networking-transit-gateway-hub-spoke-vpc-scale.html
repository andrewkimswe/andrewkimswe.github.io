[AWS/Networking] VPC가 1,000개라면 Peering은 왜 무너질까? - Transit Gateway와 Hub-and-Spoke 설계

VPC 수가 늘어나면 peering connection과 route 관리가 N²에 가깝게 복잡해집니다. Transit Gateway로 중앙 routing layer와 segmentation을 설계합니다.

2026.08.29AWSNetworkingTGWVPC

VPC 두 개를 연결할 때 VPC Peering은 단순하고 좋은 선택입니다. 문제는 VPC가 수백 개, 수천 개로 늘고 서로 통신해야 하는 순간입니다.

flowchart LR a[VPC A] --- b[VPC B] a --- c[VPC C] b --- c a --- d[VPC D] b --- d c --- d

1. VPC Peering은 point-to-point 연결이다

VPC Peering은 두 VPC 사이의 private connectivity를 제공합니다. 작은 환경에서는 이해하기 쉽지만, 연결 대상이 늘어날수록 connection과 route table 관리가 함께 증가합니다.

2. Full Mesh의 N² 문제

모든 VPC가 서로 직접 통신해야 한다면 필요한 pairwise connection 수는 N × (N - 1) / 2입니다.

3. 연결만 늘어나는 것이 아니다

Peering이 많아지면 connection object뿐 아니라 각 VPC route table, CIDR 충돌, 변경 영향 분석까지 함께 관리해야 합니다.

4. VPC Peering은 transitive하지 않다

A와 B, B와 C가 peering되어 있어도 A가 B를 경유해 C와 자동으로 통신할 수 없습니다. 이 특성 때문에 단순한 chaining으로 대규모 mesh를 줄이기 어렵습니다.

flowchart LR a[VPC A] <--> b[VPC B] b <--> c[VPC C] a -. no transitive routing .- c

5. Transit Gateway와 Hub-and-Spoke

Transit Gateway는 여러 VPC와 네트워크를 중앙 hub에 연결할 수 있도록 설계된 서비스입니다. 각 VPC가 서로 직접 peering하지 않고 TGW attachment를 통해 중앙 routing layer에 붙습니다.

flowchart TB tgw[Transit Gateway] a[VPC A] --> tgw b[VPC B] --> tgw c[VPC C] --> tgw d[VPC D] --> tgw e[VPC E] --> tgw

7. Transit Gateway Route Table로 segmentation하기

Transit Gateway에도 route table 개념이 있습니다. 이를 통해 prod, dev, shared services, security VPC의 통신 범위를 분리할 수 있습니다.

flowchart TB tgw[Transit Gateway] prod[Prod Route Table] --> prodVpc[Prod VPCs] prod --> shared[Shared Services] dev[Dev Route Table] --> devVpc[Dev VPCs] dev --> shared tgw --> prod tgw --> dev prodVpc -. blocked .- devVpc

8. Shared Services와 Hybrid 연결

대규모 AWS 환경에서는 DNS, logging, directory, security tooling 같은 공통 서비스를 별도 VPC에서 운영합니다. Transit Gateway를 사용하면 application VPC마다 shared services와 개별 peering을 맺을 필요가 줄어듭니다.

flowchart LR onprem[On-Premises] --- dx[VPN or Direct Connect] dx --- tgw[Transit Gateway] tgw --- appA[Application VPC A] tgw --- appB[Application VPC B] tgw --- shared[Shared Services VPC] tgw --- security[Security VPC]

9. VPN Mesh나 Direct Connect Gateway가 답이 아닌 이유

모든 VPC 사이에 VPN tunnel을 만드는 것은 VPC peering full mesh보다도 복잡합니다. Direct Connect Gateway는 on-premises 연결 확장을 위한 구성 요소이지, 동일 Region의 수많은 VPC 간 private routing hub 자체를 대체하는 답은 아닙니다.

10. Peering이 여전히 좋은 경우

몇 개의 VPC만 단순히 직접 연결한다면 VPC Peering이 더 단순하고 비용 면에서도 낫습니다. 선택 기준은 무조건 TGW가 아니라 network scale, operational complexity, routing requirements, segmentation, cost입니다.

Few VPCs + Simple Point-to-Point -> VPC Peering
Many VPCs + Centralized Routing + Segmentation -> Transit Gateway

마무리

Transit Gateway의 핵심 가치는 connection 수를 줄이는 것에만 있지 않습니다. 네트워크의 제어 지점을 중앙화해 routing, segmentation, shared services, hybrid connectivity를 확장 가능한 형태로 바꾸는 데 있습니다.
