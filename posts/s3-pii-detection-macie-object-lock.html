[AWS] S3에서 PII를 자동 탐지하고 삭제를 방지하기 - Macie + EventBridge + Object Lock

S3에 저장된 객체에서 PII가 발견되었을 때 단순 알림에서 끝내지 않고, 보안팀 검토 전 삭제되지 않도록 Legal Hold를 적용하는 이벤트 기반 보안 자동화 패턴을 정리한다.

2026.08.07 AWS S3 Security

S3를 데이터 레이크나 파일 저장소로 사용하다 보면 주민등록번호, 이메일 주소, 신용카드 정보와 같은 민감정보가 포함된 객체가 저장될 수 있다. 문제는 이러한 객체를 단순히 탐지하는 것만으로 충분하지 않을 수 있다는 점이다.

예를 들어 보안팀의 검토가 필요한 PII 객체가 발견되었다면 다음 세 가지가 필요하다.

  • 민감정보를 자동으로 탐지한다.
  • 탐지 결과를 이벤트로 전달한다.
  • 해당 객체가 검토 전에 삭제되지 않도록 보호한다.

이를 AWS 서비스로 구성하면 Amazon Macie, EventBridge, Lambda, S3 Object Lock을 조합한 이벤트 기반 보안 자동화 아키텍처를 만들 수 있다.

flowchart TB s3[Amazon S3
Data Bucket] macie[Amazon Macie
PII Detection] finding[Sensitive Data Finding] eventbridge[EventBridge
Finding Event] lambda[Lambda
Automated Response] lock[S3 Object Lock
Legal Hold] s3 --- macie macie --- finding finding --- eventbridge eventbridge --- lambda lambda --- lock

1. 문제 상황

다음과 같은 S3 버킷이 있다고 가정한다.

s3://company-data/

reports/
customer-data/
exports/
uploads/

다양한 시스템과 사용자가 파일을 업로드하면서 일부 객체에 PII가 포함될 가능성이 있다.

customer-data/customer-102.csv

name,email,card_number
Kim,kim@example.com,....

보안팀에서는 이런 객체를 발견하면 검토가 끝날 때까지 보존해야 한다. 사람이 모든 S3 객체를 직접 확인하는 방식은 데이터가 증가할수록 현실적이지 않다.

Detect
S3 객체에서 민감정보를 찾는다.
Event
탐지 결과를 후속 시스템으로 전달한다.
Protect
검토 전 삭제되지 않도록 객체 버전을 보호한다.

2. Amazon Macie로 민감정보 탐지

첫 번째 단계는 Amazon Macie다. Macie는 S3 객체를 분석하여 민감정보를 탐지할 수 있는 데이터 보안 서비스다. 개인정보, 자격 증명 관련 데이터, 금융정보, 기타 민감정보 패턴을 탐지하는 데 사용할 수 있다.

flowchart TB object[S3 Object] macie[Amazon Macie] finding[Sensitive Data Finding] object --- macie macie --- finding

즉 Macie의 역할은 어떤 S3 객체에 민감정보가 존재하는가를 찾아내는 것이다. 하지만 탐지만으로는 객체 삭제를 막을 수 없다.

3. Finding을 EventBridge로 전달

Macie는 생성한 finding을 Amazon EventBridge로 전달할 수 있다. 따라서 특정 유형의 finding이 발생했을 때 후속 작업을 자동으로 실행할 수 있다.

flowchart TB finding[Macie Finding] eventbridge[EventBridge] target[Target
Lambda] finding --- eventbridge eventbridge --- target

예를 들어 EventBridge rule은 Macie finding 이벤트 중 민감정보 탐지 결과만 대상으로 잡을 수 있다.

{
  "source": ["aws.macie"],
  "detail-type": ["Macie Finding"]
}

이렇게 하면 보안팀이 Macie 콘솔을 계속 확인하지 않아도 새로운 finding을 이벤트 기반으로 처리할 수 있다.

4. Lambda에서 대상 S3 객체 확인

EventBridge에서 호출된 Lambda는 Macie finding의 정보를 이용해 대상 객체를 식별한다. 개념적으로는 bucket, object key, version id를 확인한 뒤 해당 객체 버전에 Legal Hold를 적용한다.

flowchart TB eventbridge[EventBridge] lambda[Lambda] bucket[Bucket] key[Object Key] version[Version ID] eventbridge --- lambda lambda --- bucket lambda --- key lambda --- version

개념적인 Python 코드는 다음과 같다.

import boto3

s3 = boto3.client("s3")

def lambda_handler(event, context):
    bucket = get_bucket_from_finding(event)
    key = get_key_from_finding(event)
    version_id = get_version_from_finding(event)

    s3.put_object_legal_hold(
        Bucket=bucket,
        Key=key,
        VersionId=version_id,
        LegalHold={
            "Status": "ON"
        }
    )

실제 구현에서는 Macie finding의 구조를 검증하고, 어떤 finding을 자동 보존 대상으로 삼을지 필터링하는 로직이 추가로 필요하다.

5. 왜 Object Lock Legal Hold인가?

S3 Object Lock에는 크게 두 가지 보호 방식이 있다.

Retention Period
정해진 기간 동안 객체 버전 삭제를 제한한다.
Legal Hold
권한을 가진 사용자가 명시적으로 해제할 때까지 객체 버전을 보호한다.

Retention Period는 "이 객체를 1년 동안 삭제하지 못하게 한다"처럼 보호 기간이 정해져 있는 경우에 적합하다. 반면 Legal Hold는 "검토가 끝날 때까지 삭제하지 못하게 한다"처럼 종료 시점이 정해져 있지 않은 경우에 자연스럽다.

PII가 발견된 객체를 보안팀 검토가 끝날 때까지 보존한다.

6. 전체 처리 과정

전체 workflow를 정리하면 다음과 같다.

flowchart TB upload[Object Uploaded] s3[Amazon S3] macie[Amazon Macie
Sensitive Data Detection] eventbridge[EventBridge
Finding Event] lambda[Lambda
Automated Response] hold[S3 Object Lock
Legal Hold ON] upload --- s3 s3 --- macie macie --- eventbridge eventbridge --- lambda lambda --- hold

결과적으로 PII가 탐지된 객체는 자동으로 보존 대상이 된다.

7. 중요한 전제 - Object Lock은 미리 활성화해야 한다

이 아키텍처에서 놓치기 쉬운 부분이다. Lambda가 아무 S3 객체에나 갑자기 Object Lock을 적용할 수 있는 것은 아니다. 대상 버킷에는 S3 Object Lock이 활성화되어 있어야 하며 Versioning도 필요하다. 

S3 Bucket
Versioning: Enabled
Object Lock: Enabled

그 위에서 특정 객체 버전에 Legal Hold를 적용한다. Object Lock은 object version 단위로 동작한다는 점도 중요하다.

8. IAM 권한도 최소화한다

Lambda에는 모든 S3 권한을 줄 필요가 없다. Legal Hold를 적용하기 위해 필요한 권한을 중심으로 최소 권한 정책을 구성할 수 있다. 

s3:PutObjectLegalHold

대상 Resource 역시 가능하면 해당 버킷으로 제한한다.

flowchart TB role[Lambda Role] permission[PutObjectLegalHold] bucket[company-data/*] role --- permission permission --- bucket

이를 통해 보안 자동화를 수행하는 Lambda 자체도 최소 권한 원칙에 맞출 수 있다.

9. 보안팀의 검토가 끝난 후

Legal Hold는 자동으로 만료되지 않는다. 검토가 완료되면 권한을 가진 보안 담당자 또는 별도의 승인 workflow를 통해 Legal Hold를 해제할 수 있다.

flowchart TB detected[PII 발견] hold[Legal Hold ON] review[Security Review] decision[Decision] keep[Hold 유지] release[Hold OFF] detected --- hold hold --- review review --- decision decision --- keep decision --- release

이 과정까지 자동화한다면 승인 시스템이나 Step Functions 등을 추가하여 보안 검토 workflow로 확장할 수도 있다.

10. 왜 Glacier로 옮기는 것만으로는 부족할까?

PII가 포함된 객체를 Glacier Deep Archive 같은 저비용 스토리지 클래스로 이동시키는 방법을 생각할 수도 있다. 하지만 스토리지 클래스는 주로 비용과 접근 특성을 결정한다. 객체를 다른 스토리지 클래스로 이동했다고 해서 보안팀 검토 전 삭제를 방지한다는 요구사항이 자동으로 충족되는 것은 아니다.

이 문제의 핵심은 저장 비용이 아니라 immutability와 deletion protection이다.

11. Retention과 Legal Hold 선택 기준

요구사항 선택
반드시 7년 보존 Retention
규정상 1년간 절대 삭제 금지 Compliance Mode Retention
관리자가 필요한 경우 예외 처리 가능 Governance Mode Retention
조사 종료 시점까지 보존 Legal Hold
감사 완료 시점까지 보존 Legal Hold

기간이 정해져 있다면 Retention이 맞고, 언제 끝날지 모른다면 Legal Hold가 더 자연스럽다.

12. 아키텍처를 확장한다면

실제 보안 시스템에서는 알림과 승인 단계를 함께 붙일 수 있다. 단순히 객체를 보호하는 것에서 끝내지 않고, 보안팀이 확인하고 유지 또는 해제를 결정하는 workflow까지 연결하는 방식이다.

flowchart TB macie[Amazon Macie] eventbridge[EventBridge] lambda[Lambda] sns[SNS
Security Team Alert] lock[Object Lock
Legal Hold] approval[Security Approval] decision[Hold 유지 / 해제] macie --- eventbridge eventbridge --- lambda lambda --- sns lambda --- lock lock --- approval approval --- decision

13. 정리

이 아키텍처의 핵심은 각각의 AWS 서비스가 서로 다른 책임을 담당한다는 것이다.

Macie
민감정보를 탐지한다.
EventBridge
탐지 결과를 이벤트로 라우팅한다.
Lambda
보안 이벤트에 자동으로 대응한다.
Object Lock
검토 대상 객체 버전을 보호한다.

이를 조합하면 단순히 민감정보가 존재한다는 사실을 알려주는 것에서 끝나지 않고 민감정보 탐지, 이벤트 발생, 자동 대응, 객체 보호까지 연결되는 이벤트 기반 보안 자동화 구조를 만들 수 있다.

결국 중요한 것은 보안 이벤트를 발견하는 것만이 아니라, 발견된 보안 이벤트에 시스템이 어떻게 자동으로 대응할 것인가까지 설계하는 것이다.
