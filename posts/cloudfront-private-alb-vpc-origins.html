[AWS] CloudFront 뒤의 ALB를 Private하게 구성하기 - VPC Origins

CloudFront를 웹 애플리케이션의 앞단에 두더라도 Origin이 Public ALB라면 직접 접근 경로가 남을 수 있다. CloudFront VPC Origins를 사용해 Internal ALB를 Private Origin으로 구성하는 방식을 정리한다.

웹 애플리케이션의 앞단에 Amazon CloudFront를 배치하면 CDN 캐싱, TLS 종료, AWS WAF 연동 등 여러 기능을 사용할 수 있다.

일반적인 구조는 다음과 같다.

flowchart TB users[Users] cloudfront[CloudFront] alb[Public ALB] app[EC2 / ECS] users --- cloudfront cloudfront --- alb alb --- app

하지만 ALB가 Public Internet에서 접근 가능하다면 사용자가 CloudFront를 거치지 않고 ALB에 직접 접근할 가능성이 있다. CloudFront에서 WAF, 캐싱, 요청 제어 등의 정책을 적용하고 있다면 Origin에 대한 직접 접근은 이러한 제어를 우회할 수 있다.

flowchart LR user[User] cf[CloudFront] publicAlb[Public ALB] attacker[Direct Client] user --- cf cf --- publicAlb attacker --- publicAlb

이를 해결하기 위해 사용할 수 있는 방법 중 하나가 CloudFront VPC Origins다.

1. 목표 아키텍처

VPC Origin을 사용하면 ALB를 private subnet에 배치하고 CloudFront가 VPC 내부의 Origin에 접근하도록 구성할 수 있다.

flowchart TB internet[Internet] cf[CloudFront] vpcOrigin[VPC Origin] subgraph vpc[VPC] subgraph private[Private Subnets] alb[Internal ALB] ec2a[EC2] ec2b[EC2] end end internet --- cf cf --- vpcOrigin vpcOrigin --- alb alb --- ec2a alb --- ec2b

사용자는 CloudFront에만 접근한다. ALB 자체는 인터넷에서 직접 접근할 수 없다.

2. Public ALB 방식의 문제

기존에는 CloudFront가 Internet-facing ALB로 요청을 전달하는 구조를 많이 사용한다. 이 경우 ALB에는 Public Endpoint가 존재한다.

정상 경로
User, CloudFront, Public ALB 순서로 요청이 전달된다.
우회 경로
ALB DNS 이름을 알면 CloudFront를 거치지 않고 ALB로 직접 접근할 수 있다.

이 경우 CloudFront에만 적용한 보안 정책을 Origin에서 다시 구현해야 할 수 있다.

3. 기존의 우회 방지 방법

VPC Origins 이전에는 CloudFront가 Origin 요청에 특정 Custom Header를 추가하고, ALB Listener Rule에서 해당 Header를 검사하는 방법을 사용할 수 있었다.

flowchart TB cf[CloudFront
X-Origin-Secret] alb[ALB Listener Rule] forward[Forward] reject[Reject] cf --- alb alb --- forward alb --- reject

또 다른 접근은 CloudFront의 IP Range를 이용해 Security Group이나 Network Layer에서 제한하는 방식이다. 하지만 CloudFront IP Range 변경, Security Rule 관리, Secret 관리 같은 추가적인 운영 부담이 생긴다.

VPC Origin을 사용하면 Origin 자체를 Private Network 안에 둘 수 있다.

4. CloudFront VPC Origin

CloudFront VPC Origin은 CloudFront가 VPC 내부의 리소스를 Origin으로 사용할 수 있게 해준다. 대표적으로 다음 리소스를 사용할 수 있다.

  • Application Load Balancer
  • Network Load Balancer
  • EC2 Instance

이 구조의 핵심은 Origin에 Public IP나 Internet-facing Endpoint가 필요하지 않다는 점이다.

5. Private ALB 구성

예를 들어 ALB를 다음과 같이 생성한다고 가정한다.

Scheme:
Internal

Subnets:
Private Subnet A
Private Subnet B

애플리케이션 서버 역시 Private Subnet에 위치한다.

VPC

Private Subnet A
├── ALB
└── EC2

Private Subnet B
├── ALB
└── EC2

외부 사용자는 ALB에 직접 연결할 수 없다. CloudFront VPC Origin을 통해서만 접근한다.

6. Request Flow

전체 요청 흐름은 다음과 같다.

flowchart TB request[User Request] cf[CloudFront
Cache / WAF / TLS / Routing] origin[VPC Origin] alb[Internal ALB] app[EC2 / ECS] request --- cf cf --- origin origin --- alb alb --- app

따라서 애플리케이션의 Public Entry Point를 CloudFront 하나로 제한할 수 있다.

7. Security 관점의 장점

이 구조는 Defense in Depth 측면에서 의미가 있다.

Public ALB 구조
CloudFront 경로와 ALB 직접 접근 경로가 함께 존재할 수 있다.
VPC Origin 구조
Origin 자체가 Public Network에 노출되지 않아 우회 경로를 구조적으로 줄일 수 있다.

8. WAF와 결합

CloudFront에는 AWS WAF를 연결할 수 있다.

flowchart TB internet[Internet] waf[AWS WAF] cf[CloudFront] origin[VPC Origin] alb[Private ALB] internet --- waf waf --- cf cf --- origin origin --- alb

WAF에서 다음과 같은 정책을 적용할 수 있다.

  • SQL Injection
  • XSS
  • IP Reputation
  • Geo Restriction
  • Rate Limiting
  • Managed Rule Groups

이 경우 인터넷에서 들어오는 요청의 주요 보안 제어 지점을 CloudFront/WAF 계층으로 집중시킬 수 있다.

9. CloudFront와 ALB의 역할 분리

CloudFront
CDN, Edge Cache, TLS, WAF Integration, Global Edge Network
ALB
Application Load Balancing, Host-based Routing, Path-based Routing, Target Health Check
flowchart TB user[User] cf[CloudFront] alb[ALB] app[Application] user --- cf cf --- alb alb --- app

각 계층이 서로 다른 역할을 담당한다.

10. Security Group

Private ALB라고 하더라도 Security Group은 최소 권한으로 구성해야 한다.

flowchart TB origin[CloudFront VPC Origin] albSg[ALB Security Group] appSg[Application Security Group] app[Application
8080] origin --- albSg albSg --- appSg appSg --- app

ALB에서 애플리케이션으로 전달되는 트래픽 역시 필요한 Port만 허용한다.

11. Public ALB + CloudFront와 비교

Public ALB 방식
구성이 단순하지만 Origin이 Internet-facing이고 Direct Origin Access를 별도로 제한해야 한다.
VPC Origin 방식
Origin을 Public Internet에서 숨기고 CloudFront를 Public Entry Point로 집중할 수 있다.

다만 VPC Origin 관련 네트워크 요구사항과 CloudFront 기능 조합의 제약사항은 실제 구성 전에 확인해야 한다.

12. 언제 적합할까?

CloudFront를 반드시 거쳐야 하는 서비스

WAF 정책을 CloudFront에서 중앙 관리하는 서비스라면 CloudFront를 필수 진입점으로 둘 수 있다.

Origin 직접 접근을 최소화해야 하는 서비스

Origin Endpoint를 Public Internet에 노출할 이유가 없다면 VPC Origin을 고려할 수 있다.

Private Application Architecture

Public Layer를 최소화하고 ALB, ECS, EC2, RDS를 Private 영역에 두고 싶은 경우에도 적합하다.

13. 전체 Architecture

flowchart TB internet[Internet] waf[AWS WAF] cf[CloudFront] origin[VPC Origin] subgraph vpc[VPC] subgraph private[Private Subnets] alb[Internal ALB] ecs[ECS] ec2[EC2] rds[RDS] end end internet --- waf waf --- cf cf --- origin origin --- alb alb --- ecs alb --- ec2 ecs --- rds ec2 --- rds

Public Internet에 직접 노출되는 애플리케이션 계층을 최소화하면서 CloudFront의 Edge 기능과 ALB의 Layer 7 Load Balancing을 함께 사용할 수 있다.

정리

CloudFront를 사용하더라도 Origin이 Public ALB라면 CloudFront를 거치지 않는 직접 접근 경로가 존재할 수 있다. 기존에는 Security Group, CloudFront IP Range, Custom Header 등의 방식으로 Origin Access를 제한하는 구조를 사용할 수 있었다.

CloudFront VPC Origins를 사용하면 ALB 자체를 Private하게 구성하고 CloudFront가 VPC 내부의 Origin에 접근하도록 만들 수 있다.

CloudFront
Public Edge Layer
VPC Origin
CloudFront와 Private VPC Resource의 연결
Internal ALB
Private Application Routing Layer

웹 애플리케이션에서 CloudFront를 필수 진입점으로 사용하고 Origin을 인터넷에 공개할 필요가 없다면 CloudFront VPC Origin + Internal ALB 구조를 고려할 수 있다.
