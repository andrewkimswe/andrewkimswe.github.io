[AWS/Security] 취약점은 찾았는데 패치는 누가 하지? - Amazon Inspector와 Systems Manager로 EC2 패치 관리하기

Amazon Inspector는 무엇이 취약한지 찾고, Systems Manager Patch Manager는 패치를 어떻게 관리할지 다룬다. EC2 환경에서 취약점 발견과 패치 운영을 분리해 보는 글이다.

수백 대의 EC2 인스턴스를 운영하고 있다고 가정해보자.

보안팀에서 다음과 같은 취약점이 발견됐다고 알려왔다.

EC2 Instance
   ↓
Outdated Package
   ↓
Known CVE
   ↓
Security Finding

여기서 문제는 취약점을 발견하는 것만으로 끝나지 않는다는 것이다.

운영 관점에서는 다음 질문까지 답해야 한다.

  • 어떤 인스턴스가 취약한가?
  • 어떤 패치가 필요한가?
  • 언제 적용할 것인가?
  • 한꺼번에 적용해도 되는가?
  • 패치가 제대로 적용됐는가?
  • 실패한 인스턴스는 무엇인가?

AWS에서는 이 문제를 크게 두 영역으로 나눌 수 있다.

Amazon Inspector
      │
      ▼
Vulnerability Detection

AWS Systems Manager Patch Manager
      │
      ▼
Patch Management

즉,

Inspector는 무엇이 취약한지 찾고, Patch Manager는 패치를 어떻게 관리할지를 담당한다.

이 글에서는 두 서비스를 중심으로 대규모 EC2 환경의 취약점 관리와 패치 운영 구조를 살펴본다.

1. Detection과 Remediation은 다른 문제다

보안 운영에서 가장 먼저 구분해야 할 개념이다.

Detection

"이 서버에 취약한 패키지가 있다."

Remediation

"그 취약점을 해결하기 위해 패치를 적용한다."

하나의 도구가 모든 것을 처리한다고 생각하기 쉽지만, 역할을 분리하면 아키텍처가 훨씬 명확해진다.

EC2 Fleet
   │
   ├──────────────► Amazon Inspector
   │                    │
   │                    ▼
   │              Vulnerability
   │                 Findings
   │
   └──────────────► Systems Manager
                        │
                        ▼
                  Patch Manager
                        │
                        ▼
                   Compliance

2. Amazon Inspector의 역할

Amazon Inspector는 AWS 워크로드를 지속적으로 스캔해 소프트웨어 취약점 등의 문제를 식별하는 vulnerability management 서비스다.

EC2 관점에서 생각하면:

EC2
 ↓
Installed software/package information
 ↓
Inspector
 ↓
Known vulnerability analysis
 ↓
Finding

Finding에는 어떤 리소스에서 어떤 취약점이 발견됐는지와 같은 정보가 포함된다.

따라서 Inspector의 핵심 질문은 다음이다.

"현재 내 AWS 워크로드에서 알려진 취약점은 어디에 존재하는가?"

3. GuardDuty와 Inspector를 혼동하면 안 된다

AWS 보안 서비스를 공부할 때 자주 헷갈리는 부분이다.

둘 다 "보안 문제를 찾는 서비스"처럼 보이기 때문이다.

하지만 질문이 다르다.

Inspector

"이 EC2에 취약한 소프트웨어가 설치되어 있는가?"

GuardDuty

"현재 AWS 환경에서 의심스러운 활동이나 위협 징후가 발생하고 있는가?"

단순화하면:

Inspector
= Vulnerability

GuardDuty
= Threat / Suspicious Activity

예를 들어 오래된 패키지에 알려진 CVE가 있는지 확인하려는 문제라면 Inspector의 영역이다.

반면 비정상적인 API 호출이나 의심스러운 행위 등을 탐지하려는 문제는 GuardDuty 쪽에 가깝다.

4. Inspector가 취약점을 찾았다고 패치가 끝난 것은 아니다

Inspector에서 Finding이 발생했다고 하자.

Instance: i-xxxxxxxx
Package: example-package
Severity: HIGH
Status: ACTIVE

이제 운영자는 실제 서버를 수정해야 한다.

수십 대라면 사람이 SSH로 접속해서 패치할 수도 있을 것이다.

하지만 수백 또는 수천 대라면?

Engineer
 ├── SSH → EC2 #1
 ├── SSH → EC2 #2
 ├── SSH → EC2 #3
 ├── ...
 └── SSH → EC2 #500

확장성이 없다.

더 큰 문제는 패치 결과를 일관되게 관리하기 어렵다는 것이다.

그래서 Systems Manager를 사용한다.

5. AWS Systems Manager Patch Manager

Patch Manager는 관리 대상 노드의 패치 작업을 자동화하는 데 사용할 수 있다.

운영자가 원하는 것은 단순히:

yum update

를 여러 서버에서 실행하는 것이 아니다.

실제로는 다음과 같은 정책이 필요하다.

어떤 패치를
    +
어떤 서버에
    +
언제
    +
어떤 기준으로
    +
어떤 순서로

적용할지를 결정해야 한다.

Patch Manager를 사용하면 이러한 패치 관리 프로세스를 중앙화할 수 있다.

6. Patch Baseline

모든 패치를 발견 즉시 production에 설치하는 것이 항상 좋은 전략은 아니다.

예를 들어 특정 업데이트가 애플리케이션과 호환되지 않을 수도 있다.

따라서 패치 관리에는 기준이 필요하다.

개념적으로:

Available Patches
      │
      ▼
Patch Baseline
      │
      ├── Approved
      ├── Rejected
      └── Approval Rules

Patch baseline은 어떤 패치를 승인된 것으로 간주할지를 정의한다.

예를 들어 조직의 정책에 따라:

Critical security patches
        ↓
빠르게 승인

일반 업데이트
        ↓
검증 기간 이후 승인

같은 정책을 구성할 수 있다.

핵심은 패치 작업을 단순 명령 실행이 아니라 정책 기반 관리로 바꾸는 것이다.

7. Scan과 Install을 분리한다

패치 관리에는 두 가지 중요한 작업이 있다.

Scan

현재 인스턴스가
패치 기준을 만족하는가?

Install

필요한 승인 패치를
실제로 설치한다.

따라서 다음과 같은 운영 흐름을 구성할 수 있다.

Scan
 ↓
Compliance 확인
 ↓
Maintenance Window
 ↓
Install
 ↓
Re-scan
 ↓
Compliance 확인

이렇게 하면 단순히 "패치 명령을 실행했다"가 아니라 실제 패치 상태를 검증하는 과정까지 포함할 수 있다.
