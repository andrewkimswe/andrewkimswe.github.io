[AWS/Security] EC2 패치 자동화는 어디까지 자동화해야 할까? - Maintenance Window, Compliance, Staged Rollout

취약점 발견 이후의 패치 자동화는 언제, 어떤 순서로, 어떻게 검증할지의 문제다. Maintenance Window, staged rollout, compliance를 중심으로 EC2 패치 운영 흐름을 정리한다.

2026.08.16 AWS Security Systems Manager

EC2 취약점을 찾고 패치 기준을 정했다면, 다음 문제는 운영 환경에서 언제 어떻게 적용할 것인가다.

패치는 보안 작업이지만 동시에 production 변경 작업이다. 따라서 Maintenance Window, staged rollout, health check, compliance report까지 하나의 운영 흐름으로 설계해야 한다.

1. 패치는 언제 실행해야 할까?

운영 서버에 아무 시간이나 패치를 설치하면 위험하다.

패치가 다음을 유발할 수 있기 때문이다.

  • 프로세스 재시작
  • OS reboot
  • dependency 변경
  • application incompatibility
  • 일시적인 capacity 감소

따라서 패치 작업은 일반적으로 정해진 유지보수 시간과 연결된다.

Maintenance Window
        │
        ▼
Target Instances
        │
        ▼
Patch Operation
        │
        ▼
Verification

예:

Sunday 03:00
     ↓
Patch Group A
     ↓
Install
     ↓
Reboot if required
     ↓
Health Check

2. 모든 서버를 동시에 패치하면 안 되는 이유

예를 들어 웹 애플리케이션이 EC2 100대로 구성되어 있다고 하자.

ALB
 │
 ├── EC2
 ├── EC2
 ├── EC2
 ├── ...
 └── EC2

100대를 동시에 패치하고 재부팅하면 패치 시스템은 성공했더라도 서비스는 실패할 수 있다.

따라서 실제 운영에서는 단계적 rollout이 중요하다.

예를 들어:

Wave 1
5 instances
   ↓
Validation
   ↓
Wave 2
20 instances
   ↓
Validation
   ↓
Remaining fleet

혹은 태그를 이용해 환경을 분리할 수도 있다.

Environment=dev
        ↓
Environment=staging
        ↓
Environment=production

production에서도:

PatchGroup=prod-canary
        ↓
PatchGroup=prod-a
        ↓
PatchGroup=prod-b

처럼 나눌 수 있다.

이렇게 하면 패치 자체가 장애를 만드는 blast radius를 줄일 수 있다.

3. Vulnerability Finding이 발생하면 즉시 자동 패치해야 할까?

다음 구조는 매우 매력적으로 보인다.

Inspector
   ↓
Finding
   ↓
EventBridge
   ↓
Automation
   ↓
Patch immediately

하지만 production에서는 신중해야 한다.

취약점이 발견됐다는 사실과 지금 즉시 모든 production 서버를 변경해도 안전하다는 사실은 동일하지 않다.

예를 들어:

Critical CVE 발견
      │
      ▼
Risk Assessment
      │
      ▼
Test Environment
      │
      ▼
Canary
      │
      ▼
Production Rollout

같은 흐름이 더 적절할 수 있다.

따라서 자동화의 목표를:

"사람을 완전히 제거한다."

로 잡기보다

"반복 가능한 정책과 안전장치 안에서 사람이 직접 수행해야 하는 작업을 줄인다."

라고 보는 것이 좋다.

4. Compliance가 중요한 이유

대규모 환경에서 운영자가 알고 싶은 것은 단순히:

"어제 패치 작업을 실행했는가?"

가 아니다.

더 중요한 질문은:

"현재 몇 대가 조직의 패치 정책을 준수하고 있는가?"

이다.

예를 들어:

EC2 Fleet: 500

Compliant:      472
Non-Compliant:   23
Unknown:          5

이런 형태의 상태를 확인할 수 있어야 한다.

패치 자동화의 최종 결과는 command execution이 아니라 desired security state에 대한 compliance라고 볼 수 있다.

5. 운영 구조

전체 흐름을 조금 더 확장하면 다음처럼 생각할 수 있다.

                    ┌──────────────────┐
                    │     EC2 Fleet    │
                    └────────┬─────────┘
                             │
              ┌──────────────┴──────────────┐
              │                             │
              ▼                             ▼
     ┌─────────────────┐          ┌─────────────────┐
     │ Amazon Inspector│          │ Systems Manager │
     └────────┬────────┘          └────────┬────────┘
              │                            │
              ▼                            ▼
     Vulnerability Finding           Patch Manager
              │                            │
              │                            ▼
              │                     Patch Baseline
              │                            │
              │                            ▼
              │                    Maintenance Window
              │                            │
              └────────────┐               ▼
                           │          Patch Execution
                           │               │
                           ▼               ▼
                     Security / Ops    Compliance

여기에 EventBridge와 SNS 등을 추가하면 Finding notification 또는 후속 workflow를 만들 수도 있다.

Inspector Finding
       ↓
EventBridge
       ↓
Severity Filtering
       ↓
SNS / Automation Workflow
       ↓
Security / Operations

중요한 것은 notification과 실제 production remediation을 반드시 동일한 자동화 단계로 묶을 필요는 없다는 점이다.

6. Immutable Infrastructure라면 이야기가 달라진다

여기까지는 실행 중인 EC2를 직접 패치하는 patch-in-place 방식이었다.

하지만 현대적인 인프라에서는 다른 방법도 있다.

Old AMI
   ↓
Patch / Build
   ↓
New AMI
   ↓
New EC2 instances
   ↓
Traffic shift
   ↓
Old instances terminate

즉 기존 서버를 수정하지 않고 새로운 이미지를 만들어 교체하는 방식이다.

두 전략을 비교하면:

방식 Patch-in-place Immutable replacement
기존 서버 직접 수정 교체
Patch Manager 매우 적합 일부 역할
일관성 관리 필요 상대적으로 높음
Legacy workload 적합 전환 비용 존재
Auto Scaling 기반 서비스 가능 특히 잘 맞음

따라서 Patch Manager가 존재한다고 해서 모든 EC2 아키텍처가 반드시 patch-in-place를 사용해야 한다는 의미는 아니다.

환경의 특성에 따라 선택해야 한다.

7. 실패까지 생각해야 한다

패치 작업은 항상 성공하지 않는다.

Patch
  ↓
Install Failure

또는:

Patch
  ↓
Reboot
  ↓
Application fails to start

가 발생할 수 있다.

따라서 운영 관점에서는:

Patch
 ↓
Instance health
 ↓
Application health
 ↓
Compliance

를 함께 확인해야 한다.

패키지가 최신 상태라는 사실만으로 서비스가 정상이라는 것을 보장할 수 없기 때문이다.

예를 들어 ALB 기반 서비스라면 패치 이후 target health를 확인하는 것도 중요한 검증 수단이 될 수 있다.

8. 패치 자동화의 목표

자동화라고 하면 흔히 다음 구조를 떠올린다.

Schedule
 ↓
Patch all
 ↓
Done

하지만 운영 환경에서 필요한 것은 더 긴 lifecycle이다.

Discover
   ↓
Prioritize
   ↓
Approve
   ↓
Schedule
   ↓
Patch
   ↓
Verify
   ↓
Report

AWS 서비스에 대응시키면 대략 다음과 같다.

Inspector
   ↓
Vulnerability discovery

Patch Baseline / Policy
   ↓
Patch decision

Systems Manager
   ↓
Execution

Compliance
   ↓
Verification / reporting

즉 보안 패치 관리는 하나의 API 호출이 아니라 지속적인 운영 프로세스다.

10. 정리

EC2 보안 패치 문제를 단순하게 생각하면:

서버가 오래됐다.
      ↓
업데이트한다.

로 끝난다.

하지만 서버 수가 늘어나면 문제는 다음처럼 변한다.

What is vulnerable?
        ↓
What should be patched?
        ↓
When should it be patched?
        ↓
How should it be rolled out?
        ↓
Did the patch succeed?
        ↓
Is the application still healthy?
        ↓
Are all instances compliant?

여기서 각 서비스의 역할을 기억하면 명확하다.

Amazon Inspector
= 취약점을 발견한다.

Systems Manager Patch Manager
= 패치 작업을 관리한다.

Patch Baseline / Policy
= 어떤 패치를 적용할지 결정한다.

Maintenance Window
= 언제 변경할지 통제한다.

Compliance
= 현재 원하는 상태에 도달했는지 확인한다.

결국 패치 자동화의 핵심은 업데이트 명령을 자동으로 실행하는 것이 아니다.

취약점 발견부터 변경, 검증, 보고까지 반복 가능한 운영 프로세스로 만드는 것

이것이 대규모 EC2 환경에서 패치 관리가 필요한 이유다.
