[AWS] S3 Data Lake에서 Lake Formation으로 Row-Level Access Control 구현하기

여러 팀이 하나의 S3 Data Lake를 공유할 때, 같은 테이블을 사용하면서도 사용자의 역할에 따라 조회 가능한 Row와 Column을 다르게 제한하는 패턴을 정리한다.

2026.08.31 AWS Lake Formation Data Governance

여러 팀이 하나의 S3 Data Lake를 공유하는 환경에서는 단순히 "이 사용자가 S3에 접근할 수 있는가?"만으로는 충분하지 않을 수 있다.

예를 들어 글로벌 서비스에서 국가별 데이터를 하나의 테이블에 저장한다고 가정해보자. 

s3://company-data-lake/
└── battery/
    └── battery_metrics.parquet

데이터에는 다음과 같이 여러 국가의 정보가 함께 저장되어 있다.

device_id | region | soh | voltage
----------|--------|-----|--------
EV-001    | KR     | 92  | 401
EV-002    | JP     | 88  | 398
EV-003    | US     | 95  | 405
EV-004    | KR     | 90  | 400

이때 다음과 같은 접근 정책이 필요하다고 가정한다.

  • 한국 분석팀은 region = 'KR' 데이터만 조회
  • 일본 분석팀은 region = 'JP' 데이터만 조회
  • 글로벌 데이터팀은 모든 지역 데이터 조회

모든 팀이 같은 테이블을 사용하지만 사용자의 역할에 따라 조회할 수 있는 Row가 달라져야 한다. 이러한 Fine-Grained Access Control은 AWS Lake Formation의 Data Filter를 이용해 구현할 수 있다.

Architecture

flowchart TB s3[Amazon S3
Data Lake] glue[AWS Glue Data Catalog
battery_db.battery_metrics] lake[AWS Lake Formation
Data Filters] kr[KR Team
region = KR] jp[JP Team
region = JP] global[Global Team
All Rows] athena[Amazon Athena] s3 --- glue glue --- lake lake --- kr lake --- jp lake --- global kr --- athena jp --- athena global --- athena

핵심은 데이터를 팀별 S3 Bucket이나 별도의 테이블로 복제하지 않고, 하나의 Data Lake와 Data Catalog Table을 유지하면서 Lake Formation에서 논리적으로 접근 범위를 제한하는 것이다.

1. 왜 IAM과 S3 Bucket Policy만으로는 부족할까?

S3와 IAM을 이용하면 다음과 같은 Resource-Level Access Control을 구현할 수 있다.

Team A: bucket-a 접근 허용
Team B: bucket-b 접근 허용

Prefix를 기준으로 권한을 분리하는 것도 가능하다.

s3://data-lake/korea/*
s3://data-lake/japan/*

하지만 요구사항이 다음과 같다면 이야기가 달라진다.

하나의 Table

device_id | region | soh
----------|--------|----
EV-001    | KR     | 92
EV-002    | JP     | 88
EV-003    | US     | 95

한국팀에는 첫 번째 Row만 보여주고, 일본팀에는 두 번째 Row만 보여줘야 한다. 즉 접근 제어의 대상이 S3 Object가 아니라 Table 내부의 데이터가 된다.

IAM / S3 Policy
Bucket / Object 수준 접근 제어
Lake Formation
Table / Column / Row / Cell 수준 접근 제어

이런 경우 Lake Formation을 Data Lake의 Governance Layer로 사용할 수 있다.

2. S3 데이터를 Glue Data Catalog에 등록

Lake Formation의 Fine-Grained Access Control은 Data Catalog의 Table을 기준으로 적용할 수 있다. 따라서 S3의 데이터를 AWS Glue Data Catalog에 등록한다. 

Database: battery_db
Table: battery_metrics

Columns:
- device_id
- region
- soh
- voltage
flowchart LR object[S3
Physical Data
battery_metrics.parquet] catalog[Glue Data Catalog
Metadata
battery_db.battery_metrics] lake[AWS Lake Formation
Permissions and Filters] object --- catalog catalog --- lake

Lake Formation은 이 Data Catalog Table을 대상으로 권한과 Data Filter를 관리한다.

3. Lake Formation Data Filter 생성

한국 분석팀이 KR 데이터만 조회할 수 있도록 Row Filter를 생성한다. 개념적으로 다음 SQL 조건과 같다. 

region = 'KR'

예를 들어 Data Filter를 다음과 같이 정의할 수 있다.

Filter Name:
kr-region-filter

Database:
battery_db

Table:
battery_metrics

Column Access:
All Columns

Row Filter:
region = 'KR'

일본팀에는 별도의 Filter를 생성한다.

Filter Name:
jp-region-filter

Row Filter:
region = 'JP'
flowchart TB table[battery_metrics] krFilter[KR Filter
region = KR] jpFilter[JP Filter
region = JP] noFilter[No Filter
All Rows] krAnalyst[KR Analyst] jpAnalyst[JP Analyst] globalAnalyst[Global Analyst] table --- krFilter table --- jpFilter table --- noFilter krFilter --- krAnalyst jpFilter --- jpAnalyst noFilter --- globalAnalyst

4. IAM Principal에 Filter 기반 SELECT 권한 부여

Data Filter를 생성한 뒤 해당 Filter를 IAM User 또는 IAM Role에 연결하여 SELECT 권한을 부여한다. 

Role:
KRDataAnalystRole

Permission:
SELECT

Resource:
battery_db.battery_metrics

Data Filter:
kr-region-filter

이제 KRDataAnalystRole을 사용하는 사용자가 Athena에서 다음 쿼리를 실행한다고 가정하자. 

SELECT *
FROM battery_db.battery_metrics;

원본 데이터가 다음과 같더라도,

EV-001 | KR | 92 | 401
EV-002 | JP | 88 | 398
EV-003 | US | 95 | 405
EV-004 | KR | 90 | 400

한국 분석팀에는 허용된 Row만 반환되도록 접근 범위를 제한할 수 있다.

EV-001 | KR | 92 | 401
EV-004 | KR | 90 | 400

애플리케이션이나 분석가가 매번 WHERE region = 'KR' 조건을 직접 추가할 필요가 없다. 접근 정책을 데이터 소비자의 쿼리 로직에 의존하지 않고 Data Governance Layer에서 중앙 관리할 수 있다는 것이 중요한 차이점이다.

5. Column-Level Security와 결합하기

Lake Formation Data Filter는 Row뿐만 아니라 Column 접근도 제한할 수 있다.

device_id
region
customer_id
battery_serial
soh
voltage

분석팀에는 배터리 분석에 필요한 정보만 제공하고 customer_id와 같은 개인정보는 노출하고 싶지 않을 수 있다. 

Row Filter:
region = 'KR'

Allowed Columns:
device_id
region
battery_serial
soh
voltage
flowchart LR row[Row Security
region = KR] column[Column Security
customer_id excluded] cell[Cell-Level Security] row --- column column --- cell

즉 사용자의 역할에 따라 어떤 Row와 어떤 Column을 동시에 볼 수 있는지 제어할 수 있다.

6. Athena에서 조회

Lake Formation은 Athena와 통합하여 S3 Data Lake에 대한 Fine-Grained Access Control을 적용할 수 있다.

flowchart TB analyst[Analyst] athena[Amazon Athena] lake[AWS Lake Formation
Authorization] glue[AWS Glue Data Catalog] s3[Amazon S3] analyst --- athena athena --- lake lake --- glue glue --- s3

사용자가 Athena에서 쿼리를 실행하면 Lake Formation에 설정된 권한에 따라 접근 가능한 데이터 범위가 결정된다. 이를 통해 데이터 분석가는 동일한 Table을 사용하면서도 자신의 역할에 허용된 데이터만 조회할 수 있다.

7. 팀별 데이터 복제와 비교

Lake Formation 없이 접근 범위를 물리적으로 분리한다면 다음과 같은 구조를 고려할 수도 있다.

S3
├── korea-data/
├── japan-data/
└── us-data/

또는 별도의 Table을 만들 수도 있다.

battery_kr
battery_jp
battery_us

하지만 데이터 소비자가 늘어날수록 데이터 복제와 권한 관리가 복잡해질 수 있다. Lake Formation을 이용하면 데이터와 접근 정책을 분리하여 관리할 수 있다.

flowchart TB lake[Single Data Lake] table[Single Table] governance[Lake Formation] kr[KR Team] jp[JP Team] us[US Team] lake --- table table --- governance governance --- kr governance --- jp governance --- us

8. Lake Formation의 역할

전체 구조에서 각 서비스의 역할은 다음과 같이 정리할 수 있다.

Amazon S3
실제 Data Lake Storage
AWS Glue Data Catalog
데이터의 Schema와 Metadata 관리
AWS Lake Formation
데이터 접근 정책 및 Fine-Grained Access Control
Amazon Athena
SQL 기반 데이터 조회 및 분석
IAM
사용자 및 Role의 인증과 AWS 권한 기반 제공

특히 IAM과 Lake Formation의 역할을 구분하는 것이 중요하다.

IAM: 이 사용자는 누구이며 어떤 AWS 작업을 수행할 수 있는가?

Lake Formation: 이 사용자가 이 Data Lake에서 실제로 어떤 데이터를 볼 수 있는가?

실제 권한 모델에서는 IAM과 Lake Formation이 함께 작동하며, Lake Formation이 Data Lake에 대한 보다 세밀한 데이터 접근 제어를 담당한다.

9. 언제 Row-Level Security가 유용할까?

대표적으로 다음과 같은 Multi-Tenant 또는 Data Governance 환경에서 사용할 수 있다.

지역별 데이터 분리

KR Team: region = 'KR'
JP Team: region = 'JP'
US Team: region = 'US'

고객별 데이터 분리

Customer A: tenant_id = 'A'
Customer B: tenant_id = 'B'

부서별 데이터 분리

Sales: department = 'SALES'
Finance: department = 'FINANCE'

민감 데이터 접근 제한

Row Filter와 Column Filter를 조합하여 특정 조직에 필요한 데이터만 제공할 수 있다.

정리

S3 Data Lake에서 IAM과 Bucket Policy는 기본적인 Resource-Level Access Control을 제공하지만, 동일한 데이터셋 내부에서 사용자별로 접근 가능한 Row나 Column을 다르게 해야 한다면 더 세밀한 Data Governance가 필요하다.

AWS Lake Formation의 Data Filter를 사용하면 Data Catalog Table에 대해 Row-Level, Column-Level, Cell-Level Access Control을 적용할 수 있다.

flowchart TB s3[Amazon S3
Data Storage] glue[Glue Data Catalog
Metadata] lake[AWS Lake Formation
Governance and Fine-Grained Access Control] athena[Amazon Athena
Authorized Query] s3 --- glue glue --- lake lake --- athena
S3 / IAM
Bucket, Object 중심의 접근 제어
Lake Formation
Table, Column, Row, Cell 중심의 접근 제어

따라서 여러 조직이 하나의 Data Lake를 공유하면서도 데이터의 민감도, 지역, Tenant, 부서 등에 따라 서로 다른 데이터 접근 범위를 가져야 하는 환경에서는 Lake Formation을 Data Governance Layer로 활용할 수 있다.
