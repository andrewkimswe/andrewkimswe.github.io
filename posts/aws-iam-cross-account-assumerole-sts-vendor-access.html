[AWS/IAM] 외부 업체에 Access Key를 주지 않고 AWS 계정 접근을 허용하기 - Cross-Account AssumeRole과 STS

외부 업체에 장기 Access Key를 넘기지 않고 접근을 위임하려면 IAM User 복제가 아니라 Cross-Account Role과 STS AssumeRole을 설계해야 합니다.

외부 운영 업체나 SaaS 벤더가 우리 AWS 계정의 리소스에 접근해야 할 때 가장 단순한 방법은 IAM User를 만들고 Access Key를 전달하는 것입니다. 하지만 이 방식은 외부 업체가 우리 계정의 장기 자격 증명을 보관하게 만듭니다.

flowchart LR vendor[Vendor Account] --> sts[AWS STS AssumeRole] sts --> role[Company VendorAccessRole] role --> resources[Allowed AWS Resources]

1. 문제를 먼저 분해한다

필요한 것은 Vendor AWS Account에서 Company AWS Account의 리소스에 접근하는 것입니다. 외부 업체가 이미 자신의 AWS identity를 가지고 있다면 우리 계정에 IAM User를 새로 만들 필요가 없습니다.

2. 전체 구조

flowchart TB subgraph vendorAccount[Vendor Account] automation[AutomationRole] end subgraph companyAccount[Company Account] role[VendorAccessRole] policy[Permission Policy] resource[EC2 S3 CloudWatch SSM] end automation -->|sts:AssumeRole| role role --> policy policy --> resource

3. IAM Role과 IAM User의 차이

IAM User는 password나 access key 같은 장기 credential을 가질 수 있습니다. 반면 IAM Role은 직접 장기 access key를 가지지 않고, STS를 통해 임시 보안 자격 증명을 발급받아 사용합니다.

4. Trust Policy와 Permission Policy를 같이 봐야 한다

Cross-account role에는 두 질문이 있습니다. 누가 이 role을 assume할 수 있는가, 그리고 assume한 뒤 무엇을 할 수 있는가입니다.

정책역할
Trust PolicyWHO can assume this role?
Permission PolicyWHAT can this role do?
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::<VENDOR_ACCOUNT_ID>:role/AutomationRole"
  },
  "Action": "sts:AssumeRole"
}

5. Access Key를 넘기지 않는 이유

IAM User와 Access Key를 전달하면 key 생성, 전달, 저장, rotation, 유출 대응, 계약 종료 시 폐기까지 credential lifecycle을 우리가 관리해야 합니다. AssumeRole 구조에서는 temporary credential이 자동 만료되고, trust relationship을 제거하는 방식으로 접근을 철회할 수 있습니다.

6. 최소 권한 원칙

외부 업체가 운영 업무를 한다고 해서 AdministratorAccess가 필요한 것은 아닙니다. EC2 상태 확인과 재시작만 담당한다면 DescribeInstances, RebootInstances, StartInstances, StopInstances 정도로 권한을 좁힐 수 있습니다.

7. Vendor Account 전체를 신뢰하지 않는다

trust policy에서 vendor account root를 principal로 지정할 수도 있지만, 가능하면 vendor의 특정 automation role처럼 principal을 좁히는 편이 명확합니다. 최소 권한은 resource permission뿐 아니라 누가 assume할 수 있는지에도 적용됩니다.

8. External ID와 Confused Deputy Problem

제3자 SaaS처럼 하나의 vendor가 여러 고객 AWS 계정에 접근한다면 External ID를 고려해야 합니다. External ID는 vendor가 어느 고객을 대신해 AssumeRole을 수행하는지 구분해 confused deputy risk를 줄이는 장치입니다.

{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::<VENDOR_ACCOUNT_ID>:role/AutomationRole"
  },
  "Action": "sts:AssumeRole",
  "Condition": {
    "StringEquals": {
      "sts:ExternalId": "company-specific-id"
    }
  }
}
flowchart TB attacker[Wrong Customer Context] -. Role ARN only .-> vendor[Vendor Service] vendor --> assume[AssumeRole Request] assume --> check{ExternalId valid?} check -->|yes| role[Customer Role] check -->|no| deny[Deny]

10. IAM Group이나 IdP가 답이 아닌 경우

다른 계정의 IAM User를 우리 계정의 IAM Group에 직접 추가하는 방식은 cross-account delegation 모델이 아닙니다. 또 AWS 계정 간 접근을 위해 별도의 SAML/OIDC IdP를 만드는 것도 문제의 핵심이 아닐 수 있습니다. AWS account 간에는 role trust가 기본 해법입니다.

11. 사람 접근과 machine 접근을 구분한다

외부 사람이 AWS Console과 Private EC2 OS에 접근해야 한다면 IAM Identity Center와 Session Manager 같은 workforce access 설계가 더 적절합니다. 반면 vendor의 automation workload가 우리 AWS account에 접근한다면 Cross-Account IAM Role과 STS AssumeRole이 자연스럽습니다.

Human Access -> Identity Center / Federation
Machine Cross-Account Access -> IAM Role + Trust Policy + STS

12. 외부 workload 접근의 선택 기준

다른 AWS account의 vendor 또는 automation workload가 우리 account 리소스에 접근해야 한다면 Cross-Account IAM Role과 STS AssumeRole을 먼저 검토합니다. 사람의 대화형 접근인지 machine-to-machine 접근인지부터 구분해야 권한 수명과 감사 경계를 올바르게 설계할 수 있습니다.

마무리

안전한 cross-account access의 핵심은 다른 계정의 identity를 우리 계정에 복제하는 것이 아닙니다. 기존 identity를 신뢰하고, 필요한 권한을 가진 role을 일시적으로 위임하는 것입니다.

Identity → Trust → Temporary Credential → Least Privilege 흐름으로 보면 Cross-Account IAM 설계가 훨씬 단순해집니다.
