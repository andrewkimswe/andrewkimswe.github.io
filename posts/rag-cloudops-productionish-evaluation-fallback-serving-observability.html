RAG · CloudOps · Observability

[RAG] 튜토리얼 RAG를 운영 가능한 CloudOps RAG로 확장하기 - 평가, Fallback, Serving, Observability

RAG는 Chunk, Embed, Retrieve, Generate만으로도 동작하지만 그것만으로 신뢰할 수 있는 시스템이 되지는 않는다. CloudOps RAG를 평가, fallback, serving, observability, regression gate와 untouched validation까지 확장한 흐름을 정리한다.

RAG(Retrieval-Augmented Generation)를 처음 구현하는 것은 생각보다 어렵지 않다.

문서를 나누고, 임베딩하고, Vector DB에 저장한 뒤, 질문과 유사한 문서를 검색해 LLM에 전달하면 된다.

flowchart TB doc[Document] --> chunk[Chunk] chunk --> docEmbed[Document Embedding] docEmbed --> vector[Vector DB] query[User Query] --> queryEmbed[Query Embedding] queryEmbed --> retrieve[Retrieve] vector --> retrieve retrieve --> llm[LLM] llm --> answer[Answer]

몇십 줄의 코드만으로도 "문서에 질문하면 답하는 RAG"를 만들 수 있다.

하지만 CloudOps troubleshooting처럼 운영 판단에 영향을 주는 도메인에서는 질문이 달라진다.

검색된 문서가 실제로 맞는 문서인지 어떻게 알 수 있을까?

관련 문서가 없는데도 LLM이 답을 만들어내면 어떻게 할까?

검색은 성공했지만 답변이 틀렸다면 어디에서 실패한 것일까?

외부 LLM API가 느려지거나 실패하면 API 서버는 어떻게 동작해야 할까?

실제 요청의 검색, 생성 지연 시간과 fallback 비율은 어떻게 확인할까?

CloudOps RAG 프로젝트에서는 AWS와 Kubernetes 공식 트러블슈팅 문서를 대상으로 RAG를 구현한 뒤, 단순한 데모에서 끝내지 않고 다음 lifecycle로 확장했다.

flowchart TB baseline[Baseline RAG] --> retrievalEval[Retrieval Evaluation] retrievalEval --> fallback[Threshold Fallback] fallback --> answerEval[Answer Evaluation] answerEval --> failure[Failure Analysis] failure --> serving[FastAPI Serving] serving --> reliability[Timeout / Retry] reliability --> observability[Observability]

이 글은 각 실험을 깊게 반복하기보다, 프로젝트 전체가 어떻게 "동작하는 RAG"에서 "평가하고 관찰할 수 있는 RAG"로 확장되었는지를 정리한다.

1. Baseline RAG - 답이 나온다고 시스템이 검증된 것은 아니다

CloudOps RAG의 기본 구조는 일반적인 RAG와 크게 다르지 않다.

공식 AWS/Kubernetes 문서를 가져와 파싱하고 일정 크기로 나눈 뒤, 각 chunk를 embedding하여 Chroma에 저장한다.

질문이 들어오면 동일한 embedding model로 query vector를 생성하고 유사한 chunk를 검색한다.

flowchart TB docs[Official AWS / Kubernetes Docs] --> parse[Parse] parse --> chunk[Chunk] chunk --> embedding[Embedding] embedding --> chroma[Chroma]

Runtime query는 다음과 같다.

flowchart TB query[User Query] --> embedding[Query Embedding] embedding --> retrieval[Chroma Retrieval] retrieval --> context[Retrieved Context] context --> llm[gpt-4o-mini] llm --> answer[Answer + Sources]

최종 frozen configuration은 다음과 같았다.

chunk_size       = 1024
chunk_overlap    = 128
embedding        = text-embedding-3-small
vector DB        = Chroma
retrieval_top_k  = 5
generation       = gpt-4o-mini

여기까지 구현하면 겉으로는 RAG가 완성된 것처럼 보인다. 질문을 입력하면 답이 나오고 관련 문서도 함께 표시된다.

하지만 답변이 자연스럽다는 사실은 retrieval이 제대로 작동한다는 증거가 아니다. LLM은 잘못 검색된 context를 기반으로도 자연스러운 답을 만들 수 있기 때문이다.

그래서 다음 단계는 prompt를 더 다듬는 것이 아니라 먼저 검색 품질을 측정하는 것이었다.

2. Retrieval Evaluation - 검색이 실제로 맞았는가?

검색 품질을 평가하려면 먼저 정답을 정의해야 한다.

CloudOps RAG에서는 각 평가 질문에 대해 해당 질문의 근거가 되는 공식 문서 ID를 직접 지정했다.

Question
"What should I check when an EKS pod cannot access AWS services?"

Expected document
eks-iam-roles-for-service-accounts

Ground truth를 chunk가 아니라 document ID 기준으로 정의했다. Chunk 경계는 chunk size나 overlap을 변경할 때 달라질 수 있기 때문이다.

평가 데이터는 총 50개 질문으로 구성했다.

flowchart TB total[50 Questions] --> dev[Dev: 40] total --> heldout[Held-out: 10] dev --> devIn[In-scope: 36] dev --> devOut[Out-of-scope: 4] heldout --> heldIn[In-scope: 8] heldout --> heldOut[Out-of-scope: 2]

Dev set으로 retrieval 설정을 비교한 뒤 configuration을 freeze하고, 이후 held-out set으로 확인했다.

주요 metric은 Hit@k와 MRR이었다.

Hit@k = expected document가 Top-k 안에 있는가
MRR   = 첫 번째 expected document가 얼마나 높은 rank에 있는가

Frozen configuration은 작은 held-out set에서 Hit@3 = 8/8, MRR = 0.9375를 기록했다.

이 수치는 일반 benchmark가 아니라 현재 corpus와 평가 질문에 대한 validation snapshot으로 해석해야 한다.

세부 chunking, embedding, top-k, threshold 선택 과정은 기존 retrieval tuning 글에서 따로 다뤘고, 여기서는 핵심만 남긴다.

3. Threshold Fallback - 모르면 LLM을 호출하지 않는다

Retrieval 평가 다음으로 해결하고 싶었던 문제는 관련 문서가 없는 질문이었다.

일반적인 RAG에서는 검색 결과가 좋지 않더라도 top-k 결과를 그대로 LLM에 전달할 수 있다.

flowchart TB query[Unsupported Query] --> search[Vector Search] search --> context[Irrelevant Context] context --> llm[LLM] llm --> answer[Plausible-looking Answer]

CloudOps troubleshooting 도구에서는 이것이 위험하다고 판단했다. 관련 근거가 없다면 억지로 답을 생성하기보다 답변 생성을 거부하는 편이 낫다.

그래서 top-1 retrieval distance에 threshold를 적용했다.

top_1_l2_distance <= 1.042478 -> accept, call LLM
top_1_l2_distance >  1.042478 -> reject, return fallback, skip LLM

동작은 다음과 같다.

flowchart TB query[Query] --> retrieval[Retrieval] retrieval --> distance{Top-1 L2 distance} distance -->|<= threshold| accept[Accept] distance -->|> threshold| reject[Reject] accept --> llm[Call LLM] reject --> fallback[Fallback] fallback --> skip[Skip LLM]

Dev와 held-out의 작은 out-of-scope sample에서는 threshold가 의도대로 동작했다.

하지만 threshold는 high-confidence semantic misretrieval을 막지 못한다. 높은 confidence로 잘못된 문서를 검색하면 threshold는 통과할 수 있다.

따라서 threshold fallback은 hallucination을 해결하는 만능 장치가 아니라 low-confidence generation을 통제하는 하나의 gate다.

4. Fallback과 Dependency Error는 다르다

구현하면서 구분한 또 하나의 개념은 fallback과 시스템 오류다.

둘 다 사용자에게 원하는 답이 나오지 않는다는 점에서는 비슷해 보이지만 원인이 완전히 다르다.

Fallback

flowchart TB retrieval[Retrieval succeeds] --> confidence[Confidence too low] confidence --> fallback[Return fallback] fallback --> skip[Skip LLM]

Fallback은 시스템이 설계대로 동작한 결과다.

Dependency Error

flowchart TB query[Query] --> openai[OpenAI API] openai --> failure[Timeout / Failure]

Dependency error는 외부 서비스나 네트워크 문제다.

따라서 두 상황을 동일한 error로 처리하지 않았다.

Fallback
= Controlled low-confidence response

Dependency Error
= Infrastructure / external service failure

이 구분은 metrics에서도 중요했다. Fallback rate가 증가한 것과 OpenAI failure가 증가한 것은 전혀 다른 문제이기 때문이다.

5. Answer Evaluation - 검색 성공은 답변 성공이 아니다

Retrieval 평가만으로 RAG 전체 품질을 설명할 수는 없다.

정답 문서를 검색했다고 하더라도 LLM이 중요한 내용을 누락하거나 잘못 해석할 수 있기 때문이다.

그래서 retrieval과 answer generation을 별도로 평가했다.

Answer evaluation에서는 네 가지 기준을 사용했다.

Correctness
Completeness
Faithfulness
Source Support

11개 생성 답변에 대한 human evaluation에서는 faithfulness가 가장 높고 correctness와 completeness가 상대적으로 낮았다.

이 결과에서 중요한 결론은 단순했다.

Faithful하다고 correct한 것은 아니다.

대표적인 실패 사례에서는 ConfigMap 관련 질문에 대해 Secrets 중심의 context가 검색됐다.

LLM은 검색된 context를 충실하게 사용했지만, 처음부터 context가 질문에 맞지 않았기 때문에 답변의 correctness는 낮아졌다.

flowchart TB question[Question] --> retrieval[Wrong Retrieval] retrieval --> context[Wrong Context] context --> generation[Faithful Generation] generation --> answer[Wrong Answer]

이 사례는 RAG 평가에서 retrieval quality와 answer quality를 분리해야 하는 이유를 보여준다.

6. Failure Analysis - 점수보다 실패 원인을 찾는다

평가 metric을 계산하는 것만으로는 시스템을 개선하기 어렵다.

그래서 생성된 답변의 실패를 유형별로 분류했다.

Generation-side failure
Retrieval + Generation failure
Retrieval failure
No material failure

중요한 것은 정답/오답보다 어느 단계에서 실패했는가였다.

flowchart TB query[Query] --> retrieval[Retrieval] retrieval --> context[Context] context --> generation[Generation] generation --> answer[Answer]

각 단계는 서로 다른 failure mode를 가진다.

flowchart TB miss[Relevant document not retrieved] --> retrievalFailure[Retrieval failure] omission[Relevant context present, key point omitted] --> generationFailure[Generation failure] partial[Some evidence found, not all required documents] --> multiDoc[Multi-document incompleteness] wrong[Wrong document retrieved with high confidence] --> misretrieval[High-confidence semantic misretrieval]

이렇게 원인을 분리해야 다음 실험도 구체적으로 설계할 수 있다.

7. Multi-document Retrieval은 별도의 문제다

Failure analysis에서 특히 크게 드러난 약점은 여러 문서가 동시에 필요한 질문이었다.

단일 관련 문서를 하나 찾는 것은 비교적 잘 동작했다. 하지만 두 개 이상의 문서가 모두 필요한 질문에서는 다른 문제가 생겼다.

그래서 multi-document query에는 Any-Hit과 All-Hit을 분리해서 봤다.

Any-Hit = 필요한 문서 중 하나라도 검색했는가
All-Hit = 필요한 문서를 모두 검색했는가

Held-out에서는 Any-Hit@5는 성공했지만 All-Hit@5는 실패했다.

즉 관련 문서를 하나 찾는 능력과 필요한 evidence를 모두 수집하는 능력은 다르다.

Top-5를 살펴보니 동일 문서의 유사한 chunk가 여러 자리를 차지하는 경우가 있었다. 그래서 per-document cap을 post-hoc candidate로 실험했고 Dev set에서는 효과가 있었다.

하지만 이후 untouched validation에서는 document diversity 개선은 재현됐지만 retrieval quality 개선은 재현되지 않았다. 그래서 이 설정은 frozen configuration에 넣지 않았다.

이 부분은 8월 21일 업데이트에서 다시 다룬다. 여기서는 운영 가능한 RAG로 가기 위해 failure mode를 명시적으로 분류했다는 점만 남긴다.

8. FastAPI Serving - 평가 코드와 실제 서비스는 분리한다

평가가 끝났다고 사용자가 RAG를 사용할 수 있는 것은 아니다.

그래서 FastAPI 기반 API로 runtime layer를 구성했다.

주요 endpoint는 다음과 같다.

GET  /health
GET  /metrics
POST /query
POST /documents
GET  /documents/{id}/status

전체 runtime 흐름은 다음과 같다.

flowchart TB client[Client] --> api[FastAPI] api --> embedding[Query Embedding] embedding --> chroma[Runtime Chroma] chroma --> gate{Threshold Gate} gate -->|Accept| llm[LLM] gate -->|Reject| fallback[Fallback] llm --> answer[Answer + Sources]

문서 ingestion은 다음 흐름으로 처리한다.

flowchart TB url[URL] --> fetch[Fetch] fetch --> parse[Parse] parse --> chunk[Character Chunk] chunk --> embedding[Embedding] embedding --> chroma[Runtime Chroma]

현재 portfolio-scale에서는 ingestion을 synchronous하게 처리한다. 대규모 ingestion pipeline까지 구현한 것은 아니다.

9. Evaluation Chroma와 Runtime Chroma를 분리한 이유

평가용 collection과 실제 runtime collection도 분리했다.

flowchart TB corpus[Evaluation Corpus] --> chroma[Evaluation Chroma] chroma --> eval[Offline Evaluation]
flowchart TB docs[Runtime Documents] --> chroma[Runtime Chroma] chroma --> query[User Query]

평가 데이터가 실제 runtime state와 섞이면 document ingestion이나 삭제 같은 runtime 변화가 evaluation reproducibility에 영향을 줄 수 있다.

따라서 evaluation state와 runtime state의 lifecycle을 분리했다.

필요한 경우 evaluation collection을 runtime 초기 데이터로 사용할 수 있지만, 두 collection이 같은 역할을 하는 것은 아니다.

10. Production-ish Reliability - 외부 API 실패를 제한한다

RAG에 /query endpoint를 추가했다고 바로 운영 가능한 시스템이 되는 것은 아니다.

CloudOps RAG는 OpenAI API라는 외부 dependency를 가진다.

flowchart TB api[FastAPI] --> embedding[OpenAI Embedding API] embedding --> retrieval[Retrieval] retrieval --> generation[OpenAI Generation API]

외부 API에는 timeout, rate limit, temporary server error, network failure, permanent client error가 발생할 수 있다.

그래서 호출을 무한정 기다리거나 모든 오류를 무조건 retry하는 대신 bounded timeout과 bounded retry를 적용했다.

Embedding timeout  : 30 seconds
Generation timeout : 45 seconds
Retry attempts     : max 3 total attempts

Timeout은 504로 구분한다.

flowchart TB request[Request] --> openai[OpenAI] openai --> timeout[Timeout] timeout --> response[504 external_dependency_timeout]

Timeout이 아닌 외부 dependency failure는 503으로 구분한다.

503 external_dependency_unavailable

Retry도 무조건 수행하지 않는다.

flowchart TB retryable[Retryable failure] --> retry[Bounded retry + backoff] timeout[Timeout] --> timeoutFail[Fail fast by timeout policy] permanent[Permanent 4xx] --> failFast[Fail fast]

무제한 retry는 dependency 장애 상황에서 트래픽 증폭을 만들 수 있기 때문이다.

11. Observability - RAG 내부 단계를 나눠서 본다

서비스가 실행되기 시작하면 최종 API latency 하나만 보는 것으로는 부족하다.

RAG 요청은 내부적으로 여러 단계로 구성된다.

flowchart TB query[Query] --> embedding[Embedding] query --> retrieval[Retrieval] query --> generation[Generation] embedding --> response[Response] retrieval --> response generation --> response

전체 latency가 증가했을 때 원인은 여러 가지일 수 있다.

Embedding API가 느려짐
Chroma retrieval이 느려짐
Generation이 느려짐
Fallback이 증가함
OpenAI failure가 증가함

그래서 Prometheus metric도 단계별로 분리했다.

HTTP latency
Query latency
Embedding latency
Retrieval latency
Generation latency
Fallback count/rate
Document ingestion
OpenAI failures

이렇게 하면 "RAG가 느리다"에서 끝나는 것이 아니라 어느 단계가 느린지, fallback이 늘었는지, 외부 dependency 문제가 늘었는지 구분할 수 있다.

Metric label도 제한했다.

status="success|fallback|error"
stage="embedding|retrieval|generation"
error_type="timeout|dependency|..."

사용자 query, document body, raw URL, raw exception message처럼 고유 값이 많은 데이터는 label로 사용하지 않는다.

Observability 자체가 새로운 운영 문제를 만들지 않도록 하기 위해서다.

12. 여기까지 했다고 Production-Grade RAG인가?

아니다.

CloudOps RAG는 일반적인 tutorial RAG보다 평가와 서비스 운영 요소를 확장했지만, 실제 대규모 production system이라고 주장할 수준은 아니다.

현재 구조에는 명확한 한계가 있다.

Evaluation set이 작다.
Large-scale load test가 없다.
Ingestion이 synchronous하다.
Circuit breaker가 없다.
Async retry queue가 없다.
Diversification candidate는 untouched validation에서 quality 개선이 재현되지 않았다.

이 글에서 중요한 것은 production의 모든 문제를 해결했다는 주장이 아니다.

오히려 현재 구현된 것과 아직 해결하지 않은 것을 구분하는 것이 중요했다.

13. 8월 19일 업데이트 - 회귀 방지와 운영 경계

평가, fallback, serving, observability를 추가한 뒤에도 한 가지 문제가 남았다. 한 번 좋은 retrieval configuration을 찾았다고 해서 이후 변경에서도 그 품질이 유지된다는 보장은 없다는 점이다.

일반적인 소프트웨어에서는 unit test가 기능 회귀를 잡는다. RAG에서는 코드가 정상 실행되어도 retrieval quality가 떨어질 수 있다.

flowchart TB change[Code / Retrieval / Corpus Change] --> tests[Unit Tests] tests --> pass[Tests Pass] pass --> question{Retrieval Quality?} question --> gate[Evaluation Regression Gate]

Evaluation Regression Gate

그래서 기존 evaluation 결과를 baseline으로 저장하고, 현재 retrieval 결과와 비교하는 regression gate를 CI에 연결했다.

flowchart TB baseline[results/eval_regression_baseline.json] --> checker[scripts/check_eval_regression.py] current[Current Evaluation Result] --> checker checker --> decision{Regression Check} decision -->|PASS| pass[CI Pass] decision -->|FAIL| fail[CI Fail]

Hard gate로 보는 항목은 baseline이 비교적 명확한 metric에 한정했다.

Dev Hit@3             : 33 / 36
Held-out Hit@3        :  8 / 8
Dev OOS Reject        :  4 / 4
Held-out OOS Reject   :  2 / 2

Multi-document All-Hit처럼 아직 표본이 작고 추가 검증이 필요한 metric은 warning gate로 시작했다. 모든 수치를 처음부터 hard failure로 만들면 작은 evaluation set에 과하게 최적화된 개발 흐름이 될 수 있기 때문이다.

flowchart TB stable[Stable baseline metric] --> hard[Hard Gate] exploratory[Promising but insufficiently validated metric] --> warning[Warning Gate]

Production Readiness Boundary

Regression gate까지 추가했다고 해서 이 프로젝트를 실제 대규모 production system이라고 부르지는 않았다. 대신 현재 상태를 구현된 것, 정책으로 정의한 것, 아직 검증하지 않았거나 의도적으로 범위 밖에 둔 것으로 나누었다.

flowchart TB implemented[Implemented] --> current[Current System] policy[Readiness / Policy] --> current out[Not Yet Validated / Out of Scope] --> current

실제로 구현한 영역은 retrieval evaluation, threshold fallback, answer evaluation, failure analysis, FastAPI serving, timeout/retry/backoff, Prometheus metrics, evaluation regression gate, CI test와 Docker build다.

반면 SLO, latency/cost budget, large-scale load test 같은 영역은 실제 production traffic 없이는 달성 여부를 주장하기 어렵다. 그래서 현재는 관찰해야 할 지표와 판단 기준을 정의하는 수준으로 제한했다.

Corpus Governance

RAG에서 corpus는 단순한 초기 데이터가 아니다. 문서가 추가되거나 변경되면 chunk, embedding, candidate ranking이 바뀌고 retrieval behavior도 달라질 수 있다.

flowchart TB corpus[Corpus Change] --> chunk[Chunk Change] chunk --> embedding[Embedding Change] embedding --> ranking[Candidate Ranking Change] ranking --> quality[Retrieval Quality Change]

그래서 corpus 변경은 콘텐츠 업데이트가 아니라 system behavior를 바꿀 수 있는 변경으로 취급한다. CloudOps RAG에서는 공식 AWS/Kubernetes troubleshooting documentation을 source로 삼고, evaluation ground truth는 안정적인 doc_id 기준으로 관리한다.

Rollout Policy

Dev metric이 좋아졌다고 바로 새로운 retriever나 configuration을 채택하지 않는다. Dev set을 반복해서 보며 설정을 바꾸면 그 데이터에 맞춰진 결과일 수 있기 때문이다.

flowchart TB dev[Dev Evaluation] --> heldout[Held-out Validation] heldout --> answer[Diagnostic Answer Evaluation] answer --> canary[Canary] canary --> rollout[Full Rollout]

현재 프로젝트에서 실제 production traffic canary를 수행한 것은 아니다. 여기서 중요한 점은 좋은 Dev 결과와 검증된 rollout을 구분하고, 향후 변경을 적용할 때 볼 guardrail을 명시했다는 것이다.

Monitoring Budget

Metric은 많이 수집하는 것보다 어떤 운영 질문에 답하는지가 중요하다.

Query latency     -> 사용자가 경험하는 응답 시간이 증가했는가?
Retrieval latency -> vector retrieval이 병목인가?
Generation latency -> LLM dependency가 latency를 지배하는가?
Fallback rate     -> 지원하지 못하는 query가 증가했는가?
OpenAI failure    -> 외부 dependency 문제가 발생하는가?
Retry count       -> 일시적 dependency failure가 증가하는가?
Ingestion metric  -> 문서 처리가 정상적으로 완료되는가?

사용자 query, document URL, raw exception message처럼 값이 계속 늘어나는 데이터는 Prometheus label로 사용하지 않는다. Observability를 추가하면서 monitoring system 자체의 cardinality 문제를 만들지 않기 위해서다.

의도적으로 아직 넣지 않은 것

Circuit breaker, async retry queue, async ingestion, large-scale load test는 기술적으로 추가할 수 있다. 하지만 현재 CloudOps RAG는 local portfolio API이고 실제 production traffic이나 장기간 dependency failure distribution이 없다.

그래서 현재는 timeout, bounded retry, backoff, dependency error classification을 우선 적용했다. 확장 가능한 구조를 알고 있다는 이유만으로 현재 workload에 필요하지 않은 infrastructure를 추가하지 않는 것도 중요한 판단이라고 봤다.

다음 우선순위

가장 직접적으로 검증할 가치가 있는 개선안은 multi-document retrieval diversification이었다. Per-document cap 후보는 Dev에서 promising했지만, 이 가설은 Dev failure analysis에서 나온 post-hoc 개선안이었다.

따라서 다음 단계는 더 많은 기능을 붙이는 것이 아니라, 이미 관찰한 failure mode가 새로운 데이터에서도 같은 방식으로 개선되는지 확인하는 것이었다.

14. 8월 21일 업데이트 - Dev에서 좋아진 결과를 바로 적용하지 않은 이유

앞선 failure analysis에서는 multi-document 질문에서 필요한 문서를 모두 가져오지 못하는 문제가 확인되었다.

특히 Top-5 검색 결과에서 하나의 문서에서 나온 여러 chunk가 상위 결과를 차지하면서 다른 관련 문서가 들어올 공간을 줄이는 현상이 있었다.

flowchart TB top[Top-5 Retrieval Result] --> s1[Secrets / chunk 3] top --> s2[Secrets / chunk 7] top --> s3[Secrets / chunk 2] top --> c1[ConfigMap / chunk 1] top --> s4[Secrets / chunk 9] s1 --> docs[Only 2 unique documents] s2 --> docs s3 --> docs c1 --> docs s4 --> docs

검색 결과 5개를 사용하고 있지만 실제로 포함된 문서는 2개뿐인 셈이다.

이 문제를 확인하기 위해 기존 dense similarity 순서는 유지하되, 하나의 문서에서 최대 2개의 chunk만 Top-k에 포함시키는 per-document cap=2를 실험했다.

Dev set에서는 baseline 대비 multi-document 질문의 All-Hit@5가 개선되었다.

Metric Baseline cap=2
Multi All-Hit@5 2/6 4/6
Avg. unique documents 1.975 2.950
Duplicate ratio 0.605 0.365

결과만 보면 cap=2를 새로운 retrieval policy로 적용해도 될 것처럼 보였다.

하지만 이 가설 자체가 Dev set의 실패 사례를 분석한 뒤 만들어졌다는 문제가 있었다.

flowchart TB devFailure[Dev failure 확인] --> duplicate[Duplicate occupancy 발견] duplicate --> hypothesis[cap=2 가설 설계] hypothesis --> sameDev[같은 Dev set에서 다시 평가] sameDev --> improved[성능 개선]

따라서 이 결과만으로는 실제로 일반화되는 개선인지, Dev set의 실패 패턴에 맞춰진 post-hoc optimization인지 구분하기 어렵다.

그래서 cap=2를 frozen configuration에 바로 반영하지 않고, 기존 Dev 질문과 분리된 untouched validation set을 만들었다.

diversification_validation.csv

Total        : 12
In-scope     : 11
Out-of-scope : 1

확인하려는 질문은 단순했다.

Dev에서 관찰된 diversification 효과가 새로운 질문에서도 재현되는가?

먼저 document diversity 개선은 재현되었다.

Metric Baseline cap=2
Avg. unique document count 2.0000 3.3333
Avg. duplicate ratio 0.6000 0.3167

cap=2를 적용하자 평균 unique document 수가 약 2개에서 3.33개로 증가했고, duplicate ratio는 0.60에서 약 0.32까지 감소했다.

하지만 실제 retrieval quality를 측정하자 결과가 달랐다.

Metric Baseline cap=2
Hit@3 11/11 11/11
Hit@5 11/11 11/11
MRR 0.8030 0.8030
Multi All-Hit@5 1/3 1/3

Dev에서는 Multi All-Hit@5가 2/6 -> 4/6으로 개선되었지만, untouched validation에서는 1/3 -> 1/3으로 개선이 재현되지 않았다.

flowchart TB cap[cap=2] --> diversity[Top-k document diversity 증가] cap --> quality[Retrieval completeness 증가] diversity --> yes[재현됨] quality --> no[재현되지 않음]

이 차이가 이번 실험에서 가장 중요한 결과였다. 검색 결과가 다양해졌다는 것과 검색 품질이 좋아졌다는 것은 같은 의미가 아니었다.

처음 세운 가설은 동일 문서 chunk가 Top-k를 과점하고, 그 때문에 다른 relevant document가 밀려 multi-document retrieval이 실패한다는 것이었다.

하지만 cap=2로 빈자리를 만들어도 그 자리에 항상 필요한 문서가 들어오는 것은 아니었다.

flowchart TB baseline[Baseline Top-5] --> a1[Doc A chunk 1] baseline --> a2[Doc A chunk 2] baseline --> a3[Doc A chunk 3] baseline --> c1[Doc C chunk 1] baseline --> a4[Doc A chunk 4] capped[cap=2 Top-5] --> ca1[Doc A chunk 1] capped --> ca2[Doc A chunk 2] capped --> cc1[Doc C chunk 1] capped --> d1[Doc D chunk 1] capped --> e1[Doc E chunk 1] expected[Expected: Doc A + Doc B] expected -.-> docb[Doc B is not in top candidates]

필요한 Doc B가 dense retrieval의 후보 상위권에 존재하지 않는다면 duplicate를 제거하는 것만으로는 문제를 해결할 수 없다.

Diversity는 retrieval completeness의 필요조건이 될 수 있지만, 충분조건은 아니었다.

그래서 frozen configuration은 변경하지 않았다.

flowchart TB dev[Dev Experiment] --> improved[cap=2 improvement observed] improved --> untouched[Untouched Validation] untouched --> diversity2[Diversity improvement reproduced] untouched --> noQuality[Retrieval improvement not reproduced] noQuality --> keep[Keep frozen configuration]

처음 목표만 보면 실패한 실험처럼 보일 수 있다. 하지만 이 결과 덕분에 failure model은 더 구체화되었다.

flowchart TB failure[Multi-document failure] failure --> duplicate2[Duplicate chunk occupancy] failure --> recall[Relevant document candidate recall] failure --> confusion[Semantic confusion] failure --> ranking[Ranking problem]

Duplicate occupancy는 실제 현상이지만 전체 failure의 유일한 원인은 아니었다.

따라서 다음 분석에서 확인해야 할 질문도 명확해졌다.

필요한 문서가 raw candidate pool에는 존재하지만 Top-5 ranking에서 밀린 것인가, 아니면 dense retriever가 처음부터 해당 문서를 후보로 가져오지 못한 것인가?

flowchart TB query[Query] --> dense[Dense Retrieval] dense --> pool[Top-20 / Top-50 Candidate Pool] pool --> expected{Expected Documents 존재?} expected -->|YES| ranking2[Ranking / Reranking 문제] expected -->|NO| embedding[Embedding / Query Representation 문제]

만약 expected document가 Top-20에는 있지만 Top-5에 없다면 diversification이나 reranking을 개선할 여지가 있다.

반대로 Top-20이나 Top-50에도 없다면 Top-5 후처리만 바꿔서는 해결할 수 없다. 이 경우에는 embedding, query representation, chunking 또는 retrieval architecture 자체를 다시 살펴봐야 한다.

이번 diversification 실험에서 얻은 가장 큰 결과는 새로운 retrieval heuristic 자체보다 평가 과정이었다.

가설을 세우고, 이미 본 데이터에서 효과를 확인하고, 보지 않은 데이터에서 다시 검증한 뒤, 개선이 재현되지 않으면 적용하지 않는 것.

RAG를 개선하면서 중요한 것은 새로운 기법을 계속 추가하는 것만이 아니었다.

15. 튜토리얼 RAG에서 무엇이 달라졌는가

처음에는 다음 구조였다.

flowchart LR chunk[Chunk] --> embed[Embed] embed --> retrieve[Retrieve] retrieve --> generate[Generate]

하지만 프로젝트를 진행하면서 구조는 다음처럼 확장됐다.

flowchart TB build[Build] --> measure[Measure] measure --> compare[Compare] compare --> freeze[Freeze] freeze --> heldout[Held-out Validate] heldout --> answerEval[Answer Evaluate] answerEval --> failures[Analyze Failures] failures --> serve[Serve] serve --> observe[Observe]

가장 큰 변화는 기술 스택 자체가 아니었다.

시스템을 바라보는 질문이 달라졌다.

검색은 실제로 맞았는가?
검색 결과가 불확실하면 답하지 않을 수 있는가?
검색 성공과 답변 성공을 구분할 수 있는가?
실패가 Retrieval 때문인지 Generation 때문인지 알 수 있는가?
외부 API가 실패하면 시스템은 어떻게 반응하는가?
어느 단계에서 latency가 증가했는지 확인할 수 있는가?

CloudOps RAG에서 가장 중요했던 것은 새로운 프레임워크를 하나 더 추가하는 것이 아니라 이 질문들에 답할 수 있는 구조를 만드는 것이었다.

16. 정리

RAG를 구현하는 가장 단순한 구조는 여전히 유효하다.

flowchart LR chunk[Chunk] --> embed[Embed] embed --> retrieve[Retrieve] retrieve --> generate[Generate]

하지만 이것만으로는 retrieval이 맞았는지, unsupported query인지, answer가 올바른지, 어디에서 실패했는지, dependency가 정상인지, latency가 어디서 발생하는지 알 수 없다.

CloudOps RAG에서는 이를 평가, fallback, answer evaluation, failure analysis, serving, reliability, observability, regression gate, untouched validation으로 확장했다.

그리고 이 과정에서 얻은 가장 중요한 결론은 다음과 같다.

RAG가 답을 생성한다는 것과 RAG 시스템이 신뢰할 수 있게 동작한다는 것은 서로 다른 문제다.

검색 품질을 측정하고, 근거가 부족하면 생성을 중단하고, retrieval과 generation을 따로 평가하고, 실패 원인을 분류하고, 외부 dependency의 timeout과 retry를 통제하고, 실제 요청의 각 단계를 관찰할 수 있어야 단순한 RAG 데모를 넘어가기 시작한다.

CloudOps RAG는 아직 완전한 production-grade 시스템은 아니다.

하지만 현재 구현된 것과 아직 해결하지 않은 것을 구분하고, 측정 결과와 한계를 함께 남기는 것.

그것이 이번 프로젝트에서 동작하는 RAG를 평가하고 운영할 수 있는 RAG로 확장하면서 가장 중요하게 본 부분이다.
