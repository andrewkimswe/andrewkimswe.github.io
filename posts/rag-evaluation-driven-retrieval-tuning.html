RAG · Evaluation · Retrieval Tuning

[RAG] 감으로 Top-k를 정하지 않기 - Chunking, Embedding, Threshold를 실험으로 선택한 과정

작은 RAG 프로젝트에서도 chunk size, embedding model, top_k, threshold를 감으로 고르면 이후 결과를 설명하기 어렵다. Development set에서 비교하고 freeze한 뒤 held-out으로 확인한 과정을 정리한다.

2026.08.11 RAG Evaluation Retrieval

RAG를 처음 구현할 때는 많은 값이 임의로 정해진다.

chunk_size = 1000
overlap = 100
top_k = 4

튜토리얼에서는 충분하다. 하지만 실제 프로젝트에서는 왜 이 chunk size인지, 왜 이 embedding model인지, 왜 Top-5인지, 검색 결과를 언제 신뢰하지 않아야 하는지 설명할 수 있어야 한다.

CloudOps RAG에서는 이 질문에 답하기 위해 Build, Measure, Compare, Freeze, Held-out Validate 순서로 retrieval configuration을 선택했다.

1. 평가 대상

Corpus는 AWS와 Kubernetes 공식 troubleshooting 문서 20개로 구성했다. Retrieval dataset은 직접 작성한 50개 질문이고, development와 held-out으로 나눴다.

Split 구성
Development 40 questions, in-scope 36, out-of-scope 4
Held-out 10 questions, in-scope 8, out-of-scope 2

작은 dataset이므로 이 결과를 일반 benchmark로 해석하지 않는다.

2. Ground Truth를 Document로 정의한 이유

Chunking 설정을 바꾸면 chunk ID와 경계가 바뀐다. 특정 chunk를 정답으로 고정하면 chunking experiment 자체가 ground truth를 바꾼다. 그래서 expected source는 document ID 수준으로 정의했다. 

expected_doc_ids = ["k8s_debug_pods"]

평가는 검색된 chunk가 어느 expected document에서 왔는지를 확인한다.

3. Hit@k와 MRR

Hit@k는 expected document가 Top-k 안에 하나라도 존재하면 hit로 본다. MRR은 첫 번째 relevant result가 얼마나 높은 순위에 있는지 본다.

Metric 의미
Hit@k 필요한 문서가 Top-k 안에 있는가?
MRR 첫 relevant result가 얼마나 앞에 있는가?
Multi All-Hit 복수 evidence가 필요한 질문에서 모두 검색됐는가?

RAG generator는 한 개 문서만 사용하는 것이 아니므로 Hit@1만으로 retrieval quality를 판단하기 어렵다.

4. Chunking Experiment

대표 설정으로 512/0과 1024/128을 비교했다.

설정 관찰
512 / 0 더 세밀하지만 문맥이 끊길 수 있다.
1024 / 128 Hit@3가 32/36에서 33/36으로 개선됐지만 Hit@1과 MRR은 감소했다.

프로젝트에서는 generation에 여러 context가 들어간다는 점과 Top-3 evidence coverage를 고려해 1024/128을 선택했다. 이는 universal optimum이 아니라 이 corpus와 evaluation set에서의 engineering trade-off다.

5. Embedding Model 비교

선택된 chunking 설정에서 OpenAI text-embedding-3-small과 sentence-transformers/all-MiniLM-L6-v2를 비교했다.

Embedding Development Hit@3
MiniLM 31/36
OpenAI text-embedding-3-small 33/36

MiniLM이 잘못된 모델이라는 뜻은 아니다. 로컬 실행, privacy, cost, latency 요구사항이 다르면 선택도 달라질 수 있다.

6. Top-k

k를 늘리면 relevant document를 찾을 가능성이 높아질 수 있지만 무한정 늘릴 수는 없다.

장점
Recall이 증가할 수 있고 multi-document question에서 coverage가 좋아질 수 있다.
비용
Context size, generation cost, noise, duplicate evidence가 함께 증가할 수 있다.

프로젝트에서는 k=3과 k=5를 비교했고, multi-document query에서 Multi All-Hit이 0/6에서 2/6으로 개선되어 최종 top_k = 5를 선택했다.

7. Out-of-Scope 질문과 Distance Threshold

CloudOps 문서만 가진 시스템에 프랑스 혁명은 왜 일어났나요? 같은 질문이 들어와도 vector store는 가장 가까운 문서를 반환한다. Nearest neighbor search에는 기본적으로 관련 문서 없음이라는 결과가 없다.

그래서 가장 가까운 문서가 충분히 가까운지 판단하는 gate가 필요하다.

top_1_l2_distance <= 1.042478
accept

top_1_l2_distance > 1.042478
fallback

Development에서는 in-scope 36/36 accept, out-of-scope 4/4 reject를 기록한 뒤 threshold를 freeze했다.

8. Freeze

flowchart TB experiments[Development Experiments] decision[Configuration Decision] freeze[Freeze] heldout[Held-out Evaluation] experiments --- decision decision --- freeze freeze --- heldout 
chunk_size = 1024
chunk_overlap = 128
embedding = text-embedding-3-small
top_k = 5
threshold = L2 <= 1.042478
generation = gpt-4o-mini

Held-out 결과를 보고 다시 threshold나 chunking을 바꾸면 held-out set은 더 이상 held-out이 아니다. 이후 개선 아이디어는 frozen result와 분리해 post-hoc experiment로 취급했다.

9. Held-out Validation

항목 결과
Hit@1 7/8
Hit@3 8/8
MRR 0.9375
Threshold 8/8 in-scope accepted, 2/2 out-of-scope rejected

좋은 snapshot이지만 표본이 매우 작다. 따라서 CloudOps 질문을 100% 정확하게 검색한다가 아니라, 8개의 in-scope held-out questions에서 expected document가 모두 Top-3 내에 나타났다고 제한해서 말해야 한다.

10. Threshold가 해결하지 못하는 것

Distance gate가 잘 작동해도 semantic misretrieval을 막지는 못한다. ConfigMap 질문이 Secrets 문서와 높은 similarity를 보이면 threshold는 high-confidence wrong retrieval을 accept할 수 있다.

해결하는 것
low-confidence out-of-scope retrieval
해결하지 못하는 것
high-confidence wrong retrieval

11. Evaluation Collection과 Runtime Collection

서비스에 새로운 URL을 등록할 수 있게 만들면서 evaluation index가 변경되면 과거 실험을 재현하기 어렵다. 그래서 frozen experiments용 Evaluation Chroma와 mutable service data용 Runtime Chroma를 분리했다.

flowchart TB official[Official Corpus] eval[Frozen Eval Collection] results[Evaluation Results] ingestion[Runtime Ingestion] runtime[Mutable Runtime Collection] query[Production-like Query Path] official --- eval eval --- results ingestion --- runtime runtime --- query

정리

CloudOps RAG에서 최종 configuration은 1024/128 character chunking, text-embedding-3-small, Chroma, top_k = 5, L2 threshold = 1.042478, gpt-4o-mini였다.

하지만 핵심은 숫자 자체가 아니다. RAG configuration을 tutorial default나 감으로 고르지 않고, Development set에서 비교하고 freeze한 뒤 Held-out set에서 검증하는 과정이 더 중요했다. retrieval을 측정하고 나면 다음 질문이 생긴다. expected document를 잘 찾았으면 최종 답변도 좋은가?
