RAG · Query Clarification · State

[RAG] 불완전한 질문을 바로 검색하지 않기 - Running State와 Slot Filling으로 Query Clarification 설계하기

사용자의 질문이 충분히 구체적이지 않다면 retriever가 의도를 추측하게 된다. 검색 전에 running state를 채우고, 필요한 slot이 부족할 때 clarification을 수행하는 구조를 정리한다.

2026.08.09 RAG LangChain CloudOps

일반적인 RAG 파이프라인은 사용자의 질문이 들어오면 곧바로 임베딩하고, 벡터 검색을 수행한 뒤, 검색된 문서를 LLM의 컨텍스트에 넣는다. 질문이 충분히 구체적이라면 이 구조는 잘 동작한다.

flowchart TB query[User Query] embedding[Embedding] retriever[Retriever] context[Context] llm[LLM] answer[Answer] query --- embedding embedding --- retriever retriever --- context context --- llm llm --- answer

하지만 실제 운영 환경의 질문은 항상 친절하지 않다. Kubernetes 운영 지원 시스템에 Pod가 계속 죽어요라는 질문이 들어오면 Pod 상태, OOMKilled 여부, 최근 배포 변경, 특정 노드 재현 여부, 애플리케이션 로그 같은 중요한 정보가 빠져 있다.

이 상태에서 바로 semantic retrieval을 수행하면 검색기가 사용자의 의도를 추측해야 한다. 검색에 필요한 조건 자체가 질문에 없다면 embedding model을 바꾸는 것만으로 해결하기 어렵다.

1. Stateless RAG의 한계

가장 단순한 RAG 요청은 stateless function처럼 볼 수 있다.

def answer(question):
    documents = retriever.invoke(question)
    return generator.invoke(question, documents)

입력은 question, 출력은 answer다. 문제는 질문 자체가 부족한 경우다. EC2가 느려요만으로는 CPU, EBS I/O, 네트워크, 메모리 중 어디를 봐야 할지 알기 어렵다.

검색 전에 질문을 더 완전하게 만드는 단계가 필요할 수 있다.

2. Running State

대화형 시스템도 일반 프로그램처럼 실행 중 필요한 정보를 보존할 state가 필요하다.

state = {
    "user_input": "Pod가 계속 죽어요",
    "service": None,
    "resource": None,
    "symptom": None,
    "error": None,
    "recent_change": None,
}

첫 번째 분석 이후에는 다음처럼 갱신될 수 있다.

state = {
    "user_input": "Pod가 계속 죽어요",
    "service": "Kubernetes",
    "resource": "Pod",
    "symptom": "restarting",
    "error": None,
    "recent_change": None,
}
flowchart TB initial[Initial State] branchA[Branch A] updatedA[Updated State] branchB[Branch B] updatedB[Updated State] initial --- branchA branchA --- updatedA updatedA --- branchB branchB --- updatedB

3. Branch는 State에서 필요한 값을 계산한다

Branch는 전체 state를 입력받아 특정 값을 계산하는 작은 chain으로 생각할 수 있다. 예를 들어 internal LLM이 질문에서 troubleshooting 정보를 추출하고, 그 결과를 기존 state에 병합한다. 

{
  "service": "Kubernetes",
  "resource": "Pod",
  "symptom": "restarting"
}

중요한 것은 chain의 출력으로 기존 입력 전체를 대체하지 않고 필요한 값을 state에 누적하는 것이다. LangChain 계열의 runnable abstraction에서는 passthrough와 assignment 패턴으로 이런 구조를 만들 수 있다.

4. Slot Filling

troubleshooting에 필요한 필드를 slot으로 정의한다.

required_slots = [
    "service",
    "resource",
    "symptom",
    "error",
]

사용자가 EKS에서 Pod가 계속 재시작돼요라고 말했다면 service, resource, symptom은 어느 정도 채워졌지만 error는 아직 비어 있다. 이때 retrieval로 바로 가지 않고 clarification branch를 실행한다.

Pod 상태나 이벤트에서 CrashLoopBackOff, OOMKilled 같은 메시지가 보이나요?

사용자가 답하면 error = CrashLoopBackOff처럼 state를 갱신하고, 그제야 retrieval-ready query를 만들 수 있다.

5. 전체 흐름

flowchart TB input[User Input] state[Initialize / Update State] extraction[Internal LLM
Extract Slots] check[Required Information Sufficient?] clarify[Clarifying Question] query[Build Retrieval Query] retriever[Retriever] generator[Generator] answer[Answer] input --- state state --- extraction extraction --- check check --- clarify clarify --- state check --- query query --- retriever retriever --- generator generator --- answer
Internal Model
사용자에게 직접 보여줄 답이 아니라 다음 행동을 결정할 structured state를 만든다.
External Model
검색된 근거를 바탕으로 최종 사용자 응답을 생성한다.

6. Structured Output이 중요한 이유

Internal LLM에게 자유 형식 문장을 생성하게 한 뒤 Python이 다시 해석하면 불안정하다. 가능한 경우 명시적인 schema를 정의하는 편이 좋다. 

{
  "service": "EKS",
  "resource": "Pod",
  "symptom": "restart",
  "error": "CrashLoopBackOff",
  "needs_clarification": false
}

이 결과는 사람이 읽기 위한 답이 아니라 프로그램이 다음 branch를 선택하기 위한 데이터다. 그래서 slot filling은 단순 prompt engineering보다 애플리케이션 로직에 가깝다.

7. 모든 Slot을 무조건 채워야 할까?

그렇지는 않다. Pod가 Pending 상태인데 왜 그런가요?는 이미 상당히 구체적이지만 Kubernetes가 이상해요는 추가 정보가 필요하다. 목표는 모든 정보를 수집하는 것이 아니라 검색에 필요한 정보만 수집하는 것이다.

Too Little
검색 입력이 모호해져 retrieval ambiguity가 커진다.
Too Much
사용자에게 불필요한 질문을 반복해 conversation friction이 커진다.

8. CloudOps RAG에 적용한다면

기존 query path가 retrieval confidence를 generation 전에 확인하는 구조라고 해보자.

flowchart TB user[User Query] clarification[Query Clarification Layer] structured[Structured State] ready[Retrieval Ready?] ask[Ask User] embedding[Embedding] chroma[Chroma] gate[Confidence Gate] result[Generation / Fallback] user --- clarification clarification --- structured structured --- ready ready --- ask ask --- clarification ready --- embedding embedding --- chroma chroma --- gate gate --- result

Query Clarification은 입력 정보가 충분한지 확인하고, retrieval threshold는 검색 결과를 신뢰할 만한지 확인한다. 두 단계는 서로 다른 문제를 해결한다.

9. Query Rewriting과의 관계

state에 필요한 정보가 모였다면 최종 retrieval query를 마지막 사용자 문장 그대로 사용할 필요가 없다. Pod가 계속 죽어요와 CrashLoopBackOff예요라는 대화가 있었다면 다음처럼 검색 질의를 구성할 수 있다. 

EKS Kubernetes Pod CrashLoopBackOff troubleshooting

running state는 conversational memory뿐 아니라 retrieval query construction의 입력이 된다.

10. 언제 Retrieval을 실행할 것인가

state와 conditional logic이 있다면 retrieval 자체도 선택할 수 있다.

General Conversation
retrieval 없이 직접 응답한다.
Missing Information
검색 전에 clarification을 수행한다.
Unsupported Domain
지원 범위 밖 질문으로 거절한다.
Troubleshooting Query
retrieval과 generation을 수행한다.

CloudOps처럼 실패 비용이 있는 영역에서는 가능한 부분을 명시적인 state, schema, condition으로 제한하는 것이 디버깅과 평가에 유리하다.

11. 구현 전에 측정해야 할 것

Query Clarification을 추가했다고 RAG가 자동으로 좋아졌다고 말할 수는 없다.

영역 확인할 것
Retrieval Hit@k, MRR, multi-document metrics가 개선되는가?
Interaction Cost 평균 clarification turn, clarification rate, time to final answer가 적절한가?
Answer Quality correctness, completeness, faithfulness, source support가 좋아지는가?

정리

RAG 성능 문제가 보이면 embedding model이나 vector DB부터 바꾸고 싶어진다. 하지만 retrieval의 입력인 질문 자체가 불완전하다면 검색기만 개선해서 해결할 수 없는 문제가 있다.

Running State와 Slot Filling을 사용하면 retrieval 전에 질문을 구조화하고, 필요한 정보가 부족한 경우 사용자에게 다시 묻고, 충분한 정보가 모였을 때 검색 질의를 구성할 수 있다. 좋은 RAG는 답변 생성뿐 아니라 검색하기 좋은 질문을 만드는 과정까지 포함한다.
