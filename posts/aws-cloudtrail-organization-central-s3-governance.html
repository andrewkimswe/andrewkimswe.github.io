멀티 계정 환경에서 CloudTrail을 중앙 S3 버킷으로 보내는 작업은 짧은 Bucket Policy 하나로 시작할 수 있습니다. 하지만 보안 감사에서 필요한 것은 "지금 객체가 들어온다"가 아니라 "앞으로 추가될 계정도 빠짐없이 들어오며, 누군가 정책을 바꾸거나 KMS 키를 비활성화해도 정해진 시간 안에 발견하고 복구할 수 있다"는 보장입니다.

이 글은 실제 프로덕션 수치를 회고하는 글이 아니라, 소규모 AWS Organizations 환경을 운영 가능한 중앙 감사 로그 체계로 전환하기 위한 설계와 검증 계획입니다. 아래의 수치는 측정 결과가 아니라 도입 전에 합의할 acceptance target이며, 구현 뒤 대시보드에서 실측값으로 교체해야 합니다.

1. 문제를 객체 저장이 아니라 감사 연속성으로 정의한다

Account B와 Account C의 임의 IAM Principal에게 Account A의 S3 쓰기 권한을 주고 싶은 것이 아닙니다. 각 계정의 CloudTrail이 만든 감사 로그만 Log Archive 계정에 전달하고, workload 계정의 관리자는 수집 경로와 보존 정책을 변경하지 못하게 만들고 싶습니다.

flowchart LR subgraph org[AWS Organization] management[Management Account] workloadB[Workload Account B] workloadC[Workload Account C] end subgraph archive[Log Archive Account] bucket[(Central S3 Bucket)] key[KMS Key] monitor[Delivery Monitor] end management --> trail[Organization Trail] trail --> workloadB trail --> workloadC trail -->|Service delivery| bucket key --> bucket bucket --> monitor

이 문제에는 네 종류의 실패가 있습니다.

실패결과탐지 기준
Coverage gap새 계정이나 Region이 Trail에 포함되지 않음Organizations 계정 목록과 Trail 상태 비교
Delivery gapS3 또는 KMS 정책 오류로 객체가 도착하지 않음get-trail-status와 객체 도착 지연
Integrity gap전달 이후 객체가 변조 또는 삭제됨Digest chain과 validate-logs
Access gap불필요한 Principal이 로그를 읽거나 삭제함Access Analyzer, IAM 검토, negative test

2. 요구사항과 비요구사항을 먼저 고정한다

아키텍처를 선택하기 전에 운영 계약을 먼저 고정합니다. 여기서는 다음을 요구사항으로 둡니다.

  • 현재 계정뿐 아니라 이후 Organization에 추가되는 계정도 자동으로 management event 수집 대상이 됩니다.
  • CloudTrail 서비스만 정해진 S3 prefix와 KMS key를 사용할 수 있습니다.
  • 수집 권한과 열람 권한을 분리하고, workload 계정에는 기본적으로 중앙 로그 읽기 권한을 주지 않습니다.
  • 정책 변경은 코드 리뷰와 자동 검증을 거쳐야 하며 콘솔의 수동 수정은 drift로 취급합니다.
  • 수집 지연, 전달 오류, 무결성 검증 실패에 담당자와 대응 시간이 존재합니다.

반면 모든 data event를 무조건 수집하거나 CloudTrail Lake를 즉시 도입하는 것은 비요구사항입니다. Data event는 양이 많고 첫 번째 사본부터 비용이 발생하므로, 보호할 resource와 탐지 use case가 정해진 뒤 별도 예산으로 추가합니다.

3. 개별 Trail보다 Organization Trail을 선택한 이유

중앙 수집에는 계정별 Trail과 Organization Trail 두 선택지가 있습니다.

기준계정별 TrailOrganization Trail
계정 온보딩계정마다 생성과 정책 갱신 필요Organization 가입 시 자동 적용
예외 구성계정별로 세밀함조직 공통 baseline에 적합
운영 주체각 계정 또는 StackSetsManagement 또는 delegated administrator
Drift surface계정 수만큼 증가중앙 Trail과 정책으로 축소
비용 위험중복 management event 사본이 생기기 쉬움공통 baseline을 한 사본으로 관리

계정별로 서로 다른 이벤트 셀렉터가 반드시 필요한 환경이 아니라면 Organization Trail이 더 단순합니다. AWS는 Organization에 계정이 추가될 때 Trail 사본과 service-linked role을 추가하고 logging을 자동으로 시작합니다. Member account는 Trail을 볼 수 있지만 중지하거나 삭제할 수 없습니다.

단, opt-in Region을 사용하는 경우에는 계정과 Organization Trail의 home Region 조건을 확인해야 합니다. "multi-Region" 한 줄만으로 모든 opt-in Region이 자동 커버된다고 가정하면 coverage gap이 생길 수 있습니다.

4. Service Principal만 허용해도 충분하지 않다

cloudtrail.amazonaws.com을 Principal로 지정하면 IAM User나 Role 대신 CloudTrail 서비스가 쓰도록 제한할 수 있습니다. 그러나 그 서비스는 모든 AWS 고객이 사용합니다. 따라서 "어떤 서비스인가"와 함께 "어떤 Trail인가"를 확인해야 합니다.

flowchart TD request[PutObject request] --> principal{Principal is CloudTrail?} principal -->|no| deny[Deny] principal -->|yes| source{SourceArn is approved Trail?} source -->|no| deny source -->|yes| prefix{Target is approved org prefix?} prefix -->|no| deny prefix -->|yes| acl{Required ACL header?} acl -->|no| deny acl -->|yes| allow[Allow delivery]

aws:SourceAccount도 지원되지만 Organization Trail에서는 값이 member account가 아니라 Trail 소유자인 management account입니다. 따라서 Account B와 C의 ID 배열만 넣는 정책은 Organization Trail 모델과 맞지 않습니다. 특정 Trail ARN까지 고정하는 aws:SourceArn을 주 경계로 사용하고, S3 object resource를 Organization prefix로 좁히는 편이 정확합니다.

5. 실제 S3 Bucket Policy의 최소 경계

다음 정책은 prefix를 사용하지 않는 Organization Trail의 핵심 부분입니다. 실제 적용 시 partition, home Region, management account ID, organization ID와 Trail 이름을 IaC 변수로 주입합니다.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AWSCloudTrailAclCheck",
      "Effect": "Allow",
      "Principal": { "Service": "cloudtrail.amazonaws.com" },
      "Action": "s3:GetBucketAcl",
      "Resource": "arn:aws:s3:::<CENTRAL_LOG_BUCKET>",
      "Condition": {
        "StringEquals": {
          "aws:SourceArn": "arn:aws:cloudtrail:<HOME_REGION>:<MANAGEMENT_ACCOUNT_ID>:trail/<TRAIL_NAME>"
        }
      }
    },
    {
      "Sid": "AWSCloudTrailManagementAccountWrite",
      "Effect": "Allow",
      "Principal": { "Service": "cloudtrail.amazonaws.com" },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::<CENTRAL_LOG_BUCKET>/AWSLogs/<MANAGEMENT_ACCOUNT_ID>/*",
      "Condition": {
        "StringEquals": {
          "s3:x-amz-acl": "bucket-owner-full-control",
          "aws:SourceArn": "arn:aws:cloudtrail:<HOME_REGION>:<MANAGEMENT_ACCOUNT_ID>:trail/<TRAIL_NAME>"
        }
      }
    },
    {
      "Sid": "AWSCloudTrailOrganizationWrite",
      "Effect": "Allow",
      "Principal": { "Service": "cloudtrail.amazonaws.com" },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::<CENTRAL_LOG_BUCKET>/AWSLogs/<ORGANIZATION_ID>/*",
      "Condition": {
        "StringEquals": {
          "s3:x-amz-acl": "bucket-owner-full-control",
          "aws:SourceArn": "arn:aws:cloudtrail:<HOME_REGION>:<MANAGEMENT_ACCOUNT_ID>:trail/<TRAIL_NAME>"
        }
      }
    }
  ]
}

arn:aws:s3:::bucket/* 전체를 허용하지 않는 이유는 delivery identity뿐 아니라 destination scope도 최소화하기 위해서입니다. Prefix를 쓴다면 Trail 설정과 Bucket Policy의 prefix가 정확히 일치해야 합니다. 한쪽만 변경하면 CloudTrail이 로그를 전달하지 못합니다.

6. KMS 정책은 쓰기와 읽기를 분리한다

SSE-KMS를 켜는 순간 S3 Policy만 맞아서는 부족합니다. CloudTrail에는 kms:GenerateDataKey*와 kms:DescribeKey가 필요하고, 로그를 읽는 조사 Role에는 별도의 kms:Decrypt가 필요합니다. 암호화 권한을 얻었다고 복호화 권한까지 생기지 않게 분리합니다.

{
  "Sid": "AllowCloudTrailEncryptLogs",
  "Effect": "Allow",
  "Principal": { "Service": "cloudtrail.amazonaws.com" },
  "Action": "kms:GenerateDataKey*",
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "aws:SourceArn": "arn:aws:cloudtrail:<HOME_REGION>:<MANAGEMENT_ACCOUNT_ID>:trail/<TRAIL_NAME>"
    },
    "StringLike": {
      "kms:EncryptionContext:aws:cloudtrail:arn": "arn:aws:cloudtrail:*:<MANAGEMENT_ACCOUNT_ID>:trail/*"
    }
  }
}

KMS key가 disable되거나 정책이 틀리면 CloudTrail은 로그를 전달하지 못합니다. 따라서 KMS 변경은 일반 애플리케이션 키 변경보다 높은 위험도로 분류하고, security break-glass role 외에는 key disable과 deletion schedule 권한을 주지 않습니다.

7. 보존은 암호화와 다른 통제다

암호화는 내용을 보호하지만 삭제를 막지 않습니다. 중앙 버킷에는 Block Public Access, versioning, lifecycle과 별도 read role을 적용합니다. 규제나 포렌식 요구가 있다면 S3 Object Lock도 검토합니다.

처음부터 compliance mode를 적용하지는 않습니다. Compliance mode에서는 root user도 보존 기간 안에 객체를 삭제할 수 없고 기간을 줄일 수 없으므로, 잘못된 retention 설정 자체가 운영 사고가 될 수 있습니다. 먼저 governance mode와 짧은 retention으로 복구 절차, lifecycle, 비용을 검증한 뒤 승인된 데이터 분류에만 compliance mode를 적용합니다.

flowchart LR delivered[Delivered log] --> hot[S3 Standard
investigation window] hot --> archive[S3 archive class
long retention] archive --> expire[Expire by policy] delivered --> digest[Integrity digest] digest --> validate[Scheduled validation]

8. 정책을 코드로 만들고 회귀를 CI에서 막는다

중앙 로그 정책은 배포 한 번보다 이후 변경이 더 위험합니다. IaC와 CI에서 최소한 다음 불변 조건을 검사합니다.

  • CloudTrail write statement의 Principal은 cloudtrail.amazonaws.com입니다.
  • aws:SourceArn은 승인된 Organization Trail ARN과 정확히 일치합니다.
  • s3:PutObject Resource는 management account 또는 Organization log prefix 밖으로 확장되지 않습니다.
  • 와일드카드 Principal, public read, workload account의 delete 권한이 없습니다.
  • KMS encrypt와 investigator decrypt Principal이 분리되어 있습니다.
  • Multi-Region, log file validation, bucket versioning이 활성화되어 있습니다.
# policy-regression.yml
checks:
  - id: cloudtrail-source-arn-required
    resource: central_log_bucket_policy
    assert: exact_trail_arn
  - id: cloudtrail-prefix-bounded
    resource: central_log_bucket_policy
    deny_if_resource_matches: "arn:aws:s3:::central-log-bucket/*"
  - id: investigator-cannot-delete
    principal: SecurityInvestigatorRole
    denied_actions:
      - s3:DeleteObject
      - kms:ScheduleKeyDeletion
  - id: trail-baseline
    assert:
      multi_region: true
      log_file_validation: true

이 YAML은 특정 도구 문법이 아니라 검증 계약의 예시입니다. 실제 프로젝트에서는 CDK assertions, Terraform test, OPA/Conftest 또는 조직의 policy-as-code 도구 중 이미 사용하는 것을 선택합니다. 이 규모에서 검증만을 위해 별도 상시 서비스를 만들 필요는 없습니다.

9. 한 번에 전환하지 않고 관측 가능한 단계로 rollout한다

기존 계정별 Trail이 있다면 바로 제거하지 않습니다. 짧은 기간 동안 새 Organization Trail과 병행해 계정·Region별 객체 도착과 event selector를 비교합니다. 중복 사본은 비용을 만들 수 있으므로 이 기간에는 종료 조건과 최대 기간을 둡니다.

flowchart LR inventory[0. Existing trail inventory] --> sandbox[1. Sandbox account] sandbox --> canary[2. Canary OU] canary --> dual[3. Short dual logging] dual --> verify{Coverage and delivery pass?} verify -->|no| rollback[Keep old trail
fix and retry] verify -->|yes| expand[4. Expand to organization] expand --> retire[5. Retire duplicate trails]

Rollout gate는 다음과 같습니다.

  1. Sandbox에서 승인·거부 정책 테스트를 통과합니다.
  2. Canary OU에서 모든 활성 Region의 management event가 중앙 prefix에 도착합니다.
  3. KMS 암호화와 investigator read-only 복호화를 각각 검증합니다.
  4. 24시간 이상 SLO 위반과 delivery error가 없을 때 범위를 확대합니다.
  5. 중복 Trail 제거 전 Cost Explorer에서 paid duplicate event가 없는지 확인합니다.

10. Delivery SLO를 정의하고 오류와 지연을 분리한다

CloudTrail은 CloudWatch Logs에 이벤트를 평균 약 5분 안에 전달하지만 이는 보장 시간이 아닙니다. 따라서 AWS 설명을 그대로 SLO로 선언하지 않고 우리 시스템의 내부 목표를 정의합니다.

SignalAcceptance target측정 방법
Coverage활성 계정·Region 100%Organizations inventory와 Trail 상태 정기 비교
Delivery freshness99.9%가 15분 이내 도착eventTime과 S3 관측 시각의 차이
Delivery error연속 10분 오류 없음get-trail-status의 latest error 필드
Integrity일일 검증 실패 0건aws cloudtrail validate-logs
Policy drift다음 검사 주기 안에 100% 탐지IaC drift와 AWS Config 또는 정기 비교

15분과 99.9%는 AWS SLA가 아니라 이 시스템의 초기 목표입니다. 실제 workload와 조사 요구가 30분을 허용한다면 더 느슨하게 잡을 수 있습니다. 반대로 보안 탐지 파이프라인이 5분 안에 반응해야 한다면 S3 archive 경로와 별도로 CloudWatch Logs 또는 EventBridge의 실시간 경로를 설계해야 합니다.

11. 모니터링은 로그 내용과 로그 파이프라인을 함께 본다

CloudTrail 이벤트에서 위험 API를 찾는 모니터링과 CloudTrail 자체가 정상 전달되는지 확인하는 모니터링은 다릅니다. 후자가 없으면 탐지 시스템이 조용한 이유가 "위험 이벤트가 없음"인지 "로그가 끊김"인지 구분할 수 없습니다.

12. 실패 유형별 runbook을 분리한다

모든 문제를 "CloudTrail 장애"로 묶으면 복구가 느려집니다.

증상먼저 볼 곳복구 후 검증
InsufficientEncryptionPolicyExceptionKMS key 상태, SourceArn, encryption context새 객체의 KMS key ID와 delivery status
S3 AccessDeniedBucket Policy prefix, ACL condition, SourceArn새 로그와 digest가 모두 도착
특정 계정만 누락Organization membership, opt-in Region, Trail copy해당 account ID prefix 생성
Digest chain 실패누락·이동·변조된 digest와 log object원래 위치에서 validate-logs 재실행
비용 급증중복 Trail, data event selector, CloudWatch Logs ingestusage type과 일별 event volume 안정화

Bucket 또는 KMS 정책 오류가 나면 CloudTrail은 최대 30일 동안 재전송을 시도하고 재전송에도 표준 요금이 발생할 수 있습니다. 따라서 "언젠가 다시 들어오겠지"가 아니라 오류 발생 시각, 수정 시각, backfill 종료 시각을 incident timeline에 남깁니다.

13. 비용은 계정 수보다 이벤트 사본과 보존에서 관리한다

비용 모델은 다음 네 항목으로 나눕니다.

Monthly cost
  = duplicate management event delivery
  + selected data event delivery
  + S3 storage and lifecycle transitions
  + optional CloudWatch Logs or query cost

첫 번째 management event 사본은 Region별로 무료지만 추가 사본에는 비용이 생기며, data event는 첫 사본부터 과금됩니다. 따라서 "보안을 위해 모든 것을 수집"하기보다 threat model에 맞춰 S3 object-level, Lambda invoke 같은 data event를 선택합니다.

초기 비용 guardrail은 금액을 임의로 정하기보다 현재 7일 event volume으로 baseline을 만든 뒤 정합니다. 예를 들어 management event 유료 사본은 0을 목표로 하고, data event와 CloudWatch Logs ingest는 주간 증감률과 절대 예산을 함께 경보로 둡니다.

14. 계정 온보딩과 예외를 governance workflow로 만든다

Organization Trail이 새 계정을 자동 포함하더라도 "계정 생성 완료"와 "감사 준비 완료"는 같지 않습니다. Account vending workflow에 다음 검증을 포함합니다.

  1. 계정이 승인된 OU와 Organization Trail에 포함되었는지 확인합니다.
  2. 활성·opt-in Region 목록을 inventory에 반영합니다.
  3. 중앙 S3에 해당 account ID 경로가 생성되는지 확인합니다.
  4. 예외 data event selector가 있다면 owner, 사유, 만료일을 기록합니다.
  5. 계정 폐쇄 시 보존 기간과 조사 접근권한을 별도 처리합니다.

예외에는 반드시 만료일이 있어야 합니다. 비용 때문에 특정 data event를 끄거나 기술적 이유로 Region을 제외했다면 영구 설정으로 남기지 않고 재검토 날짜를 둡니다.

15. 운영 책임을 코드 소유권과 incident 역할로 나눈다

긴급 복구에서 누가 Bucket Policy를 바꿀 수 있는지, 누가 KMS key를 다시 enable할 수 있는지, 누가 감사 증적을 열람할 수 있는지를 미리 분리합니다. 한 명의 관리자에게 수집 중지, 로그 삭제, key 삭제와 조사 권한이 모두 모이지 않게 하는 것이 핵심입니다.

16. 배포 후 검증은 성공 테스트와 거부 테스트를 함께 한다

"S3에 파일 하나가 생겼다"만으로는 완료가 아닙니다. 다음 acceptance suite를 실행합니다.

# Trail이 logging 중이고 delivery error가 없는지 확인
aws cloudtrail get-trail-status --name <TRAIL_ARN>

# 설정 baseline 확인
aws cloudtrail get-trail --name <TRAIL_ARN>
aws cloudtrail get-event-selectors --trail-name <TRAIL_ARN>

# 지정 기간의 digest와 log 무결성 확인
aws cloudtrail validate-logs \
  --trail-arn <TRAIL_ARN> \
  --start-time <ISO_8601_TIME> \
  --verbose
  • 허용된 Organization Trail은 management·organization prefix에 쓸 수 있습니다.
  • 임의 IAM Role과 승인되지 않은 Trail은 같은 bucket에 쓸 수 없습니다.
  • Investigator role은 읽고 복호화할 수 있지만 삭제하거나 retention을 바꿀 수 없습니다.
  • Workload account administrator는 Organization Trail을 중지하거나 수정할 수 없습니다.
  • 새 계정을 canary로 추가했을 때 별도 수동 정책 수정 없이 로그가 도착합니다.
  • KMS와 Bucket Policy의 의도적 오류를 sandbox에서 주입했을 때 경보와 runbook이 작동합니다.

17. 아직 production-grade라고 주장하지 않는 범위

이 설계만으로 모든 감사 요구를 충족했다고 볼 수는 없습니다.

  • 실제 계정·Region 규모에서 delivery freshness 분포를 측정하지 않았습니다.
  • 조직의 법적 보존 기간과 Object Lock mode는 compliance owner의 승인이 필요합니다.
  • 모든 서비스의 data event를 수집하지 않으므로 threat model별 selector 검토가 남아 있습니다.
  • CloudTrail Lake, Security Lake, SIEM 전달은 분석 요구와 비용을 확인한 뒤 별도 결정해야 합니다.
  • 복구 훈련과 KMS key 장애 주입을 정기적으로 실행하기 전에는 runbook의 실효성을 보장할 수 없습니다.

이 한계를 적는 이유는 기술 목록을 늘리는 것보다 어디까지 검증했는지 구분하는 것이 더 중요한 운영 정보이기 때문입니다.

18. 마무리

CloudTrail 중앙화의 핵심은 여러 계정에 S3 쓰기 권한을 주는 것이 아닙니다. Organization이 만드는 coverage, Service Principal과 SourceArn이 만드는 delivery boundary, KMS와 보존 정책이 만드는 evidence boundary, SLO와 runbook이 만드는 운영 책임을 연결하는 것입니다.

Central logging은 저장 위치가 아니라 통제 시스템입니다. 수집 여부뿐 아니라 누락을 언제 발견하고, 누가 복구하며, 어떤 증거로 정상화를 판단할지까지 설계해야 합니다.
