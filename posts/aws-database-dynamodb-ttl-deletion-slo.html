[AWS/Database] TTL이 지났는데 왜 데이터가 계속 보일까? - DynamoDB TTL, Streams, 삭제 SLO

세션, 인증 코드, 임시 권한과 개인정보 처리 중간 상태를 DynamoDB에 저장할 때 TTL을 자주 사용합니다. 그런데 expireAt이 지난 직후 같은 item을 조회했더니 여전히 반환될 수 있습니다. TTL이 고장 난 것이 아니라, 애플리케이션이 기대한 만료와 DynamoDB가 수행하는 물리 삭제의 의미가 달랐던 것입니다.

이 글은 실제 프로덕션 장애 회고가 아니라, TTL이 있는 DynamoDB table을 운영 가능한 데이터 lifecycle로 만들기 위한 설계와 검증 계획입니다. 아래 숫자는 실측 결과나 AWS SLA가 아닌 초기 acceptance target입니다. 부하와 삭제 지연을 실제 환경에서 측정하기 전에는 개선 결과로 주장하지 않습니다.

1. 문제를 삭제 실패가 아니라 서로 다른 네 개의 시계로 정의한다

하나의 item에는 적어도 네 개의 시각이 존재합니다. 이 시각을 하나로 취급하면 만료된 세션이 다시 노출되거나, 삭제 후처리가 늦고, 감사 기록은 완료라고 표시되는 문제가 생깁니다.

운영상 가장 중요한 계약은 물리 삭제가 늦어도 논리적으로 만료된 데이터는 즉시 사용할 수 없어야 한다는 것입니다.

2. DynamoDB TTL은 삭제 예약이지 삭제 시각 보장이 아니다

TTL attribute는 Unix epoch의 초 단위 Number여야 합니다. 유효한 시각이 현재보다 과거가 되면 item은 삭제 대상이 되지만 즉시 삭제되는 것은 아닙니다. AWS 문서상 만료 item은 일반적으로 며칠 안에 background process로 삭제될 수 있습니다.

삭제 대기 중인 item은 GetItem, Query, Scan에서 계속 보일 수 있고 저장 공간과 읽기 비용에도 포함됩니다. 문자열 timestamp, millisecond epoch, 대소문자가 다른 attribute와 5년보다 오래된 과거 값은 TTL process가 기대대로 처리하지 않을 수 있습니다.

TTL은 "이 시각에 지워 달라"는 lifecycle hint입니다. "이 시각부터 절대로 읽히지 않는다"는 접근 통제도, 정해진 시각까지 삭제된다는 compliance SLA도 아닙니다.

4. Data contract에 만료 시각과 정책 버전을 함께 남긴다

expireAt 하나만 있으면 왜 그 시각이 선택되었는지 추적하기 어렵습니다. Writer가 clock, unit과 retention policy를 소유하도록 item contract를 고정합니다.

{
  "pk": "SESSION#01J8...",
  "subjectId": "USER#4821",
  "createdAt": "2026-09-04T01:20:00Z",
  "expireAt": 1788481200,
  "retentionPolicy": "session-v3",
  "schemaVersion": 2
}
  • expireAt은 UTC Unix epoch seconds를 Number로 기록합니다.
  • Millisecond 값이 들어가지 않도록 허용 가능한 최소·최대 범위를 schema validation에 둡니다.
  • 보존 기간을 코드 곳곳에 상수로 복제하지 않고 retentionPolicy에서 계산합니다.
  • 영구 item과 임시 item을 같은 table에 둘 경우 TTL attribute가 없는 상태의 의미를 문서화합니다.
  • Client가 전달한 만료 시각을 그대로 신뢰하지 않고 server가 계산합니다.
from datetime import datetime, timedelta, timezone

RETENTION = {
    "session-v3": timedelta(hours=8),
    "verification-v2": timedelta(minutes=10),
}


def expiration_epoch(policy: str, now: datetime | None = None) -> int:
    current = now or datetime.now(timezone.utc)
    expires = current + RETENTION[policy]
    return int(expires.timestamp())

5. Read path가 논리적 만료를 즉시 집행한다

GetItem에는 FilterExpression이 없으므로 애플리케이션이 반환 전에 expireAt을 검사해야 합니다. 만료 item은 존재 여부를 외부에 드러내지 않고 not found 또는 domain-specific expired response로 변환합니다.

import time
from decimal import Decimal


def get_active_item(table, key):
    item = table.get_item(
        Key=key,
        ConsistentRead=True,
    ).get("Item")

    if item is None:
        return None

    expire_at = item.get("expireAt")
    if not isinstance(expire_at, Decimal):
        raise ValueError("invalid lifecycle contract")

    if int(expire_at) <= int(time.time()):
        return None

    return item

Query와 Scan에서는 FilterExpression으로 만료 item을 결과에서 제외할 수 있습니다. 그러나 filter는 DynamoDB가 item을 읽은 뒤 적용되므로 읽기 capacity를 줄여주지 않으며, 1MB 평가 한도도 filter 이전에 적용됩니다. 만료 item이 대부분이라면 timestamp를 sort key에 포함하거나 active item 전용 access pattern을 설계해야 합니다.

flowchart TD request[Read request] --> fetch[Get or Query] fetch --> exists{Item exists?} exists -->|no| missing[Return not found] exists -->|yes| contract{Valid numeric expireAt?} contract -->|no| error[Contract violation metric] contract -->|yes| active{expireAt greater than now?} active -->|no| hidden[Return expired or not found] active -->|yes| serve[Return item]

6. 만료 직전 갱신은 조건식으로 경쟁을 막는다

만료된 item이 아직 물리 삭제되지 않았을 때 일반 UpdateItem을 실행하면 stale writer가 데이터를 되살릴 수 있습니다. 반대로 TTL process가 먼저 삭제한 뒤 조건 없는 update가 오면 같은 key의 새 item이 만들어질 수 있습니다.

import time
from datetime import timedelta


def refresh_session(table, key, policy="session-v3"):
    now = int(time.time())
    next_expiry = now + int(RETENTION[policy].total_seconds())

    return table.update_item(
        Key=key,
        UpdateExpression=(
            "SET expireAt = :next, retentionPolicy = :policy"
        ),
        ConditionExpression=(
            "attribute_exists(pk) AND expireAt > :now"
        ),
        ExpressionAttributeValues={
            ":next": next_expiry,
            ":now": now,
            ":policy": policy,
        },
    )

ConditionalCheckFailedException은 무조건 재시도할 transient error가 아닙니다. 이미 만료되었거나 삭제된 session이라는 domain 결과로 처리해야 합니다. 갱신 가능 시간과 최대 lifetime도 정책에 넣어 무한 연장을 막습니다.

7. TTL과 Streams 설정을 IaC와 상태 검증으로 묶는다

TTL attribute 이름은 대소문자를 구분하며 restored table에는 TTL을 다시 구성해야 합니다. 콘솔 설정에 의존하지 않고 table 정의와 배포 검증에 포함합니다.

TTL 활성화는 모든 partition에 전파되는 데 시간이 걸릴 수 있고 UpdateTimeToLive 호출은 idempotent하지 않습니다. 배포 코드는 먼저 DescribeTimeToLive로 현재 상태를 읽고, 이미 원하는 설정이면 성공으로 처리합니다.

8. Streams는 삭제를 빠르게 만드는 장치가 아니라 후처리 경계다

TTL이 item을 실제 삭제하면 같은 Region의 DynamoDB Streams record에 service delete를 식별할 수 있는 userIdentity가 포함됩니다. Lambda는 일반 사용자 삭제와 TTL 삭제를 구분해 lifecycle audit, 비민감 archive 또는 파생 저장소 정리를 수행할 수 있습니다.

sequenceDiagram participant T as DynamoDB TTL participant D as DynamoDB Table participant S as DynamoDB Streams participant L as Cleanup Lambda participant A as Lifecycle Audit T->>D: Delete expired item D->>S: REMOVE with OldImage S->>L: Service delete event L->>L: Validate policy and deduplicate L->>A: Record non-sensitive completion 
from datetime import datetime, timezone


def handler(event, context):
    failures = []
    now = datetime.now(timezone.utc).timestamp()

    for record in event["Records"]:
        identity = record.get("userIdentity", {})
        is_ttl_delete = (
            record.get("eventName") == "REMOVE"
            and identity.get("type") == "Service"
            and identity.get("principalId") == "dynamodb.amazonaws.com"
        )
        if not is_ttl_delete:
            continue

        old_image = record["dynamodb"].get("OldImage", {})
        expire_at = int(old_image["expireAt"]["N"])
        deletion_lag = max(0, now - expire_at)

        try:
            emit_lifecycle_metric(deletion_lag, old_image)
            write_non_pii_audit(old_image)
        except Exception:
            failures.append({"itemIdentifier": record["eventID"]})

    return {"batchItemFailures": failures}

이 consumer는 partial batch response, bounded retry, maximum record age와 on-failure destination을 함께 설정해야 합니다. 삭제 대상이 개인정보라면 OldImage 전체를 로그나 DLQ에 복사하지 않고 key hash, 정책 버전과 완료 시각처럼 필요한 최소 증거만 남깁니다.

9. Global Tables에서는 삭제 출처와 비용 경계가 달라진다

MREC Global Tables에서는 한 Region에서 발생한 TTL 삭제가 다른 replica로 복제됩니다. 최초 TTL 삭제는 원본 Region의 write capacity를 소비하지 않지만, 각 replica의 복제 삭제에는 replicated write capacity 또는 replicated write request 비용이 발생합니다. 대량 만료가 replica write traffic과 겹치면 provisioned capacity에서 throttling 가능성도 검토해야 합니다.

TTL service identity는 실제 TTL 삭제가 수행된 Region의 Stream에서만 식별할 수 있습니다. 모든 Region에서 같은 filter가 TTL 이벤트를 잡을 것이라고 가정하면 후처리가 누락되거나 중복됩니다. 삭제 audit consumer의 실행 Region과 failover 절차를 명시해야 합니다. 또한 MRSC Global Tables는 TTL을 지원하지 않으므로 consistency mode 선택 단계에서 확인합니다.

10. 삭제 기한이 있는 데이터는 별도 erasure workflow를 사용한다

회원 탈퇴나 보안 incident처럼 삭제 완료 기한이 있는 요청을 expireAt = now로 끝내면 안 됩니다. 명시적 workflow가 원본 item을 삭제하고, downstream 저장소별 작업을 추적하며, TTL은 누락된 임시 데이터에 대한 safety net으로만 남습니다.

flowchart TD request[Erasure request] --> ledger[Create idempotent job] ledger --> deny[Immediately deny reads and writes] deny --> primary[Delete primary DynamoDB items] primary --> copies{Downstream copies} copies --> search[Search index] copies --> object[S3 objects] copies --> analytics[Analytics dataset] search --> verify[Verify completion] object --> verify analytics --> verify verify --> evidence[Store minimal audit evidence]

Primary table의 DeleteItem 성공은 전체 삭제 완료와 같지 않습니다. Streams, backups, export, data lake, search index와 로그의 보존 정책을 inventory해야 합니다. 삭제 증거에는 원본 개인정보를 넣지 않고 request ID, 대상 범주, 정책 버전, 완료 시각과 결과만 기록합니다.

11. Backup과 restore는 lifecycle 정책을 자동 복원하지 않는다

PITR이나 on-demand backup은 실수로부터 복구하기 위한 제어이고 TTL은 운영 table의 lifecycle 제어입니다. 과거 시점으로 복원하면 그 시점에 존재하던 item이 새 table에 돌아올 수 있으며, restored table의 TTL 설정도 다시 확인해야 합니다.

Restore runbook에는 다음 단계를 포함합니다.

  1. 복원 table을 production read path에 연결하기 전에 TTL 상태와 attribute 이름을 확인합니다.
  2. 현재 시각 기준으로 만료된 item을 read path가 숨기는지 검증합니다.
  3. 삭제 요청 ledger와 대조해 되살아난 대상이 없는지 검사합니다.
  4. 검색·분석 등 downstream 재구축 과정에서도 동일한 retention filter를 적용합니다.
  5. 검증이 끝난 뒤에만 traffic을 전환하고 복원 근거를 남깁니다.

12. Rollout 순서는 read 차단이 TTL 활성화보다 먼저다

flowchart LR inventory[1. Inventory data and copies] --> shadow[2. Shadow-write expireAt] shadow --> audit[3. Audit type and coverage] audit --> read[4. Enforce logical expiry] read --> stream[5. Enable Streams consumer] stream --> ttl[6. Enable TTL on canary table] ttl --> gate{7. Lifecycle gates pass?} gate -->|no| contain[Stop new TTL writes
contain irreversible deletes] gate -->|yes| expand[8. Expand and observe]

TTL 삭제는 되돌릴 수 없으므로 feature flag처럼 간단히 rollback할 수 없습니다. 잘못된 timestamp가 이미 기록된 상태에서 TTL부터 켜면 대량 삭제가 시작될 수 있습니다. 먼저 shadow-write 기간에 attribute type, 초 단위 범위, 정책별 분포와 누락률을 검사합니다.

TTL을 비활성화해도 잠시 삭제가 계속될 수 있으므로 rollback은 "즉시 삭제 중단"으로 표현하지 않습니다. 이상 징후가 보이면 새 TTL writer를 중단하고 table backup, change freeze와 incident 절차로 영향을 제한합니다.

15. CloudWatch 기본 지표만으로 삭제 적시성을 증명할 수 없다

특히 삭제량 급증은 처리량을 늘려 빨리 끝낼 문제가 아닐 수 있습니다. Millisecond와 seconds 혼동 또는 잘못된 retention migration이면 데이터 손실 incident이므로 먼저 변경을 멈추고 복구 가능성을 확보해야 합니다.

17. 비용 모델에는 읽힌 만료 item과 replica 삭제를 포함한다

Monthly lifecycle cost
  = reads of expired-but-not-deleted items
  + storage during deletion lag
  + DynamoDB Streams read and Lambda processing
  + replicated TTL deletes across MREC replicas
  + explicit erasure writes and downstream cleanup
  + audit storage and lifecycle canary cost

원본 Region에서 TTL system delete가 write capacity를 소비하지 않는다는 사실만으로 "무료 삭제"라고 부르면 안 됩니다. Query filter 이전에 읽은 만료 item은 read cost를 만들고, Global Tables replica delete에는 replicated write 비용이 발생하며, Streams consumer와 파생 저장소 정리도 과금됩니다.

비용 최적화는 TTL lag를 임의로 줄이는 것이 아니라 access pattern을 바꾸는 데서 시작합니다. 만료 item 비율, item 크기, read 빈도와 replica 수를 측정해 별도 ephemeral table이나 시간 기반 key가 더 경제적인지 비교합니다.

18. Lifecycle contract를 CI와 배포 gate로 고정한다

# lifecycle-gate.yml - 특정 CI 제품에 종속되지 않은 계약 예시
dynamodb_ttl_gate:
  schema:
    attribute: expireAt
    type: number
    unit: epoch_seconds
    allowed_policies:
      - session-v3
      - verification-v2
  require:
    expired_read_exclusion: 100%
    new_item_ttl_coverage: 100%
    invalid_ttl_values: 0
    stale_refresh_rejected: 100%
    stream_partial_failure_test: pass
    restore_lifecycle_check: pass
  block_on:
    - ttl_attribute_rename
    - retention_reduction_without_approval
    - read_guard_removed
    - destructive_backfill_without_backup

Schema test만으로는 충분하지 않습니다. clock boundary, daylight saving과 무관한 UTC 계산, expired-but-present item, conditional update, pagination, cache와 restore 경로를 contract test에 포함합니다. Retention 기간 단축은 일반 설정 변경이 아니라 대량 삭제를 일으킬 수 있는 destructive change로 취급합니다.

20. 아직 production-grade라고 주장하지 않는 범위

  • 이 글의 삭제 지연과 erasure SLO는 실제 AWS 환경에서 측정한 값이 아닙니다.
  • 대량 backfill과 같은 시각에 집중된 수백만 item 만료를 부하 테스트하지 않았습니다.
  • MREC Global Tables의 Region 장애 중 TTL 발생과 consumer failover를 검증하지 않았습니다.
  • 모든 backup, export, 로그와 분석 dataset에 대한 법적 삭제 요구를 특정하지 않았습니다.
  • Streams 24시간 보존 범위 안에서 장기 consumer 장애를 복구하는 별도 replay source를 구현하지 않았습니다.
  • Client cache, CDN과 외부 SaaS로 복제된 데이터까지 end-to-end 삭제를 증명하지 않았습니다.

이 범위가 남아 있다면 "TTL을 켰다"고 말할 수는 있지만 "삭제 lifecycle을 운영한다"고 말하기는 어렵습니다. 실제 canary의 lag 분포, 실패한 migration, restore drill과 승인 기록을 채워야 운영 주장이 완성됩니다.

21. 마무리

DynamoDB TTL의 핵심은 자동 삭제 기능 자체가 아닙니다. 논리적 만료는 애플리케이션이 즉시 집행하고, 물리 삭제는 비동기 process로 관측하며, 기한이 있는 삭제는 별도 workflow로 보장하는 책임 분리입니다.

TTL이 지난 item을 보여주지 않는 책임과 실제로 지워졌는지 증명하는 책임은 서로 다릅니다. 두 책임을 데이터 contract, SLO와 운영 절차로 연결해야 TTL이 기능에서 lifecycle이 됩니다.
